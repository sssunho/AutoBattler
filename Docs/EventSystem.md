# 정적 이벤트 시스템 명세

개정일: 2026-11-01

이 문서는 `plan.md`와 `World_Premise.md`의 현재 원정 구조를 기준으로 한다.

축복의 상세 규칙은 [BlessingSystem.md](BlessingSystem.md)를 따른다. 이 문서는 이벤트가 축복 조건에 쓰이는 태그·상태를 제공하고, 처리 완료 후 축복 시스템으로 연결하는 책임 경계를 정의한다.

장비의 보관·거래·고정 강화와 일반·특수 장비 콘텐츠는 [MercenarySystem.md](MercenarySystem.md), 전투 효과는 [BattleSystem.md](BattleSystem.md)를 따른다. 이벤트의 장비 강화 기회·특수 장비 보상은 확정 요구사항이며, 현행 Result JSON의 장비 처리 지원과 대상 선택·적용 순서는 별도 계약이다.

원정 목표와 종료 규칙은 왕의 길잡이 획득과 시간 소진 후 최종 도전 전환을 기준으로 한다. `GoalCatalog`, `Goal` Event, `goalId`, `RevealedGoalIds`와 `revealGoalIds`는 현행 데이터 계약의 명칭을 유지한다. 별도 Goal Node 타입이나 복수 최종 목표를 뜻하지 않으며, 단일 목표의 획득 확인·최종 도전 진행 상태와 기존 데이터의 이행 계약은 별도로 정한다. 문서 반영은 코드·데이터 마이그레이션 완료를 의미하지 않는다.

---

## 1. 목적

이 시스템은 자유롭게 장소를 이동하며 전투하고 파티를 성장시키는 모험에서, 사건과 선택·고정 스토리라인을 정적 이벤트 데이터로 구성하고 처리한다.

사전에 설계한 스토리라인을 최소 3개 제공하는 것이 콘텐츠 목표다. 이는 즉시 구현 범위가 아니며, 각 스토리라인을 서로 분리된 일방통행 이동 루트로 만들지 않는다. 내용·진행 순서·상호 관계·완주 조건과 Arc 데이터의 연결은 별도 설계한다. 모든 스토리라인 완주를 최종 도전의 필수 조건으로 간주하지 않는다.

중앙 도시가 전설의 보물 **왕의 길잡이**를 가져온 자에게 큰 상을 약속하고 모험가가 찾아 떠난다. 길잡이는 옛 왕가가 소유했던 신비로운 도구로 왕실의 도로와 숨겨진 통로를 드러낸다. 최종 목표 장소는 하나이며 길잡이를 지닌 채 실종된 왕의 마지막 행선지를 중심으로 구상한다. 세부 장소·왕의 행적·최종 난관은 미정이다.

목표노드의 최종 사건이나 전투를 해결하고 길잡이를 실제로 획득하는 순간 모험을 끝낸다. 단순 도착·목격·전투 승리만으로 성공을 대신하지 않는다. 시간제한은 탐험과 성장의 준비 기간이며, 제한 전에는 언제든 최종 도전에 나설 수 있다. 조기 도전의 별도 보상·점수·이득은 없다. 시간이 소진되면 현재 방문의 결과까지 처리한 뒤 최종 도전으로 전환한다.

원정은 대도시 Node에서 시작한다. 이미 알려진 장소는 도시를 중심으로 방사형으로 펼쳐져 있으며, 이미 밝혀진 구간의 이동 방식은 미정이다. 유한한 특별 장소의 발견·영구 기록·해금 개념은 최종 목표와 구분하여 유지한다.

이벤트 데이터는 개발 단계에서 정적으로 생성한다. 런타임에는 LLM이 개입하지 않는다. 이벤트끼리는 다음 Event ID를 직접 지정하지 않으며, 연결과 분기는 State·Tags·Arc Stage로 표현한다. 짧은 텍스트·낮은 빈도로 이벤트를 축소하는 방안은 아직 확정하지 않았다.

## 2. 책임 분리

### 이벤트 생성기

이벤트 생성기는 다음 내용을 만든다.

- 이벤트의 제목과 본문
- 발생 가능한 Location과 State 조건
- 선택지 또는 자동 결과
- 선택 후 결과 문구
- 전투가 발생한다는 사실
- Tags, Fame, Reputation, Money의 변화
- 축복 조건에 쓰이는 태그의 추가를 포함한 이벤트 결과
- 해당 이벤트가 속한 Arc의 진행 변화
- 현행 `revealGoalIds` 계약에 따른 목표 정보 공개 효과
- Opening, Introduction, Normal 등 이벤트의 역할과 최종 도전의 서사·결과

이벤트 생성기는 다음 내용을 결정하지 않는다.

- 런의 총 원정 시간
- Edge의 `weight`와 이동 시간 차감
- 시간 소진에 따른 최종 도전 전환, 성공·패배 판정과 신규 발견 기록의 영구 확정
- 런 이벤트 풀과 Node별 잠재 후보 목록 구성, 출현 보장 시점
- Node의 첫 방문·재방문 여부와 새 조건 후보 판정
- 단일 최종 목표 설정과 안내, 제한 전 자율 도전 및 시간 소진 후 도전 진입 처리
- 신별 축복 효과·티어와 축복 조건 사용 기록의 처리
- 실제 전투의 적 구성, 전장, 난이도와 보상
- Area 내부 이동, Entrance 전환과 시설 이용 UI
- 런 종료 화면과 통계 처리

### Unity 런타임

Unity는 다음 작업을 담당한다.

- 대도시 Node를 시작 Location으로 설정
- 왕의 길잡이를 획득할 단일 최종 목표 Location 설정과 정보 안내
- 제한 전 자율 도전이 가능하도록 목표 접근 경로를 검토하고, 시간 소진 후 최종 도전 진입을 보장
- 이번 런에 포함할 Arc와 Standalone Event 선택
- 런 이벤트 풀과 Node별 잠재 후보 참조 목록 구성
- 정규 이벤트의 런 전체 소비 상태 관리
- Opening Event 하나 선택
- Area 내부의 Edge 이동, `weight`에 따른 이동 시간 차감과 Entrance 전환
- Node별 방문 여부와 과거 유효 후보 전체 기록
- 새로운 탐험 계기 판정
- 실제로 진입한 Node의 잠재 후보 목록에서 현재 State를 기준으로 이벤트와 선택지 사용 가능 여부 판정
- 후보 이벤트 중 실제 발생 이벤트 선택
- 목표 표시, 이번 런의 발견과 기존 영구 발견 기록의 구분
- 전투 결과에 연결된 전투 데이터 호출
- 이벤트 결과 적용
- 관련 이벤트와 결과 처리 완료 후 축복 조건 판정 단계로 연결
- 축복 시스템을 통한 신별 축복·티어와 조건 사용 기록 관리
- Arc와 RunPhase 관리
- 이번 런의 특별 장소 발견과 영구 기록·해금 상태의 구분
- 길잡이 획득 성공·전투 패배에 따른 종료와 시간 소진 후 최종 도전 전환
- 종료 사유와 별개로 신규 발견 기록·발견 원정대·영구 해금의 확정 여부 관리
- 실제 사건과 선택 결과의 연대기 기록

### 노드 진입 이벤트와 시설 이용

Node의 실제 진입에는 같은 서사 이벤트 규칙을 적용한다. 서사 이벤트는 일러스트, 본문, 선택지 또는 자동 결과, 결과 문구와 Result Effect로 구성한다. 각 노드가 항상 이벤트를 제공해야 하는 것은 아니다.

상점, 주점 등의 시설 이용은 별도의 시스템 UI가 담당한다. 노드 진입 이벤트가 없거나 이미 처리되었더라도 시설 이용은 가능하며, 시설 이용 자체를 정규 이벤트의 발생이나 덱 소비로 취급하지 않는다. 장비 구매·판매와 재고 규칙은 아래 확정 내용을 따르고, 나머지 시설의 비용·반복 이용 규칙은 별도 기획을 따른다. Entrance에도 사건을 배치하거나 원정 목표 역할을 지정할 수 있다. 목적지 Entrance의 진입 처리와 Area 전환 사이에는 별도의 시설 이용 UI를 끼워 넣지 않으며, 시설은 입구 옆이나 내부의 별도 Node에 배치하는 것을 권장한다.

### 장비 거래·강화와 이벤트의 경계

- 장비는 상점에서 골드로 구매하며 보유 장비를 판매해 골드를 얻을 수 있다. 판매 재고는 유한하고 구매 수량만큼 감소하며, 같은 원정 동안 보충하거나 재방문으로 복구하지 않는다. 가격·초기 재고·생성 시점·되사기·판매품의 재고 편입·특수 장비 판매 여부는 미정이다.
- 용병당 부위 구분 없이 최대 3개를 장착하고 같은 종류·동일 장비의 중복도 허용한다. 미장착 장비는 수량 제한 없는 파티 공용 인벤토리에 보관한다. 전투 밖에서는 장소 제한 없이 장착·해제·파티원 간 교환이 가능하며 전투 중에는 변경하지 않는다. 장비 교체로 직업의 기본 공격 방식과 무기 표현을 바꾸지 않는다.
- 일반 장비를 강화하면 정해진 특수 장비 하나로 바뀐다. 기존 능력치를 삭제하거나 낮추지 않고 정해진 특수효과를 추가하며, 능력치 상승 자체를 금지하지 않는다. 같은 일반 장비는 같은 결과가 되고 결과 선택 분기나 무작위를 사용하지 않는다.
- 강화 기회는 기본적으로 이벤트에서 제공한다. 플레이어가 장착·보관 중인 강화 가능한 장비 한 개를 직접 선택하며, 동일 장비가 여럿이어도 선택한 한 개만 강화한다. 장비마다 한 번만 강화하고 특수 장비는 추가 강화하지 않는다.
- 특수 장비는 보상으로도 직접 획득할 수 있다. 강화형·보상 획득형 모두 중복 장착과 원정 종료 초기화 규칙을 따르며, 장착·보관 장비는 다음 원정으로 이월하지 않는다.
- 현행 Conditions·Result·Effects에는 장비 보유·대상 선택·지급·강화를 처리하는 계약이 없다. 이 요구를 구현하려면 명시적인 데이터·런타임 계약이 필요하며, 아이템 ID를 임의의 Tag로 대체하거나 개별 Event JSON에 미정 필드를 추가하지 않는다.

일반 5종과 고정 강화형 5종의 이름·효과는 장비 상세 문서에 정의한다. 강화의 공통 비용·조건·빈도와 다른 경로의 전면 금지는 확정하지 않았다. 대상 없음·취소·결과 미리보기 및 장비 처리와 이벤트 완료·소비·기록의 순서는 20절의 후속 계약으로 남긴다. 상점 거래와 자유로운 장비 교체를 매번 서사 이벤트로 만들어 정규 후보·재방문·소비 규칙을 우회하지 않는다.

### 수동 전투 제작

프로토타입에서는 이벤트 생성 후 사람이 각 전투 결과에 맞는 전투를 직접 제작한다.

이벤트 생성기는 전투가 발생한다는 사실만 정의한다. 실제 전투는 안정적인 `Event ID + Choice ID` 조합에 수동으로 연결한다.

## 3. 참조 데이터

이벤트 시스템은 다음 데이터를 참조한다.

```text
Data/Facts.csv
Data/Knowledges.csv
Data/Traits.csv
Data/Locations.csv
Events/Generated/ArcCatalog.json
Events/Generated/GoalCatalog.json
```

- 이벤트가 사용하는 Tag는 Facts, Knowledges, Traits 중 하나에 정의되어야 한다.
- 현행 데이터 계약에서 `CurrentLocation`과 이벤트의 `locations`에는 Locations에 존재하는 ID만 사용할 수 있다.
- 모든 Node는 공간 단위인 Area를 부모로 가진다. Area는 Node가 아니며, 서로 다른 종류의 상위·하위 노드로 나누지 않는다.
- 일반 이동은 같은 Area의 Node 사이에 명시된 Edge와 통행 조건을 따른다. 다른 Area의 Node를 일반 이동 목적지로 선택할 수 없다.
- Edge의 `weight`는 원정 시간 비용이다. 0을 허용하며, 시간 비용이 없는 내부 연결도 `weight = 0`인 Edge로 표현한다.
- Entrance는 지정된 다른 Area의 Node로 전환하는 진입점이다. 전환 자체의 시간 비용은 0이다. 플레이어가 선택한 이동 목적지인지에 따라 전환 여부를 결정하며, 상세 규칙은 11절을 따른다.
- Area·Node·Edge·Entrance 대상의 구체적인 저장 구조와 기존 Locations CSV 및 이벤트 `locations`를 새 구조에 연결하는 방식은 미정이다. 이 문서의 기존 ID와 JSON 예시는 현행 계약이며, 새 구조 지원이 완료되었다는 의미가 아니다.
- 이동 시간은 이벤트 데이터에 작성하지 않는다.

## 4. RunState와 런타임 메타데이터

이벤트 시스템이 사용하는 주요 런 상태는 다음과 같다.

```text
RunState
{
    Fame;
    Reputation;
    Money;
    CurrentLocation;
    Tags;
    RunPhase;
    ArcStates;
    ResolvedEventCount;
    RevealedGoalIds;
}
```

Unity는 이와 별도로 원정 진행을 위해 다음 런타임 메타데이터를 관리한다.

```text
ExplorationRuntimeState
{
    VisitedLocations;
    SeenEligibleEventIdsByLocation;
    RemainingExpeditionTime;
}
```

`ExplorationRuntimeState`는 이벤트 생성기가 직접 변경하는 State가 아니다.

위 필드 이름은 기존 계약의 명칭을 유지한다. Area 기반 구조에서는 현재 Area와 Node를 식별하고, 방문 기록과 후보 이력이 서로 다른 Node를 혼동하지 않아야 한다. 이를 위한 필드 타입, ID 체계, 복합 키와 직렬화 스키마는 아직 확정하지 않는다.

이번 런의 신규 발견, 특별 장소 발견에 따른 기록 보존 조건, 영구 지도·발견 원정대와 해금 상태는 서로 구분하여 원정 시스템이 관리해야 한다. 위 기존 필드만으로 이 상태가 구현되었다고 해석하지 않는다. 발견 판정 시점과 영구 저장 필드·형식은 별도로 정하며 이벤트 생성기가 임의 필드를 추가하지 않는다.

Unity는 런 시작에 구성한 Node별 잠재 후보 참조 목록과 정규 이벤트의 런 전체 소비 상태도 관리한다. 잠재 후보 목록은 장소상 발생할 수 있는 이벤트를 연결한 조회용 목록이며, 현재 조건을 만족하는 후보나 과거 방문 후보 이력과는 다르다. 여러 Node가 같은 Event ID를 참조해도 소비 상태는 런 전체에서 하나를 공유한다. 목록과 소비 상태의 구체적인 저장 필드·형식은 별도로 정한다.

장착·공용 보관 장비의 실제 개체와 강화 가능 여부, 상점의 남은 재고도 원정 상태로 관리해야 한다. 같은 정의를 쓰는 장비가 여럿이어도 선택한 한 개의 변화를 구분해야 하며, 이 상태를 boolean Tag나 이벤트 소비 이력으로 대신하지 않는다. 상태 소유권과 저장 필드·형식은 [GameState.md](GameState.md)의 후속 계약으로 두며 위 RunState 예시가 이미 이 기능을 지원한다고 해석하지 않는다.

축복 시스템은 이와 별도로 신별 축복·티어와 원정 단위 조건 사용 기록을 관리한다. 조건에 쓰이는 Tag와 그 조건의 사용 여부는 서로 다른 정보다. 저장 필드와 데이터 형식은 아직 정하지 않으며, 개별 Event JSON에 축복 지급이나 조건 사용 기록 필드를 임의로 추가하지 않는다. 상세 규칙은 [BlessingSystem.md](BlessingSystem.md)를 따른다.

### Fame

```text
int
0 ~ 10
```

모험가 파티가 세상에 얼마나 알려져 있는지를 나타낸다. Effect 적용 후 값은 `0 ~ 10`의 상하한에서 제한한다.

### Reputation

```text
int
-3 ~ 3
```

모험가 파티의 전반적인 사회적 평판을 나타낸다. Effect 적용 후 값은 `-3 ~ 3`의 상하한에서 제한한다. 세력별 평판과 NPC별 호감도는 사용하지 않는다.

### Money

```text
int
0 이상
```

모험가 파티가 보유한 골드다. Tags와 분리된 독립 State다.

확정된 사용처는 주점의 모험가 영입과 상점의 장비 구매다. 보유 장비 판매로 골드를 얻을 수 있다. 상점 거래의 가격·재고 처리 계약과 이벤트의 `moneyChange`는 구분하며, 장비 구매를 골드 차감 Effect만으로 완료한 것으로 취급하지 않는다.

### CurrentLocation

```text
int
```

현행 계약에서 현재 모험가 파티가 위치한 Location ID다. 위 `int` 표기는 기존 데이터 형식이며 Area와 Node 위치 표현의 확정안이 아니다.

### Tags

```text
string[]
```

파티 단위의 서사적 State다.

- Fact: 과거에 어떤 일이 있었는가
- Knowledge: 파티가 무엇을 알고 있는가
- Trait: 경험을 통해 파티가 어떤 성향을 얻었는가

세 분류는 런타임에서 모두 boolean Tag로 취급한다.

### ResolvedEventCount

```text
int
0 이상
```

전투 승리를 포함해 결과 처리가 끝난 이벤트 수다.

전투 패배로 게임오버가 된 이벤트는 결과가 완료되지 않았으므로 증가시키지 않는다.

### RevealedGoalIds

```text
string[]
```

현행 계약에서 플레이어에게 공개된 Goal ID 목록이다. 목표 위치 안내와 실제 발견·영구 기록은 별개이며, 이 목록에 포함됐다는 이유로 장소를 발견한 것으로 처리하지 않는다.

- 최종 목표 장소는 하나다. 이 기존 목록과 단일 목표 지정·정보 안내의 연결 및 마이그레이션은 별도로 정한다.
- 기존 `revealGoalIds`를 사용하더라도 여러 최종 목표를 추가하거나 보물 획득을 대신하지 않는다.
- 이미 공개된 Goal을 다시 공개하는 것은 상태 변화가 없는 no-op으로 처리할 수 있다.

### VisitedLocations

해당 런에서 한 번 이상 실제로 진입한 Node를 구분하여 기록한다.

이 값은 첫 방문 판정에 사용하며 이벤트 조건으로 직접 노출하지 않는다.

### SeenEligibleEventIdsByLocation

각 Node에서 이전 탐험 기회에 이미 발생 가능 후보로 확인된 정규 이벤트 ID 전체를 기록한다. 실제로 선택한 이벤트만 기록하는 것이 아니다.

런 시작에 잠재 후보를 Node에 연결한 사실이나 다른 장소에서 State가 바뀐 사실만으로 이 이력에 기록하지 않는다. 실제 Node 진입에서 조건과 소비 상태를 검사하여 유효했던 후보를 기존 탐험 기회 규칙에 따라 기록한다.

이 메타데이터는 같은 State 변화 하나를 이용해 해당 장소를 반복 왕복하며 새 이벤트를 하나씩 소진하는 것을 막기 위해 사용한다.

같은 Area와 서로 다른 Area에 속한 Node 사이에서 방문·후보 이력이 충돌하지 않아야 한다. Area 자체를 방문 대상 Node로 기록하지 않는다. 구체적인 식별자와 저장 방식은 미정이다.

## 5. RunPhase

기존 단계 이름은 `Opening`, `Normal`, `Ended`다.

- `Opening`: 시작 Location의 필수 Opening Event 처리
- `Normal`: 자유 탐험, 전투·성장과 스토리라인 진행
- `Ended`: 길잡이 획득 성공 또는 전투 패배 등 종료 결과 확정

**최종 도전 진행은 일반 탐험 및 종료와 구분해야 한다.** 이를 `FinalChallenge` 단계로 표현하는 안을 제안하지만 enum 이름·저장 필드와 진입 문맥은 구현 계약에서 확정한다. 최종 도전 진입 자체는 성공이나 종료가 아니며, 남은 시간이 0이라는 이유로 도전 도중 다시 전환하거나 끊지 않는다.

목표 정보 공개·일반 장소 발견만으로 최종 도전이나 종료 단계에 진입하지 않는다. 하나의 원정에서 중복된 최종 도전 진입 처리가 실행되지 않도록 관리한다. 최종 도전 후 탐험 복귀 허용 여부와 실패 후 처리는 미정이다. `FinaleReady`와 Main Arc Finale를 새로 도입하는 결정은 아니다.

## 6. ArcState

```text
ArcState
{
    Stage;
    Status;
}
```

### Status

```text
Pending
Active
Completed
```

- `Pending`: 이번 런에 포함됐지만 아직 도입 이벤트를 경험하지 않은 Arc
- `Active`: 현재 진행 중인 Arc
- `Completed`: 유리하거나 불리한 것과 관계없이 하나의 결말에 도달한 Arc

`Completed`는 성공만 의미하지 않는다. 목표 실패, 불리한 결말, 거절로 사건군이 끝난 경우도 모두 `Completed`다. 구체적인 결말은 Tags와 State로 구분한다.

Arc는 `Pending`으로 시작하며, Introduction Event의 정상 완료 가능한 모든 Result는 해당 Arc를 `Active` 또는 `Completed`로 전환해야 한다. 전투 패배로 Result 처리가 중단되면 이 전이는 적용하지 않는다.

`Completed`는 종결 상태이며 다시 활성화하지 않는다.

원정이 종료될 때 `Pending`이나 `Active`인 Arc를 `Abandoned` 또는 `Completed`로 강제 변경하지 않는다. 당시 상태 그대로 연대기에 기록한다.

Stage는 Arc의 정적 진행 단계 이름이다. Event ID를 의미하지 않는다.

## 7. 런의 이벤트 단위

한 런은 다음 콘텐츠로 구성한다.

```text
한 런
├─ Opening Event: 정확히 1개
├─ Arc: 0개 이상
├─ 일반 Standalone Event: 0개 이상
└─ 단일 최종 목표의 도전 콘텐츠와 일반 장소 발견 콘텐츠
```

스토리라인 수는 전체 콘텐츠 목표이며 런에 선택되는 Arc 수와 자동으로 동일하지 않다. 최종 도전은 일반 후보 추첨·재방문 이력과 별도의 특수 콘텐츠로 연결한다. 아래 Goal 명칭은 별도 Node 타입을 뜻하지 않는다.

### Opening Event

Opening Event는 Arc와 분리된 특수 이벤트다.

- `arcId`와 `arcStage`는 `null`이다.
- `goalId`는 `null`이다.
- `eventType`은 `Opening`이다.
- 모든 런에 정확히 하나 포함한다.
- 런 시작 시 시작 Location에 최초로 진입할 때 다른 후보와 경쟁하지 않고 반드시 한 번 발생한다. 이후 재방문으로 Opening을 다시 실행하지 않는다.
- Arc State를 시작하거나 변경하지 않는다.
- 결과 처리 완료 후 Unity가 `RunPhase`를 `Normal`로 전환하고 현재 Area의 노드 화면, 목표 하나의 위치·기본 정보와 남은 원정 시간을 공개한다.
- Opening과 시작 Location 내부 사건에는 원정 시간을 차감하지 않는다.

시작 Node에는 기본적으로 Opening만 발생하도록 이벤트의 배치와 조건을 구성한다. 다른 이벤트를 배치한다면 특별한 State, Tags 또는 Arc 변화가 계기가 되어 새 조건이 열리도록 작성한다. 시작 Node라는 이유로 정규 이벤트를 런타임에서 일괄 차단하지 않으며, 특별한 계기 이후 실제 재진입에는 일반 `NewCondition` 규칙을 적용한다.

### Arc

Arc는 시작, 진행과 결말을 가진 선택적 퀘스트 라인이다.

- 한 런에 0개 이상 포함할 수 있다.
- Main/Sub 구분을 사용하지 않는다.
- 여러 이벤트로 구성되지만 고정된 단일 체인일 필요는 없다.
- 현재 Stage와 State에 따라 일부 중간 이벤트를 건너뛸 수 있다.
- 결말의 좋고 나쁨과 관계없이 종결되면 `Completed`다.
- Arc 완료는 원정 성공이나 종료 조건이 아니다.
- Goal 공개에 관여할 수 있지만 모든 Arc를 Goal에 종속시키지 않는다.

### Standalone Event

일반 Standalone Event는 어떤 Arc에도 속하지 않는 독립 사건이다.

- `arcId`와 `arcStage`는 `null`이다.
- Tags, Fame, Reputation과 Money를 변경할 수 있다.
- Goal을 공개할 수 있다.
- 다른 Arc의 Stage나 Status를 직접 변경하지 않는다.

### Goal Event와 최종 도전

현행 `Goal` Event는 `eventType = Goal`, 하나의 `goalId`, `arcId = null`, `arcStage = null`을 사용하며 정규 이벤트 풀과 잠재 후보 목록에 포함하지 않는다.

단일 목표노드에 도전하기 위해 진입했을 때 최종 콘텐츠를 처리한다. 일반 후보 추첨·기존 방문 이력·정규 이벤트 고갈 때문에 최종 도전이 누락되지 않도록 한다. 시간 소진 후에는 15절에 따라 같은 최종 도전으로 전환한다. 강제 이동과 목표 이벤트 발생 중 방식, 구체 진입 UI·이동 비용은 미정이다.

Goal 콘텐츠는 마지막 난관과 길잡이 획득을 연결해야 한다. 단순 Goal Result 정상 완료나 전투 승리를 획득과 자동으로 동일시하지 않으며, 실제 획득을 확인하는 데이터 계약은 별도 설계한다. 최종 도전이 시작된 진입에서는 정규 이벤트를 추가 추첨하지 않는다. 진입 조건과 가능한 결과를 콘텐츠 구성·정적 검토로 점검하며 런타임에서 조건을 무시하거나 대체 결과를 생성하지 않는다.

일반 특별 장소의 발견은 최종 목표 도전과 구분한다. 특별 장소 발견만으로 성공하거나 도전이 끝나지 않으며, 장소 발견의 구체 트리거·이벤트 연결은 미정이다.

## 8. Arc Catalog

`Events/Generated/ArcCatalog.json`은 제작된 Arc의 정적 정보를 보관한다.

```json
{
  "arcs": [
    {
      "id": "refugee_caravan",
      "initialStage": "Introduction"
    }
  ]
}
```

- `id`는 모든 Arc에서 고유해야 한다.
- `initialStage`는 해당 Arc의 초기 Stage다.
- Catalog는 다음 또는 이전 Event ID를 지정하지 않는다.
- Finale Stage와 Finale Location은 사용하지 않는다.

---

## 9. Goal Catalog

`Events/Generated/GoalCatalog.json`은 목표의 Location과 Event 연결을 보관하는 현행 계약이다. 현재 콘텐츠의 최종 목표는 왕의 길잡이를 획득할 장소 하나다. 과거의 여러 특별 장소 중 목표를 바꿔 지정하는 규칙은 사용하지 않는다.

아래는 기존 필드 형식의 예시이며 실제 지명·위치 ID를 확정하지 않는다. Area·Node 참조와 획득 확인·최종 도전 상태의 데이터 계약은 별도 설계한다.

```json
{
  "goals": [
    {
      "id": "kings_guide",
      "locationId": 120,
      "eventId": "goal_kings_guide"
    }
  ]
}
```

- Goal ID는 고유하고 Location은 실제 참조 데이터에 존재해야 한다.
- 하나의 Node에 Goal을 하나만 연결하며 `eventId`는 해당 Goal Event를 가리킨다.
- 별도 Goal Node 타입을 만들지 않는다. Entrance에 목표 역할을 부여하는 것도 가능하며 11절의 종료·전환 순서를 따른다.
- 최종 목표의 위치·기본 정보를 안내하되 현재 Area 밖의 Node를 지도에 표시하거나 직접 이동 대상으로 선택하지 않는다. 구체 안내 UI와 실제 접근 방식은 미정이다.
- 제한 전에는 언제든 최종 도전을 선택할 수 있어야 한다. 초기 위치·경로 및 목표 접근 조건을 검토하며 스토리라인 완주를 새 필수 조건으로 넣지 않는다.
- 목표까지 전체 경로를 공개하는 것은 기존 원칙대로 전제하지 않는다. 다른 Area 목표 안내는 현재 Area의 이웃·연결 표시와 구분한다.
- `RevealedGoalIds`와 `revealGoalIds`는 현행 필드이며, 사용 사실이 복수 최종 목표 허용이나 획득 완료를 뜻하지 않는다. 목표 정보와 일반 장소 단서 공개의 구체 분리는 데이터 계약에서 정한다.
- 특별 장소의 발견·영구 효과는 최종 Goal과 별개다. 모든 특별 장소를 해금해도 다른 Location으로 최종 목표를 교체하지 않는다.

## 10. 런 시작

Unity는 런을 시작할 때 다음 작업을 수행한다.

1. 대도시 Node를 시작 Location으로 설정한다. 이 Node가 속한 Area 구조는 유지한다.
2. 단일 최종 목표와 정보를 설정하고 제한 전 자율 도전의 접근 및 시간 소진 후 최종 도전 연결을 검토한다. 구체 안내·전환 계약은 별도로 정한다.
3. 이번 런에 포함할 Arc와 일반 Standalone Event를 선택한다.
4. Opening Event 하나를 선택한다.
5. 선택된 정규 이벤트로 런 이벤트 풀을 구성하고 각 이벤트의 런 전체 소비 상태를 미소비로 초기화한다.
6. 장소상 발생 가능한 각 Node에 정규 이벤트의 참조를 연결해 잠재 후보 목록을 만든다. 초기 State·Arc 조건으로 제외하지 않는다. Opening과 최종 Goal 콘텐츠는 이 정규 목록에 포함하지 않는다.
7. `RunPhase`를 `Opening`으로 설정한다.
8. 선택된 Arc를 `Pending`과 초기 Stage로 설정한다.
9. `ResolvedEventCount`를 0으로 설정한다.
10. Node별 방문·과거 유효 후보 이력과 이번 런의 신규 발견 상태를 초기화한다. 기존 영구 발견·해금은 유지하며, 잠재 후보 목록을 방문 이력에 복사하지 않는다. 최종 도전은 아직 시작하지 않은 상태로 둔다.
11. 신별 축복·티어와 축복 조건 사용 기록을 이번 원정의 초기 상태로 설정한다.
12. 시작 Node에 최초 진입한 것으로 방문 기록에 남긴다.
13. 시작 Location에서 Opening Event를 발생시킨다.

현행 데이터 계약에서 시작 Location은 Locations에 존재해야 한다. Area 기반 구조의 시작 위치 표현은 노드 데이터 설계에서 별도로 확정한다.

대도시에서 출발해 이미 밝혀진 구간을 이동하는 방식은 미정이다. 구체적인 이동 처리와 별개로 시작 Node의 Opening 역할과 처리 순서는 유지한다.

Opening Event가 정상적으로 끝나면 `RunPhase`를 `Normal`로 전환하고 현재 Area의 노드 화면, 목표 하나의 위치·기본 정보와 남은 원정 시간을 공개한다. 전체 경로는 공개하지 않으며 현재 Node에서 바로 이동할 수 있는 이웃과 연결을 표시한다.

Opening Event에서 전투 패배가 발생하면 즉시 게임오버로 종료할 수 있다.

시작 Location의 Opening은 해당 장소의 첫 방문 콘텐츠 역할을 하므로, Opening 직후 같은 Location에서 추가 정규 첫 방문 이벤트를 실행하지 않는다. 최초 진입 시에는 유효한 정규 후보가 없도록 데이터를 구성하므로 시작 Node의 초기 정규 후보 이력은 비어 있다. 이때 잠재 후보 목록에는 특별한 계기 이후 조건을 충족할 이벤트가 포함될 수 있다. Opening Result로 새롭게 열린 정규 후보를 실제 재진입 전에 이미 확인한 과거 후보로 기록하지 않는다. 특별한 계기로 다른 이벤트 조건이 열린 경우에는 이후 실제 재진입에서 일반 후보·이력 규칙으로 판정한다. 단순 왕복만으로 다른 이벤트가 발생하지 않도록 하는 책임은 시작 Node의 이벤트 배치와 조건 구성에 있다.

## 11. Area 내부 이동과 Entrance 전환

모든 Node는 공간 단위인 Area를 부모로 가진다. Area 자체는 Node가 아니다. 같은 Area 내부에서는 명시된 Edge와 통행 조건에 따라 이동하며, 다른 Area의 Node를 일반 이동 목적지로 선택할 수 없다.

이 절은 기존 Node·Edge·Entrance 이동의 처리 규칙이다. 대도시를 중심으로 이미 밝혀진 구간을 어떤 방식으로 이동할지는 별도로 결정한다.

노드 화면에는 현재 Area에 속한 Node만 표시한다. Entrance를 통해 다른 Area로 전환하면 새 Area의 Node를 표시한다. 현재 Node에서 바로 이동할 수 있는 이웃과 연결은 표시하되 목표까지의 전체 경로는 숨긴다. 다른 Area의 목표 위치도 안내하지만, 이 안내가 다른 Area의 Node를 직접 이동 대상으로 표시한다는 뜻은 아니다. 구체적인 안내 UI는 별도 결정 사항이다.

이벤트 시스템은 시간 수치 자체를 변경하지 않으며, Unity의 이동 시스템이 Edge 이동과 시간 차감, Entrance 전환을 담당한다. 각 Edge의 `weight`를 원정 시간 비용으로 사용한다. `weight`는 0을 허용하므로 시간 비용이 없는 내부 연결도 같은 Edge 구조로 표현한다. Entrance 전환 자체의 시간 비용은 0이며, 전환 시 별도의 시간을 추가로 차감하지 않는다.

### 선택한 목적지와 경유 Entrance

- 플레이어가 Entrance를 이동 목적지로 선택하여 그 Node에 도착하면 입구의 진입 이벤트와 결과를 먼저 처리한다. 종료되지 않았고 최종 도전 진행 중도 아니라면 추가 입력 없이 지정된 다른 Area의 Node로 한 번 전환한다.
- 전환해서 도착한 Node도 Entrance이더라도 자동으로 다시 전환하지 않는다.
- 다른 목적지로 가는 경로에서 Entrance를 경유하면 Area 전환만 생략한다. 실제 Node 진입에 따른 방문 기록, 후보 판정과 서사 이벤트 판정은 유지한다.
- 경유 Node의 사건으로 이동이 일시 정지해도 그 Node가 플레이어가 선택한 이동 목적지로 바뀌지는 않는다.
- 화면이나 UI를 열고 닫는 것만으로 실제 Node 진입 또는 Entrance 목적지 도착을 대신하지 않는다.

이미 서 있는 Entrance를 다시 선택하는 조작과 복귀 방식은 미정이다. Entrance의 정상적인 진입 이벤트 완료 뒤에는 예정된 전환을 계속하므로, 돌아가거나 전환을 취소하는 선택지는 현재 지원하지 않는다. 이런 분기가 필요해지면 별도의 취소 규칙을 정한다.

### Edge 이동의 도착 처리

일반 Node와 경유 Entrance의 흐름은 다음과 같다.

```text
Edge 이동 및 weight만큼 시간 차감
→ 실제 Node 진입과 첫 방문·재방문 구분, 방문 기록
→ 해당 방문의 이벤트·전투·보상·결과 처리
→ 종료가 확정되지 않았고 일반 탐험 중이면 시간 소진 판정
→ 소진 시 최종 도전으로 전환 / 시간이 남으면 탐험 계속
```

- 노드 내부 이벤트·전투·조사·대화·거래·휴식·회복은 원정 시간을 소비하지 않는다.
- 같은 Edge 재이동이나 역행도 해당 weight를 다시 적용한다.
- 이벤트 Effect는 위치나 원정 시간을 직접 바꾸지 않는다. 시간 소진의 강제 전환은 원정 시스템의 책임이다.

### 목적지 Entrance의 도착과 전환

1. Edge weight를 차감하고 Entrance에 실제 진입하여 기존 이력에 따라 방문을 기록한다.
2. 입구의 방문 콘텐츠를 처리한다. 최종 도전 진입 대상이라면 특수 콘텐츠를, 그 외에는 일반 후보 규칙에 따라 정규 이벤트를 최대 1개 처리한다.
3. 길잡이 획득 성공이나 전투 패배로 종료가 확정되면 남은 전환을 중단한다. 최종 도전이 진행 중이라면 그 처리 중에 일반 이동으로 복귀시키지 않는다. 일반 입구 처리가 끝났고 탐험이 계속되면 전환을 진행한다.
4. 추가 시간 차감 없이 지정된 다른 Area의 Node로 한 번 전환한다. 현재 Area·Node를 함께 변경하고 새 Area를 표시한다.
5. 도착 Node의 방문을 기록하고 입구에서 변경된 State·Tags·Arc와 런 공통 소비를 반영해 도착 콘텐츠를 처리한다. 최종 도전 진입이면 특수 규칙을, 정규 판정이면 이 Node 자신의 잠재 후보·이력을 사용한다.
6. 도착지가 Entrance여도 자동으로 재전환하지 않는다. 성공·전투 패배가 확정되면 그 결과로 끝낸다.
7. 아직 일반 탐험 중이고 종료되지 않았다면 도착지의 이벤트·전투·보상·결과까지 마친 뒤 시간을 판정한다. 소진됐으면 최종 도전으로 전환하고 시간이 남으면 새 Area에서 다음 행동을 고른다.

입구와 도착지는 별도 Node이므로 방문·후보 이력을 각각 관리하며 정규 이벤트가 각각 최대 1개 발생할 수 있다. 같은 Node 진입에서 Result로 열린 정규 이벤트를 즉시 추가 실행하지 않는 규칙은 유지한다. 일반 특별 장소 발견만으로 전환을 중단하지 않는다.

입구 처리와 자동 전환 사이에 시설 이용·이동 선택 UI를 끼워 넣지 않는다. 시설은 입구 옆이나 내부의 별도 Node 배치를 권장한다. 최종 도전에서 탐험으로 돌아올 수 있는지와 그 경우 Entrance 문맥을 어떻게 처리할지는 별도 결정한다.

### 도착 후 시간 소진과 종료 판정

시간 소진 검사는 현재 Edge의 도착 처리 범위를 모두 마친 뒤 수행한다. 일반 Node·경유 Entrance는 그 Node의 이벤트·전투·보상·결과까지, 목적지 Entrance는 입구 처리·비용 0의 전환 1회·도착지 처리까지 포함한다. 이동으로 시간이 0 이하가 되어도 그 이유만으로 진행 중 사건이나 전투를 중단하지 않는다.

1. 도착 범위의 콘텐츠를 처리한다.
2. 그 과정에서 길잡이 획득 성공·전투 패배가 확정되면 즉시 해당 결과로 종료하고 남은 전환·이벤트를 진행하지 않는다.
3. 종료되지 않았고 일반 탐험이 계속되는 경우에만 전체 도착 처리 완료 후 남은 시간을 확인한다.
4. 소진되었다면 탐험 준비 기간을 끝내고 최종 도전으로 강제 전환한다. 즉시 실패·종료로 기록하지 않는다.
5. 시간이 남아 있으면 다음 탐험 행동을 허용한다.

경유 Node에서 소진되면 그곳의 결과를 마친 뒤 전환하며 원래 목적지까지 남은 경로를 먼저 진행하지 않는다. 목적지 Entrance의 마지막 방문은 전환과 도착 결과까지 최종 도전에 반영한다. 이미 확정된 성공·패배를 시간 소진으로 덮어쓰지 않는다.

최종 도전 전환이 결정된 뒤에는 weight 0인 Edge나 추가 Entrance 이동으로 일반 탐험을 연장하지 않는다. 최종 도전 진행 중에도 시간 0을 다시 검사하여 중복 전환하지 않는다. 강제 전환 방식·이동 비용·복귀·기타 실패 후 처리는 15절의 미정 범위다.

## 12. 탐험 기회와 재방문 규칙

정규 이벤트 발생 여부는 단순히 노드에 도착했다는 이유만으로 매번 다시 추첨하지 않는다. 아래 규칙은 Node의 실제 진입에 공통으로 적용하며, 경유와 Entrance 전환 도착에 따른 진입도 포함한다. 이 절의 현재 유효 후보는 해당 Node의 잠재 후보 목록을 13절의 현재 조건과 런 전체 소비 상태로 검사한 결과를 뜻한다.

정규 이벤트를 판정하는 **새로운 탐험 계기**는 다음 두 종류다.

```text
FirstVisit
NewCondition
```

### FirstVisit

해당 런에서 처음 실제로 진입한 일반 Node다.

- 현재 유효 후보가 있으면 그중 정규 이벤트 1개가 발생한다. 별도의 무이벤트 확률을 두지 않는다.
- 후보가 0개라면 이벤트 없이 방문을 마친다. 이는 정상적인 콘텐츠 구성이다.
- 한 번의 진입에서 정규 이벤트를 연속으로 여러 개 발생시키지 않는다.
- 이벤트가 없어도 해당 노드의 시설은 별도 시스템 UI로 이용할 수 있다.

Opening Location은 Opening Event가 첫 방문 콘텐츠를 담당하며 시작 Node도 방문 기록에 포함한다. 최초 진입의 정규 후보와 재방문 콘텐츠는 7절과 10절의 데이터 구성 원칙을 따른다.

최종 도전에 진입할 때는 Goal 특수 규칙을 적용하며 정규 첫 방문·재방문 이력 때문에 도전이 누락되지 않는다. 일반 특별 장소의 발견 트리거와 이벤트 연결은 별도로 정한다.

### NewCondition

이미 방문한 Node에 실제로 재진입했을 때 State, Tags 또는 Arc 상태·단계 조건에 따라 과거 탐험 기회에서 후보가 아니었던 이벤트가 새로 유효해진 경우다.

예:

```text
신전 첫 방문
→ 열리지 않는 문을 확인

폐광에서 Knowledge 획득
→ 신전의 특정 이벤트 조건 충족

신전 재방문
→ 새롭게 활성화된 이벤트 발생 가능
```

Unity는 노드별 `SeenEligibleEventIdsByLocation`을 이용해 어떤 이벤트가 과거 탐험 기회에서 이미 후보였는지 기록한다.

현재 유효 후보 중 과거에 해당 노드의 탐험 기회에서 후보가 된 적 없는 이벤트가 있을 때 `NewCondition`이 성립한다. State가 바뀌었다는 사실만으로는 탐험 기회가 생기지 않는다.

- 이 탐험 기회에서는 새로 유효해진 후보들 가운데 정규 이벤트 1개가 발생한다. 별도의 무이벤트 확률을 두지 않는다.
- 같은 State 변화로 여러 이벤트가 동시에 열려도 이후 변화 없이 반복 왕복해 나머지를 하나씩 소진할 수 없다.
- 각 탐험 기회에서 확인된 유효 후보 전체를 `SeenEligibleEventIdsByLocation`에 기록한다. 선택된 1개만 기록하지 않는다.
- 이전에 후보였던 이벤트가 조건 불충족을 거쳐 다시 유효해져도 새 후보로 취급하지 않는다.
- 후보 이력을 Result 적용 전후 어느 시점에 갱신할지에 대한 구체적인 처리 계약은 미정이다. 구현 시에는 이 절의 왕복 소진 방지와 이후 실제 재진입 판정 규칙을 함께 만족해야 한다.

### 일반 재방문

이미 방문한 노드에 재진입했지만 새로 유효해진 후보가 없으면 정규 이벤트는 발생하지 않는다. 진입 경로가 달라진 것만으로는 탐험 기회를 부여하지 않는다.

따라서 같은 두 노드를 반복 왕복해서 남아 있는 일반 이벤트만 소진하는 플레이는 지원하지 않는다. 이벤트가 없는 재방문에서도 시설 이용은 별도로 가능하다.

### 이벤트 결과 직후 연속 발생 금지

한 이벤트의 결과로 새로운 Tag나 Arc Stage가 생겨 같은 노드에서 다른 이벤트가 즉시 활성화되더라도 그 자리에서 연속 발생시키지 않는다.

새롭게 활성화된 사건은 이후 해당 노드에 실제로 재진입했을 때 `NewCondition` 규칙으로 판정한다. 노드 화면이나 시설 UI를 열고 닫는 것으로 실제 재진입을 대신할 수 없다.

축복 판정·획득은 정규 이벤트를 추가 추첨하는 절차가 아니라 별도의 후처리 단계다. 이벤트 처리 완료 후의 축복 연결은 20절과 [BlessingSystem.md](BlessingSystem.md)를 따른다.

## 13. 정규 이벤트 후보 판정

Goal Event와 Opening Event를 제외한 정규 이벤트는 실제로 진입한 Node의 잠재 후보 목록에서 판정한다. 방문할 때 런 전체 이벤트를 순회하여 장소를 찾지 않는다.

잠재 후보 목록은 런 시작에 장소상 발생 가능한 정규 이벤트를 미리 연결한 것이다. 목록에 있다는 이유만으로 현재 유효하거나 발생이 보장되는 것은 아니다. 먼저 런 전체에서 이미 소비된 이벤트를 제외하고, 나머지 참조에 현재 State·Tags·Arc 상태 및 아래 조건을 적용하여 유효 후보를 구한다. 이 검사는 이벤트 밖의 시설 이용으로 달라진 Money 등 현재 상태도 반영한다.

아래 `conditions.locations`는 현행 Locations 기반 장소 조건이며, 런 시작에 Node별 잠재 후보를 연결할 때 사용한다. Area 기반 구조에도 장소 조건으로 후보를 미리 분류하는 원칙을 적용하되, Area에 속한 Node를 이 필드에서 참조하는 구체적인 데이터 형식은 아직 정하지 않는다.

Tags·State·Arc 상태가 바뀌어도 원격 Node를 찾아 잠재 후보를 교체하거나 유효 후보를 미리 확정하지 않는다. 다음 실제 진입에서 해당 Node의 목록을 최신 상태로 검사한다. Entrance 입구의 이벤트를 처리한 뒤 도착지에 진입할 때도 입구 Result와 런 전체 소비 상태를 반영하여 도착지 목록을 검사한다.

### Arc Event

Arc 이벤트는 다음을 모두 만족해야 한다.

- 현재 Location이 `conditions.locations`에 포함된다.
- 현재 Arc Stage와 `arcStage`가 일치한다.
- Arc가 종결 상태가 아니다.
- `eventType == Introduction`이면 해당 Arc가 `Pending`이다.
- 그 밖의 Arc 이벤트라면 해당 Arc가 `Active`다.
- 이벤트의 모든 State 조건을 만족한다.
- Choice 이벤트라면 선택 가능한 Choice가 최소 하나 존재한다.
- Battle Result가 가능한 선택지에는 유효한 전투 연결이 존재한다.

### Standalone Event

Standalone Event는 다음을 모두 만족해야 한다.

- 현재 Location이 `conditions.locations`에 포함된다.
- 이벤트의 모든 State 조건을 만족한다.
- Choice 이벤트라면 선택 가능한 Choice가 최소 하나 존재한다.
- Battle Result가 가능한 선택지에는 유효한 전투 연결이 존재한다.

### 후보 선택

- 한 탐험 기회에서 정규 이벤트는 최대 1개 발생한다.
- 첫 방문은 현재 유효 후보 전체, 조건이 새로 열린 재방문은 과거 후보 이력에 없는 새 유효 후보만 선택 대상으로 삼는다.
- 유효한 탐험 기회에 선택 대상이 있으면 그중 1개를 발생시키며 별도의 무이벤트 확률을 두지 않는다.
- 런 시작에는 Node별 잠재 후보 목록을 만들고 실제 발생 이벤트는 방문 시 유효 후보 중에서 선택한다. 기존 단일 Location 모델은 이벤트 가중치나 우선순위 없이 무작위로 1개를 선택하는 기준안을 사용했다. 콘텐츠의 고정·랜덤 배치 기준, 이벤트 간 우선순위와 복수 유효 후보의 최종 선택 알고리즘은 미정이며, 이 미정 사항을 런 시작에 실행 이벤트 하나를 확정한다는 의미로 해석하지 않는다. 이동 시간 비용인 Edge의 `weight`는 이벤트 선택 가중치가 아니다.
- Goal과 Opening은 정규 후보 선택에 참여하지 않는다. 최종 도전은 정규 후보 추첨·방문 이력과 분리하여 처리하고, 일반 장소 발견 콘텐츠의 구체 연결은 별도로 정한다.

## 14. 런 이벤트 풀과 노드별 잠재 후보 목록

Unity는 다음 콘텐츠로 런 전체에서 공유하는 정규 이벤트 풀을 구성한다.

- 선택된 Arc의 모든 Introduction/Normal Event
- 이번 런에 선택된 일반 Standalone Event

다음 이벤트는 일반 이벤트 풀과 Node별 정규 잠재 후보 목록에 포함하지 않는다.

- Opening Event
- Goal Event

### 런 시작의 Node별 분류

- 런 이벤트 풀에 포함된 각 이벤트를 장소 조건상 발생 가능한 모든 Node의 잠재 후보 목록에 연결한다. 같은 이벤트가 여러 장소를 허용하면 각 Node가 동일한 Event ID를 참조한다.
- 이 목록을 만들 때 초기 Tags, Fame, Reputation, Money, 해결 이벤트 수나 Arc 상태·단계에 따라 후보를 제외하지 않는다. 당장은 조건이 맞지 않는 Arc 후속 이벤트도 포함한다.
- Node별로 이벤트 정의나 소비 상태를 복제하지 않으며, 한 Node의 목록에 같은 Event ID를 중복 연결하지 않는다.
- 잠재 후보가 없는 Node도 정상이다. 후보 참조가 있더라도 실제 방문 시 유효 후보가 0개일 수 있다.
- 목록 작성은 이벤트 선택이나 방문으로 취급하지 않는다. `SeenEligibleEventIdsByLocation`에는 잠재 후보 목록을 그대로 기록하지 않는다.
- 잠재 후보의 장소별 연결은 해당 런에서 유지한다. 상태 변화는 실제 진입 시 조건 검사로 반영하며 목록의 이벤트 교체로 표현하지 않는다.

### 런 전체의 소비 상태

기존의 이벤트 덱은 이 풀에서 아직 소비하지 않은 정규 이벤트의 논리적 집합을 뜻한다. 덱에서 제거한다는 것은 해당 이벤트를 런 전체에서 소비 처리하여 이후 모든 Node의 유효 후보에서 제외한다는 의미다. 각 Node의 잠재 후보 참조를 물리적으로 삭제하는 방식이나 구체적인 컨테이너를 요구하지 않는다.

소비와 후보 판정은 다음 규칙을 따른다.

- 실제로 정상 처리된 정규 이벤트는 결과 처리 완료 후 런 전체에서 소비 처리한다.
- 전투 패배로 게임오버가 된 이벤트는 이후 진행이 없으므로 제거 여부가 결과에 영향을 주지 않는다.
- 조건을 충족하지 못한 이벤트는 소비하지 않고 잠재 후보 참조도 유지한다. 이후 실제 방문에서 조건을 다시 검사할 수 있다.
- 여러 Location을 가진 이벤트도 한 곳에서 정상 처리되면 다른 모든 Node에서 소비된 이벤트로 판정한다.
- 한 런에서 같은 정규 이벤트를 반복하지 않는다.
- `Completed` Arc의 남은 이벤트는 후보에서 제외한다.
- 반복 방지만을 위한 Tag를 만들지 않는다.

유효 후보였지만 선택되지 않은 이벤트는 런 전체에서 소비된 것이 아니다. 그 Node에서는 기존 후보 이력 때문에 단순 왕복으로 다시 선택할 수 없지만, 다른 Node에서는 그곳의 방문·후보 이력과 현재 조건에 따라 후보가 될 수 있다.

**일반 이벤트 덱 고갈은 원정 종료 조건이 아니다.**

사건이 남지 않아도 플레이어는 Area 내부와 Entrance를 통해 탐험하고 시설을 이용하거나 Goal을 향할 수 있다. 별도의 이동·종료·시설 이용 규칙은 계속 적용한다.

첫 방문 노드의 후보가 0개인 것도 정상이다. 첫 방문 보장을 위한 조건 없는 Standalone 후보를 필수로 배치하지 않는다.

## 15. 최종 도전, 원정 종료와 발견 기록

### 자율 도전과 시간 소진

최종 목표 장소는 하나이며, 제한 전에는 언제든 그 Node로 이동하여 최종 도전에 나설 수 있다. 조기 도전은 플레이어가 정하는 챌린지이고 별도 보상·점수·이득을 주지 않는다.

시간제한은 탐험·성장에 주어진 준비 기간이다. 11절의 도착 처리 범위를 모두 마친 뒤 시간이 소진되었다면 최종 도전으로 강제 전환한다. 목표노드로 강제 이동할지, 목표 이벤트를 발생시킬지는 아직 정하지 않았다. UI·연출·이동 비용, 최종 도전 진입 후 탐험 복귀와 기타 실패 후 처리도 미정이다. 강제 전환으로 기존 Area 일반 이동 규칙을 무조건 확대하지 않는다.

이 전환은 같은 원정의 진행이며 용병·성장·장비·상점 재고·축복·Tags를 초기화하지 않는다. 마지막 방문의 전투·보상·결과까지 반영한 상태로 도전한다. 흰밀물의 귀환 현상과 이 전환을 어떻게 연결할지는 별도 설정이며 흰밀물을 적이나 모든 신비의 원인으로 바꾸지 않는다.

### 길잡이 획득 성공

최종 사건이나 전투의 난관을 넘어 왕의 길잡이를 실제로 손에 넣으면 `GoalSuccess`를 확정하고 `RunPhase = Ended`로 전환한다. 단순 도착·목격·전투 승리 또는 Goal Result의 정상 완료만을 획득으로 간주하지 않는다. 실제 획득 사실을 확인하는 데이터와 처리 계약은 별도 설계한다.

결말의 중심 감정은 ‘마침내 찾았다’다. 획득 후 도시 귀환·납품·포상은 필수 플레이가 아니며, 즉위·통치·정치적 결과나 보물을 넘길지 왕위를 주장할지 고르는 엔딩 분기는 현재 범위에 추가하지 않는다. 화면·문구·효과는 미정이다.

### 전투 패배

어떤 이벤트에서든 전투에 패배하면 후속 Result Effect를 적용하지 않고 `BattleDefeat`와 `RunPhase = Ended`를 확정한다. 실제 이벤트·선택·패배 사실은 기록할 수 있지만 적용되지 않은 효과를 기록하지 않는다. 최종 도전의 별도 실패·복귀 규칙이 정해지기 전까지 기존 전투 패배 규칙을 임의로 예외 처리하지 않는다.

### 특별 장소와 영구 기록

유한한 특별 장소의 발견, 영구 지도·발견 원정대 기록과 영구 효과 해금이라는 기존 개념은 유지한다. 일반 장소·특별 장소 발견은 최종 보물 획득과 다르며, 발견만으로 이번 모험을 성공 처리하지 않는다. 기록이 확정된 특별 장소의 영구 효과는 다음 원정부터 적용하는 기존 방향을 유지한다.

이전의 ‘특별 장소 발견 후 자발적 종료 또는 흰밀물 종료 시 기록 확정’은 새 최종 도전 구조에 그대로 적용하지 않는다. 길잡이 획득·전투 패배·기타 실패에 따른 신규 발견 보존·무효화 기준과 확정 시점, 중도 포기 허용 여부는 미정이다. 시간 소진 전환만으로 기록을 확정하거나 삭제하지 않는다. 기존 영구 기록·해금을 세계 초기화로 지우지 않는다.

목표 정보, 실제 방문·후보 이력, 이번 런 발견과 영구 기록은 각각 관리한다. 특정 이벤트 타입이나 Tag 하나를 영구 기록 확정으로 간주하지 않는다. 모든 특별 장소 해금 이후에도 단일 최종 목표는 유지하며 새로운 영구 강화 콘텐츠를 자동 추가하지 않는다.

### 종료 사유와 전환의 구분

현재 종료 결과는 길잡이 획득의 `GoalSuccess`와 기존 `BattleDefeat`다. `TimeExpired`는 새 원정의 종료 결과로 사용하지 않는다. 이전 저장값·코드의 이행과 최종 도전 상태 표현은 별도 계약이다. 최종 도전의 기타 실패 결과·중도 포기·특수 사건 종료는 미정이다. 정규 이벤트 고갈이나 시간 소진만으로 종료 결과를 만들지 않는다.

장착 장비와 공용 인벤토리의 보관 장비는 실제 원정 종료 시 초기화하며 다음 원정으로 이월하지 않는다. 필요한 종료 기록은 값으로 보존하고, 전투 등 진행 중 처리가 참조하는 원정 데이터를 먼저 폐기하지 않는다. 구체 저장·정리 순서는 GameState의 수명 계약에서 정하며 시간 소진에 따른 최종 도전 진입을 종료 초기화로 처리하지 않는다.

## 17. Event 기본 필드

### id

모든 이벤트에서 고유하고 변경되지 않는 문자열 ID다.

### arcId

- Arc 이벤트는 Catalog에 존재하는 `arcId`를 사용한다.
- Opening, Standalone, Goal Event는 `null`이다.
- Main/Sub 타입 구분은 사용하지 않는다.

### goalId

- Goal Event만 유효한 Goal ID를 가진다.
- Opening, Arc, Standalone Event는 `null`이다.

### eventType

```text
Opening
Introduction
Normal
Goal
```

- `Opening`: 시작 Location의 특수 이벤트
- `Introduction`: Pending Arc의 도입 이벤트
- `Normal`: Active Arc 진행 이벤트 또는 일반 Standalone Event
- `Goal`: 단일 최종 목표의 도전 콘텐츠를 연결하는 특수 이벤트. 별도 Node 타입이 아니며, 정상 완료만으로 실제 보물 획득을 대신하지 않는다.

`Finale`은 사용하지 않는다.

### arcStage

Arc 이벤트가 요구하는 현재 Stage다.

같은 Stage에 여러 이벤트가 존재할 수 있으며 Stage는 다음 Event ID를 뜻하지 않는다.

Opening, Standalone, Goal Event는 `null`이다.

## 18. Conditions

모든 조건은 AND 관계다. `null` 또는 빈 배열은 해당 조건을 검사하지 않는다는 뜻이다.

아래 필드와 Location ID는 현행 이벤트 JSON 계약이다. Area에 속한 Node의 참조 스키마와 진입 방향을 이벤트 조건에 포함할지는 미정이며, 현재 스키마에 임의 필드를 추가하지 않는다.

### 이벤트 조건

```text
requiredTags
forbiddenTags
fameMin / fameMax
reputationMin / reputationMax
moneyMin / moneyMax
resolvedEventCountMin / resolvedEventCountMax
locations
```

- `requiredTags`: 모두 현재 Tags에 존재해야 한다.
- `forbiddenTags`: 하나라도 현재 Tags에 존재하면 안 된다.
- `fameMin / fameMax`: Fame 범위
- `reputationMin / reputationMax`: Reputation 범위
- `moneyMin / moneyMax`: Money 범위
- `resolvedEventCountMin / resolvedEventCountMax`: 해결한 이벤트 수 범위
- `locations`: 발생 가능한 Location ID 목록

`locations`는 비어 있을 수 없다.

Goal Event는 Goal Catalog의 Location과 일치하는 Location을 가져야 한다.

Opening Event는 시작 Location에서 강제로 발생하므로 일반 후보 선택과 경쟁하지 않는다.

Goal은 정규 풀에서 제외하며 최종 도전은 특수 처리한다. 정규 방문·후보 이력 때문에 최종 도전이 누락되지 않아야 한다. 시간 소진 시 실제 위치 이동과 이벤트 발생 중 연결 방식은 별도 결정한다.

Opening은 선택될 수 있는 시작 상태에서 발생 조건을 충족하도록 데이터를 작성한다. 장소 콘텐츠도 실제 발생 대상으로 정한 상태에서 진행이 막히지 않아야 하며, Choice 이벤트라면 선택 가능한 Choice가 최소 하나 있어야 한다. 이 조건의 완결성은 개발 단계에 정적으로 검토하며, 특수 이벤트라는 이유로 발생·선택지 조건을 무시하거나 시작 Node의 정규 이벤트를 일괄 금지하지 않는다.

### 선택지 조건

프로토타입의 선택지 조건은 다음만 지원한다.

```text
requiredTags
forbiddenTags
moneyMin
```

선택지 조건은 이벤트 발생 여부에 직접 영향을 주지 않는다.

Choice 이벤트가 발생 가능한 모든 State에는 선택 가능한 선택지가 최소 하나 있어야 한다.

같은 조건에서 같은 선택지를 고르면 항상 같은 결과가 발생한다. 확률형 결과는 지원하지 않는다.

## 19. Result

각 선택지 또는 Automatic 이벤트는 하나의 확정된 Result를 가진다.

```json
{
  "text": "결과 설명",
  "battle": false,
  "effects": {
    "addTags": [],
    "removeTags": [],
    "fameChange": 0,
    "reputationChange": 0,
    "moneyChange": 0,
    "revealGoalIds": [],
    "arcTransition": null
  }
}
```

- `battle`: 결과에 전투가 포함되는가
- 하나의 Result에는 전투를 최대 한 번만 포함한다.
- Result 내부에는 무작위 분기를 넣지 않는다.
- Result는 원정 시간을 직접 변경하지 않는다.
- Result는 RunPhase를 직접 변경하지 않는다.

`runTransition`은 사용하지 않는다.

Opening 완료, 최종 도전 진입, 길잡이 획득 성공·전투 패배와 영구 기록 확정은 Unity 원정 규칙으로 처리한다. 이벤트 Result에 이동·시간 변경이나 임의의 종료·획득 확인 필드를 추가하지 않는다. 실제 보물 획득 사실과 성공 연결 계약은 별도 설계한다.

## 20. Result 처리 순서

Unity는 일반적인 Result를 다음 순서로 처리한다.

1. 선택한 Choice ID를 확정한다. Automatic이면 예약 ID `auto`를 사용한다.
2. `battle == true`라면 연결된 전투를 실행한다.
3. 전투에서 패배하면 즉시 `BattleDefeat`를 확정하고 이후 Result Effect를 적용하지 않는다.
4. 전투가 없거나 승리하면 Tags, Fame, Reputation과 Money 변화를 적용한다.
5. `arcTransition`을 적용한다.
6. `revealGoalIds`를 적용한다.
7. `ResolvedEventCount`를 1 증가시킨다.
8. 정규 이벤트라면 런 전체에서 소비 처리하여 이후 모든 Node의 유효 후보에서 제외한다. 이것이 논리적인 덱 제거이며 Node별 잠재 후보 참조를 개별 소비 상태로 분리하지 않는다.
9. 이벤트, Choice ID와 결과를 연대기에 기록한다.
10. Opening Event라면 정상 완료 후 `RunPhase = Normal`로 전환한다.
11. 최종 도전의 결과 처리에서 왕의 길잡이 실제 획득이 확인되면 GoalSuccess와 Ended를 확정한다. Goal Result 정상 완료나 전투 승리만으로 획득을 가정하지 않는다. 실제 획득 확인 계약과 일반 장소 발견 트리거는 별도로 정한다.
12. 종료되지 않았고 일반 탐험 중이면 11절의 도착 처리로 돌아간다. 목적지 Entrance는 전환 1회·도착지 이벤트·전투·보상·결과까지 마친 뒤 마지막에 시간을 검사하고, 소진 시 최종 도전으로 전환한다. 이미 최종 도전 중이라면 일반 탐험 도착 흐름이나 시간 소진 재전환으로 돌아가지 않는다.

전투가 있는 Result의 모든 비용과 보상도 전투 승리 후 적용한다.

프로토타입에서는 전투 전에 지불하거나 적용하는 Effect를 지원하지 않는다.

Goal은 정규 풀에 없으므로 완료 후 정규 덱에서 제거하지 않는다. 최종 도전 중복 진입·완료를 막는 상태 계약은 별도 설계하며, 일반 후보 소비·이력으로 대신하지 않는다.

### 장비 강화·보상의 연결 — 후속 처리 계약

2절의 장비 강화 기회와 특수 장비 직접 보상은 확정된 콘텐츠 요구다. 위 Result 순서는 현행 JSON의 Effect 처리 순서이며, 장비 지급이나 개별 장비 선택 단계가 이미 포함되었다는 뜻은 아니다.

강화에서는 플레이어가 장착·보관 중인 실제 장비 한 개를 선택해야 한다. 같은 정의의 다른 장비나 공통 정적 정의를 함께 바꾸지 않으며, 강화할 결과 종류를 다시 선택하거나 무작위로 정하지 않는다. 강화형·직접 획득형 특수 장비 모두 추가 강화 대상에서 제외한다.

대상 선택의 위치, 대상이 없는 경우·선택 취소·실패의 처리, 비용 지불, 장비 상태 변경과 나머지 Effect·완료 수 증가·이벤트 소비·연대기 기록의 선후 관계는 별도로 정한다. 선택 UI를 연 사실만으로 장비 지급·강화나 이벤트 정상 완료를 기록하지 않는다. 이 계약이 정해지기 전에는 강화 선택을 일반 Choice ID나 태그 하나로 대체하거나 예제 JSON에 임의의 장비 필드를 추가하지 않는다.

장비 강화 기회가 이벤트 중심이라는 이유로 모든 이벤트의 공통 비용·조건·출현 빈도나 다른 강화 경로의 전면 금지를 확정하지 않는다. 현행 후보 판정에 장비 소유·강화 가능 여부를 자동 조건으로 추가하는 것도 별도 명세 대상이다. 정규 이벤트의 런당 1회 소비와 재방문 후보 이력 원칙은 유지하며, 취소·대상 없음과의 연결은 후속 계약에서 명시한다.

### 축복 후처리 단계와의 연결

축복과 연결된 이벤트는 축복 조건에 필요한 태그·상태를 기존 Result로 반영한다. Result에서 축복을 직접 지급하거나 티어를 상승시키지 않으며, 태그 하나를 적용한 직후마다 축복을 검사하지 않는다.

원정이 계속되는 일반적인 경우의 연결은 다음과 같다.

```text
관련 이벤트와 Result 처리 완료
→ 반영된 태그·상태를 기준으로 미사용 축복 조건 검사
→ 조건을 만족하면 별도의 축복 획득 단계 실행
→ 축복 시스템에서 획득·티어 상승과 해당 조건의 사용 완료 기록 처리
```

조건별 원정당 1회 제한과 동시 발생 처리는 [BlessingSystem.md](BlessingSystem.md)를 따른다. 이 단계는 다른 정규 이벤트의 연속 발생을 허용한다는 뜻이 아니다.

위 흐름에 축복 후처리를 정확히 어디에 접합할지는 미정이다. 길잡이 획득 성공·전투 패배 또는 시간 소진에 따른 최종 도전 전환과 겹칠 때 축복 평가·지급을 실행하거나 생략하는 기준은 BlessingSystem에서 별도로 정한다. 이 연결만으로 확정된 원정 결과를 지연·취소하거나 종료 후 축복을 지급하지 않는다. 특별 장소 영구 효과도 신별 축복과 동일시하지 않는다.

## 21. Effects

### addTags / removeTags

정의된 Tag를 추가하거나 제거한다.

같은 Result에서 같은 Tag를 동시에 추가하고 제거할 수 없다.

### fameChange

현재 Fame에 `fameChange`를 더한 뒤 0 미만이면 0, 10을 초과하면 10으로 제한한다. 예를 들어 `10 + 1`은 10, `0 - 1`은 0이 된다. 한계값에서 증가·감소 효과가 있어도 이벤트 실행이나 다른 Effect의 적용을 막지 않는다.

### reputationChange

현재 Reputation에 `reputationChange`를 더한 뒤 -3 미만이면 -3, 3을 초과하면 3으로 제한한다. 예를 들어 `3 + 1`은 3, `-3 - 1`은 -3이 된다. 한계값에서 증가·감소 효과가 있어도 이벤트 실행이나 다른 Effect의 적용을 막지 않는다.

### moneyChange

적용 후 Money는 0보다 작아질 수 없다.

### revealGoalIds

```json
[
  "kings_guide"
]
```

- 현재 Result에서 새롭게 공개할 Goal ID 목록이다.
- 모든 ID는 Goal Catalog에 존재해야 한다.
- 이미 공개된 Goal은 중복 추가하지 않는다.
- Goal 공개는 해당 장소를 방문하거나 완료한 것으로 처리하지 않는다.
- 목표 정보 공개는 RunPhase를 변경하지 않는다. 최종 도전 진행 중인 상태를 Normal로 되돌리는 효과가 아니다.
- 이벤트 생성기는 Goal Location 자체를 변경하거나 새 지리 연결을 만들지 않는다.

### arcTransition

```json
{
  "arcId": "refugee_caravan",
  "stage": "Resolution",
  "status": "Completed"
}
```

- Arc State를 변경하지 않으면 `null`이다. Introduction Event의 Result에는 `null`을 사용할 수 없다.
- `arcId`는 현재 이벤트의 `arcId`와 일치해야 한다.
- Standalone, Opening, Goal Event는 항상 `null`이다.
- 다른 Arc의 State를 직접 변경할 수 없다.
- 사용할 수 있는 Status는 `Active` 또는 `Completed`다.
- Introduction Event의 정상 완료 가능한 모든 Result는 해당 `Pending` Arc를 `Active` 또는 `Completed`로 바꾸는 `arcTransition`을 반드시 가진다. 전투 패배로 Result를 적용하지 않는 경우에는 전이도 수행하지 않는다.
- Active Arc는 Stage를 변경하거나 `Completed`로 종결할 수 있다.
- `Completed` Arc는 다시 활성화할 수 없다.
- 불리한 결말과 목표 실패도 사건군 자체가 끝났다면 `Completed`를 사용하고 Tags로 결과를 남긴다.

## 22. 전투 연결

프로토타입에서 실제 전투는 이벤트 생성 후 사람이 직접 연결한다.

`Events/Bindings/BattleBindings.json` 예시는 다음과 같다.

```json
[
  {
    "eventId": "orc_scout_encounter",
    "choiceId": "attack",
    "battleId": "OrcScout_01"
  },
  {
    "eventId": "opening_goblin_raid",
    "choiceId": "auto",
    "battleId": "GoblinOpening_01"
  }
]
```

- Choice 이벤트는 안정적인 Choice ID를 사용한다. 배열 인덱스를 연결 키로 사용하지 않는다.
- Automatic 이벤트는 예약된 Choice ID `auto`를 사용한다.
- 일반 Choice의 ID로 `auto`를 사용할 수 없다.
- `battle == true`인 모든 Result에는 정확히 하나의 유효한 연결이 있어야 한다.
- 연결된 `battleId`는 Unity에 존재하는 전투 데이터여야 한다.
- 이벤트 생성기는 `BattleBindings.json`이나 `battleId`를 생성하지 않는다.
- Unity는 연결되지 않은 Battle Result가 있는 이벤트를 유효하지 않은 콘텐츠로 처리한다.

이 구조는 프로토타입용이다. 이후 필요하면 직접 연결 대신 전투 Theme 또는 전투 Pool을 통한 자동 선택 방식으로 교체할 수 있다.

## 23. 연대기와 후일담

Unity는 실제로 발생한 이벤트, 선택한 Choice ID와 적용된 결과를 순서대로 기록한다.

Automatic 이벤트는 Choice ID로 `auto`를 기록한다.

전투 패배 시에도 해당 이벤트와 선택, 전투 패배 사실은 기록할 수 있지만 적용되지 않은 Result Effect는 기록하지 않는다.

원정 종료 시 다음도 기록한다.

- 종료 사유: 길잡이 획득 성공 또는 전투 패배. 시간 소진은 최종 도전 진입 계기로 구분하며 추가 실패 결과의 저장 형식은 별도 확정한다.
- 제시된 목표 Location과 도달한 마지막 Location
- 이번 런에서 실제 발견한 장소와 특별 장소 발견 여부. 신규 발견 기록의 보존·무효화는 새 종료 구조의 정책을 정한 뒤 기록한다.
- 확정된 영구 지도 기록, 발견 원정대와 특별 장소의 영구 효과 해금
- Fame과 Reputation
- Arc별 최종 `Pending`, `Active`, `Completed` 상태
- 주요 Facts, Knowledges와 Traits

원정 종료 때문에 `Pending`이나 `Active` Arc를 다른 Status로 강제 변경하지 않는다.

런 내부 사건 연대기와 영구 지도·해금은 별개다. 최종 도전의 진입 계기·결과를 구분해 기록하는 방식과 신규 발견의 보존·표시 범위는 별도로 정한다. 새 종료 구조의 기록 확정 정책은 15절의 미정 사항을 따른다.

후일담 조각을 사용하는 경우 `Events/Generated/EpilogueFragments.json`에서 현재 상태와 일치하는 조각을 선택할 수 있다.

예:

```json
[
  {
    "id": "legacy_respected_party",
    "category": "Legacy",
    "arcId": null,
    "arcStatus": null,
    "conditions": {
      "requiredTags": [],
      "forbiddenTags": [],
      "fameMin": 5,
      "fameMax": 10,
      "reputationMin": 1,
      "reputationMax": 3
    },
    "text": "그 원정에서 돌아온 모험가들의 이름은 여러 여행자에게 알려졌다."
  },
  {
    "id": "refugee_caravan_unfinished",
    "category": "Arc",
    "arcId": "refugee_caravan",
    "arcStatus": "Active",
    "conditions": {
      "requiredTags": [],
      "forbiddenTags": [],
      "fameMin": null,
      "fameMax": null,
      "reputationMin": null,
      "reputationMax": null
    },
    "text": "원정이 끝날 때까지 난민 행렬의 여정은 아직 계속되고 있었다."
  }
]
```

후일담은 런의 State를 변경하거나 새로운 선택지를 제공하지 않는다.

길잡이 획득 결과는 이번 모험의 성공 결말을 설명한다. 일반 특별 장소의 발견 서사는 그 자체로 엔딩이 아니다. 시간 소진 화면은 즉시 실패가 아니라 최종 도전 전환을 안내하며, 종료 화면과 영구 기록 보존 결과는 정해진 계약에 따라 구분한다.

## 24. 필수 검증 규칙

Unity에 포함하기 전에 최소한 다음 항목을 검증한다.

Goal Catalog·Event의 필드 검증은 현행 계약 검사다. 통과하더라도 단일 목표의 실제 획득 확인·최종 도전 전환·영구 기록 기능이 구현됐음을 뜻하지 않는다.

### ID와 참조

- Event ID가 전체 이벤트에서 고유하다.
- 같은 Event 안에서 Choice ID가 중복되지 않는다.
- Choice ID로 예약어 `auto`를 사용하지 않는다.
- 참조하는 Arc, Stage, Location, Goal과 Tag가 존재한다.
- Goal Catalog의 각 Goal이 유효한 Location과 정확히 하나의 Goal Event를 가진다.
- Goal Catalog의 `locationId`는 Goal 사이에 중복되지 않으며 하나의 Node에 Goal을 하나만 연결한다.
- Goal Event의 `goalId`와 Goal Catalog의 연결이 일치한다.

### 이벤트 타입

- Opening Event의 `arcId`, `goalId`, `arcStage`는 `null`이다.
- Goal Event의 `goalId`는 유효하고 `arcId`, `arcStage`는 `null`이다.
- Standalone Normal Event의 `arcId`, `goalId`, `arcStage`는 `null`이다.
- Introduction Event는 유효한 Arc ID와 Stage를 가진다.
- Arc Normal Event는 유효한 Arc ID와 Stage를 가진다.
- `Main`, `Sub`, `Finale`, `FinaleReady` 관련 타입과 필드는 사용하지 않는다.

### 런 이벤트 풀과 Node별 잠재 후보

- 런 시작에 선정된 Arc의 모든 정규 이벤트와 일반 Standalone Event를 풀에 포함한다. Opening과 최종 Goal은 정규 풀에서 제외하고 특수 규칙으로 처리한다.
- 장소상 발생 가능한 각 Node에 동일한 Event ID의 참조를 연결하며, 초기 동적 조건이 맞지 않는다는 이유로 후보를 누락하지 않는다.
- 한 Node에 같은 Event ID를 중복 연결하지 않고, 여러 Node가 같은 이벤트의 런 전체 소비 상태를 공유한다.
- 실제 진입 시에는 해당 Node의 목록만 검사하여 현재 조건을 충족하고 아직 소비되지 않은 후보를 구한다. Tags·State 변화만으로 원격 목록을 교체하거나 이벤트를 실행하지 않는다.
- 정상 완료된 정규 이벤트는 어느 Node에서도 다시 실행하지 않는다. 조건 불충족이나 미선택만으로는 런 전체에서 소비하지 않는다.
- 잠재 후보 목록 작성이나 원격 상태 변화로 방문·후보 이력을 미리 채우지 않는다. 후보 이력은 실제 방문에서 확인한 유효 후보 전체를 기준으로 관리한다.

### 노드 진입과 재방문

- 시작 Location은 대도시 Node이며, 인류가 이미 밝혀낸 장소는 이 도시를 중심으로 방사형으로 펼쳐진다는 전제를 따른다.
- Opening Location에는 정확히 하나의 Opening Event가 존재한다.
- 시작 Node의 최초 진입을 방문 기록에 남기고 재방문으로 Opening을 다시 실행하지 않는다.
- Node의 실제 진입에 같은 서사 이벤트 규칙을 적용하며, 경유 Node의 진입 판정을 생략하지 않는다.
- 첫 방문에 유효 후보가 0개인 상태를 정상적인 무이벤트 방문으로 허용한다.
- 유효한 탐험 기회와 선택 대상 후보가 있으면 별도의 무이벤트 확률 없이 정규 이벤트 1개가 발생한다.
- 한 번의 노드 진입에서 정규 이벤트는 최대 하나만 발생한다.
- 재방문에서는 과거 해당 노드의 탐험 기회에 후보가 아니었다가 조건에 따라 새로 유효해진 후보만 선택한다.
- 같은 State 변화로 열린 후보 전체를 기록하여 단순 왕복으로 남은 이벤트를 순차 소진할 수 없도록 한다.
- 과거에 후보였던 이벤트가 다시 유효해져도 새 후보로 취급하지 않는다.
- 다른 진입 경로를 사용했다는 이유만으로 탐험 기회를 추가하지 않는다.
- 이벤트 결과가 현재 노드의 새 후보를 열어도 즉시 연속 발생하지 않고 이후 실제 재진입에서 검사한다.
- 같은 Area와 서로 다른 Area의 Node 사이에서 방문·후보 이력이 충돌하지 않는다.
- 노드 화면이나 시설 UI를 열고 닫는 것은 실제 Node 재진입으로 처리하지 않는다.
- 시설 이용은 서사 이벤트와 분리하며 무이벤트 방문과 재방문에서도 이용할 수 있다.

### Area와 Entrance 이동

- 모든 Node는 공간 단위 Area를 부모로 가지며 Area 자체를 Node로 취급하지 않는다.
- 일반 이동은 같은 Area의 명시된 Edge와 통행 조건을 따르며, 다른 Area의 Node를 일반 목적지로 선택할 수 없다.
- 노드 화면은 현재 Area의 Node만 표시하고 Entrance 전환 후 새 Area의 Node를 표시한다.
- 선택한 이동 목적지가 Entrance이면 입구 방문·이벤트 처리를 마친 뒤, 종료되지 않고 일반 탐험이 계속될 때 추가 입력 없이 지정된 다른 Area의 Node로 한 번 전환한다. 최종 도전 진행 중에는 일반 Area 전환을 실행하지 않는다.
- 전환 시 현재 Area와 위치를 함께 변경하고 도착 Node의 방문·후보 이력과 이벤트를 별도로 처리한다. 입구에서 반영한 결과와 덱 소비를 도착지 판정에 반영한다.
- 전환 대상이 Entrance여도 자동 재전환하지 않는다.
- 경유 Entrance는 전환만 생략하고 방문·후보·서사 이벤트 판정을 유지한다.
- 경유 사건으로 인한 일시 정지가 플레이어가 선택한 목적지를 바꾸지 않는다.
- Edge의 `weight`를 원정 시간 비용으로 적용하며 0을 허용한다.
- Entrance 전환 자체의 시간 비용은 0이며 전환 시 별도의 시간을 차감하지 않는다.
- 입구와 도착지에서 기존 규칙에 따라 정규 이벤트가 각각 최대 1개 발생할 수 있다. 특별 장소 발견만으로 예정된 전환을 중단하지 않으며, 길잡이 획득 성공이나 전투 패배가 확정되면 남은 전환·이벤트를 진행하지 않는다.
- 입구 정상 처리 후 종료되지 않고 일반 탐험이 계속되면 전환하며 별도의 시설 UI나 이동 선택을 끼워 넣지 않는다. 최종 도전 진행 중에는 전환하지 않으며, 현재 데이터에 임의의 전환 취소 선택지를 작성하지 않는다.
- 이미 서 있는 Entrance의 재선택과 복귀 조작, 구체적인 Area·Node 참조 스키마는 별도로 확정한다.
- 이미 밝혀진 구간의 이동 처리를 기존 Node·Edge 규칙만으로 확정하지 않는다.

### Result와 전투

- Choice 이벤트가 발생 가능한 모든 State에 선택 가능한 Choice가 최소 하나 있다.
- 모든 Result가 결정적이며 확률 분기를 포함하지 않는다.
- Battle Result마다 유효한 전투 연결이 정확히 하나 존재한다.
- Fame과 Reputation은 변화량을 적용한 뒤 각각 `0 ~ 10`, `-3 ~ 3`의 상하한에서 제한한다. 한계값에서도 다른 Effect는 정상 적용한다.
- Money는 Effect 적용 후 0보다 작아지지 않도록 선택지 조건과 비용을 구성한다. 명성·평판의 상하한 제한을 Money의 부족한 비용을 면제하는 규칙으로 사용하지 않는다.
- 같은 Result에서 같은 Tag를 동시에 추가하고 제거하지 않는다.
- `revealGoalIds`의 모든 Goal이 Goal Catalog에 존재한다.

### 축복 연결

- 축복 조건에 쓰이는 Tag도 Facts, Knowledges, Traits 중 해당 참조 데이터에 정의되어 있다.
- 이벤트 Result에 축복 직접 지급·티어 상승·조건 사용 기록을 위한 임의 필드가 없다.
- 축복 시스템은 조건 사용 여부를 Tag와 별도로 기록하며, 같은 조건으로 획득 기회를 반복 제공하지 않는다.
- 문서의 설명용 태그를 실제 참조 데이터에 등록된 콘텐츠로 간주하지 않는다.

### Arc

- Arc는 `Pending`으로 시작한다.
- Introduction Event를 통해서만 `Pending -> Active/Completed` 전환이 일어난다.
- Introduction Event의 정상 완료 가능한 모든 Result에 해당 Arc를 `Active` 또는 `Completed`로 바꾸는 `arcTransition`이 존재한다. `null` 결과로 Introduction만 소비하고 Arc를 `Pending`에 남기지 않는다.
- `Completed` Arc가 다시 활성화되지 않는다.
- Standalone, Opening, Goal Event는 `arcTransition`을 사용하지 않는다.
- 원정 종료 시 `Pending`과 `Active` Arc를 자동 종결하지 않는다.

### Opening·장소 콘텐츠의 정적 검토

다음은 이벤트 배치와 조건·결과를 작성할 때 지킬 콘텐츠 구성 원칙이며, 개발 단계에서 AI 정적 검토의 대상으로 삼는다. 이를 보장하기 위한 별도의 런타임 차단이나 임의의 대체 선택지·결과 생성 규칙은 추가하지 않는다.

- 시작 Node의 최초 진입에는 Opening만 발생하도록 정규 이벤트를 배치하고 조건을 작성한다.
- 특별한 계기 없이 시작 Node를 왕복하는 것만으로 다른 이벤트가 열리지 않는다. 명시적인 계기로 조건이 열린 경우에는 이후 실제 재진입에서 일반 재방문 규칙을 적용할 수 있다.
- 선택 가능한 Opening은 해당 시작 상태에서 발생 조건을 충족하고, Choice 방식이면 진행 가능한 선택지를 가진다.
- 장소 콘텐츠가 실제 발생 대상으로 정한 상태에서 조건 충돌, 선택지 잠김이나 전투 연결 누락으로 진행이 막히지 않는지 검토한다.
- 최종 도전은 제한 전 자율 진입과 소진 후 강제 진입 모두에서 진행 가능해야 한다. 단순 도착·목격·전투 승리와 실제 길잡이 획득을 구분하며, 임의의 대체 선택지로 막힌 콘텐츠를 우회하지 않는다.

### 목표와 영구 발견

- 최종 목표 장소는 하나이며 별도 Goal Node 타입이 아니다.
- 최소 3개 스토리라인은 콘텐츠 목표이며 단일 이동 루트나 일괄 완주 조건을 강제하지 않는다.
- 제한 전 언제든 최종 도전에 나설 수 있으며 조기 도전의 별도 이득은 없다.
- 다른 Area의 목표 정보 안내와 일반 이동 목적지 선택을 구분한다.
- 목표 공개·일반 장소 발견·길잡이 실제 획득을 서로 대신하지 않는다.
- 특별 장소의 영구 기록·해금은 유지하지만 새 성공·패배 결과에 따른 보존과 확정 시점은 미정이다. 시간 소진 전환만으로 확정·무효화하지 않는다.
- 이벤트 생성기가 획득 확인·영구 기록 필드나 새 종료 enum을 임의 추가하지 않는다.

### 런 진행

- Opening 정상 완료 후 일반 탐험으로 전환하며 최종 도전 진행과 Ended를 구분한다.
- 길잡이 실제 획득 결과 완료가 GoalSuccess이며, 단순 Goal 정상 완료·전투 승리는 충분 조건이 아니다.
- 전투 패배는 즉시 BattleDefeat와 Ended를 만들고 후속 효과를 적용하지 않는다.
- Edge weight만 시간을 소비하며 일반 노드 행위와 Entrance 전환에는 시간을 차감하지 않는다.
- 도착 이벤트·전투·보상·결과를 완료한 뒤 시간 소진을 판정한다. 목적지 Entrance는 입구 처리·전환 1회·도착지 처리까지 포함한다.
- 경유 Node에서 소진되면 그곳의 결과 뒤 최종 도전으로 전환하며 원래 경로를 더 진행하지 않는다.
- 최종 도전 전환 결정 후 0비용 이동으로 탐험을 연장하거나 최종 도전 중 시간 소진을 반복 처리하지 않는다.
- 이미 확정된 GoalSuccess·BattleDefeat를 시간 소진으로 덮어쓰지 않는다.
- 정규 이벤트 고갈과 시간 소진은 종료 결과가 아니다.

### 장비 거래·강화 연결의 검토

- 상점 이용은 시설 처리이며 정규 이벤트의 후보 선택·소비와 구분한다. 구매 수량만큼 감소한 재고를 같은 원정의 재방문으로 복구하지 않는다.
- 장비 구매·판매의 골드와 장비·재고 변화는 별도 거래 계약으로 연결한다. 현행 `moneyChange`만으로 장비 거래가 지원된다고 해석하지 않는다.
- 강화는 장착·보관 장비 중 플레이어가 선택한 실제 한 개만 변경하고, 일반형별 고정된 특수형으로 연결하며 특수 장비를 재강화하지 않는다.
- 대상 없음·취소·선택 순서·비용·완료·소비·기록의 미정 처리를 임의의 JSON 필드·태그로 대체하지 않는다.
- 같은 원정의 최종 도전 진입에서 장비·재고를 초기화하지 않고 실제 종료 후 장착·보관 장비를 다음 원정으로 이월하지 않는다.

## 25. 현재 지원하지 않거나 미정인 기능

현재 지원하지 않는 기능:

```text
런타임 LLM 생성
이벤트끼리 다음 Event ID 직접 지정
Main / Sub Arc 구분
Main Arc Finale
FinaleReady
이벤트 덱 고갈 종료
복잡한 조건식
OR 조건 그룹
임의 변수와 수식
선택 결과의 확률 분기
랜덤 Effect
한 Result 안의 복수 전투
전투 전 비용 또는 Effect 적용
이벤트 생성기가 지정하는 실제 Battle ID
이벤트 Effect를 통한 Location 이동
입구 이벤트 선택지에 의한 Entrance 전환 취소
이벤트 Effect를 통한 원정 시간 변경
이벤트 조건을 통한 원정 시간 판정
NPC별 호감도
세력별 평판
개별 모험가의 서사 State
원정 종료 시 Arc 강제 Abandoned 처리
```

개별 모험가의 직업별 레벨 보상과 공용 특성에 관한 기본 구조는 [plan.md](plan.md)를 따른다. 공용 특성은 파티 단위의 서사 Tag인 Trait과 별개이며, `Data/Traits.csv`에 정의된 태그를 의미하지 않는다.

장비 보유 조건·지급·선택 개체 강화는 현행 이벤트 JSON에서 아직 지원하지 않는다. 이는 장비 강화 기회와 특수 장비 보상 기획이 미정이라는 뜻이 아니라, 확정 요구사항을 반영할 Conditions·Result·런타임 계약이 남아 있다는 뜻이다.

현재 Plan에서 아직 미정인 항목:

- 짧은 반복 런의 구체적인 총 원정 시간
- Edge별 `weight` 산정 방식
- 남은 시간보다 긴 이동의 시작 허용과 처리 방식
- 대도시를 중심으로 이미 밝혀진 구간의 이동 처리
- 이미 서 있는 Entrance를 다시 선택하는 조작과 복귀 방식
- 콘텐츠의 고정·랜덤 배치 기준, 이벤트 간 우선순위와 방문 시 복수 유효 후보 선택 알고리즘. 런 시작의 Node별 잠재 후보 분류와 실제 진입 시 조건 검사는 확정 규칙이다.
- Area·Node·Edge·Entrance 대상의 데이터 구조와 기존 Locations CSV 마이그레이션
- 현재 위치, Node별 잠재 후보 참조와 런 전체 소비 상태, 방문·후보 이력 메타데이터, 이벤트 `locations`와 Goal Catalog의 Area·Node 참조 방식 및 식별자 스키마
- 다른 Area에 있는 목표 위치를 안내하는 구체적인 UI
- 진입 방향을 이벤트 조건에 포함할지
- 탐험 기회의 후보 이력을 Result 적용 전후 어느 시점에 갱신할지
- 회복·재정비 비용과 반복 이용 규칙
- 영입 후보 갱신. 장비 상점은 같은 원정 동안 재고를 보충하지 않는 규칙이 확정이며 초기 목록·수량·생성 시점·가격·되사기·판매품 재고 편입·특수 장비 판매 여부가 미정
- 강화 이벤트의 빈도·비용·조건·미리보기·대상 없음·취소, 실제 장비 선택·강화·특수 보상 지급과 Result 완료·소비·기록을 연결하는 데이터 및 처리 순서
- 개별 장비·보관·장착·강화·상점 재고의 저장 계약과 시작 장비 구성. 장착·보관 장비의 원정 수명과 종료 초기화는 확정
- 특별 장소의 구체적인 배치·접근 조건과 제한 시간 내 도달 가능 경로의 검증 방식
- Location의 발견을 인정하는 구체적인 행위·처리 시점과 장소 콘텐츠의 이벤트 연결·우선순위·소비 방식
- 기존 GoalCatalog·Goal 필드의 단일 최종 목표 연결, 실제 길잡이 획득 확인과 성공 처리, 최종 도전 진행 상태·중복 방지 및 이전 TimeExpired 데이터의 이행
- 최종 도전의 강제 이동·목표 이벤트 발생 중 방식 선택, 접근 UI·이동 비용 및 흰밀물 로어와의 연결
- 스토리라인의 내용·진행 순서·상호 관계·완주 조건, 선방문·중단·동시 진행과 최종 도전에 반영할 준비 요소
- 이번 런의 발견과 영구 지도·발견자·해금 저장 스키마, 새 종료 구조의 성과 보존·확정 시점
- 중도 포기 허용 여부, 최종 도전 복귀·기타 실패 후 처리
- 특별 장소 발견 후 전투 패배 시 신규 발견 기록과 해금의 보존 여부
- 모든 특별 장소 해금 이후에도 단일 목표를 유지할 때의 영구 기록·성과 처리
- 특수 사건에 따른 원정 종료와 성과 처리. 구현 우선순위는 낮다.
- 무효화된 발견이 있는 원정의 연대기 보존·표시 범위
- 확정된 공유 성장 규칙을 이벤트·전투 결과와 연결하는 보상 처리 계약. 상세 성장 기준은 MercenarySystem을 따른다.
- 영구 발견·해금과 원정 수명인 용병·공유 성장·장비·축복 상태의 저장 경계

축복 관련 후속 결정은 [BlessingSystem.md](BlessingSystem.md)의 미정 사항을 따른다. 특히 원정 종료와 축복 후처리의 정확한 순서, 비선택·거절 조건의 사용 기록, 축복 획득 후 재평가·연쇄 발생 여부와 이벤트 종료 외의 검사 시점은 아직 확정하지 않았다.

이 기능이나 규칙을 확정할 때 개별 Event JSON에 임의 필드를 추가하지 않고 EventSystem 변경 사항으로 별도 반영한다.
