# 애니메이션 이벤트 툴 사용 안내

- 갱신일: 2026-11-08
- 관련 계획: [애니메이션 직접 재생 이관 및 이벤트 툴 구현 계획](AnimationPlaybackAndEventToolPlan.md)
- 최종 화면 조작·사용성 검증은 사용자가 직접 수행한다.

## 1. 시작

Unity Editor에서 `Assets/Scenes/AnimationEventTool.unity`를 열고 Play Mode로 진입한다. Game 뷰는 최소 **900×600**, 편집에는 **1280×900 이상**을 권장한다. Scene의 Preview Camera, Directional Light, PreviewRoot, ToolController 연결은 배치되어 있다.

카메라는 위치 약 `(2.25, 4.082, 2.25)`, 회전 `(45, 225, 0)`, FOV `40`으로 캐릭터 중심을 향해 위에서 사선으로 내려다본다. ToolController는 UI 사이의 프리뷰 영역에 카메라 화면을 맞추고 종료 시 원래 화면 영역을 복원한다.

프리팹·애니메이션 목록, 이벤트 속성, 저장·안내는 오른쪽 스크롤 패널에 모여 있다. 왼쪽은 캐릭터 프리뷰이고 그 아래에 타임라인이 있다.

- 프리뷰 위 **마우스 휠**: 확대·축소.
- 프리뷰에서 **마우스 오른쪽 버튼 드래그**: 캐릭터 중심으로 시점 회전.
- **시점 초기화**: 시작 구도로 복원.

같은 캐릭터의 애니메이션을 바꾸거나 다시 스폰해도 시점을 유지한다. 다른 캐릭터를 정상적으로 불러오면 기본 시점으로 돌아간다. 패널·팝업에서는 카메라를 조작하지 않으며, 시점 변경은 에셋이나 Scene에 저장하지 않는다.

## 2. 캐릭터와 애니메이션 목록

1. **Combat 프리팹**에서 캐릭터를 선택한다. `Assets/Prefabs/Combat` 하위 프리팹을 검색하고 캐릭터 한 개를 스폰한다.
2. **캐릭터에 배정된 애니메이션**에는 해당 프리팹의 `CharacterAnimationProfile`에 저장된 항목만 표시한다. 항목을 선택하면 그 클립과 이벤트를 불러온다.
3. **애니메이션 불러오기**에서 저장 키를 입력하고 클립을 선택한다. `Assets/Art/Character/Animation` 아래 클립 및 FBX 서브에셋을 검색한다. 같은 이름은 경로와 local ID로 구분한다.
4. 같은 클립을 다른 키로 여러 번 추가할 수 있다. 각 항목의 이벤트는 독립적이다.
5. 오른쪽에서 **키 변경** 또는 **선택 애니메이션 삭제**를 사용할 수 있다. 삭제도 저장 전에는 작업본에만 적용된다.

키는 앞뒤 공백을 제거하고, 빈 값과 캐릭터 안의 중복을 거부한다. 대소문자를 구분하므로 `idle`과 `Idle`은 다른 키다. 다른 캐릭터에서는 같은 키를 사용할 수 있다.

현재 게임은 정확한 키 **`idle`**, **`move`**, **`attack1`**을 초기화 시 찾아 대기·이동·기본 공격에 사용한다. `attack1` 클립은 반복하지 않아야 한다. `skill1` 등 다른 키는 저장·프리뷰할 수 있으며 이번에는 게임 실행을 연결하지 않는다. 빈 목록이나 일부 키만 있는 목록도 툴에서 저장할 수 있지만 게임 재생에는 세 필수 키가 모두 필요하다.

같은 캐릭터 안에서 항목을 바꿔도 미저장 편집 내용은 유지된다. 다른 캐릭터로 이동할 때는 **저장 후 계속 / 변경 버리고 계속 / 취소**를 선택한다. 저장 실패 시 작업본과 확인 창이 남는다. **다시 스폰**은 현재 작업본으로 프리뷰만 다시 만든다.

## 3. 전용 목록이 없는 캐릭터

목록이 없거나 다른 프리팹과 Profile을 공유하는 경우 오른쪽에 **캐릭터 전용 목록 만들기/복사**가 표시된다. 이 동작은 `Assets/GameData/Animations/Profiles`에 전용 Profile을 저장하고 선택한 프리팹의 `_animationProfile`에 연결한다. 복사한 이벤트는 원래 Profile과 독립적이다.

선택한 기본 프리팹의 연결을 바꾸면 하위 variant까지 바뀌는 경우에는 쓰기 전에 중단하고 영향받는 경로를 표시한다. 먼저 하위 variant부터 전용 목록을 만들어야 한다. 다른 프리팹을 자동 수정하지 않는다.

목록이 비어 있거나 아직 없으면 캐릭터는 기본 자세로 스폰된다. 유효한 클립을 선택하기 전에는 타임라인을 편집할 수 없다. 생성·연결 결과가 미확정이면 생성 경로를 보존하고 추가 쓰기를 차단하므로 **원본 다시 불러오기**로 연결 결과를 확인한다.

## 4. 프레임과 공격 판정

1. 아래 슬라이더 또는 **이전 프레임 / 다음 프레임**으로 정수 프레임을 선택한다.
2. **재생**은 시간 배율과 관계없이 1배속으로 진행하고 끝에서 멈춘다. 끝에서 다시 재생하면 처음부터 시작한다. 슬라이더나 이벤트 키를 선택하면 정지한다.
3. **공격 판정 추가**를 누르면 현재 프레임의 키가 슬라이더 위에 생긴다. 기본 종류는 근접이다.
4. 위쪽 키 또는 오른쪽 **키 목록**에서 선택하고 발생 프레임, **근접 / 투사체**를 편집한다. **선택 키 삭제**로 제거한다.

같은 프레임의 키도 개별 데이터다. 마커가 위로 쌓이며 마커 영역과 오른쪽 속성 패널을 스크롤할 수 있다. 프레임 변경으로 정렬 순서가 바뀌어도 선택한 이벤트를 유지한다.

이벤트 파라미터는 **정수 발생 프레임과 근접/투사체 구분**뿐이다. 마지막 프레임은 `floor(clip.length × clip.frameRate + 0.0001)`, 프리뷰 시간은 `min(frame / fps, clip.length)`이다.

## 5. 저장과 복구

**저장**은 캐릭터의 전체 목록을 해당 Profile 한 파일에 반영한다. 저장 후 다시 읽어 키·클립·작성 FPS·길이·전체 이벤트와 연결 상태를 검증한다. 자동 저장은 없으며 **Play 종료 또는 ToolController 비활성화 시 미저장 작업본은 사라진다.** 저장한 데이터는 Play 종료 이후에도 유지된다.

프리팹·Profile·목록의 모든 클립 및 의존 에셋이 변경되면 프리뷰를 정지하고 편집·저장을 차단한다. 선택하지 않은 항목, 작업본에서 삭제했지만 아직 저장하지 않은 항목도 검사한다. FPS와 길이가 같은 재임포트도 파일·설정 변화가 있으면 감지한다. 새 클립을 추가할 때 기존 원본 변화가 승인된 것으로 처리되지는 않는다.

**원본 다시 불러오기**는 작업본을 버릴지 확인한 뒤 디스크 원본을 다시 연다. 취소하거나 읽기에 실패하면 작업본을 보존한다. **목록 새로고침**으로 충돌 차단을 해제하지 않는다.

재임포트 후 작성 FPS·길이가 달라졌다면 원본을 다시 불러온 뒤 해당 항목의 **현재 클립 기준으로 다시 작성**을 선택한다. 선택한 항목의 이벤트만 비우며, 다른 항목은 유지한다. 이후 명시적으로 저장해야 원본에 반영된다.

쓰기 전 실패는 원본 메모리와 dirty 상태를 복원한다. 쓰기 후 검증 실패는 **저장 결과 미확정**으로 표시하고 재로드 전까지 추가 쓰기를 차단한다.

## 6. 데이터 이관과 범위

Warrior·Archer·Rogue의 기존 Profile GUID와 프리팹 연결을 유지하면서 기존 Idle·Move·Attack 데이터를 각각 `idle`·`move`·`attack1` 항목으로 옮겼다. 이전 `Definitions` 에셋은 복구용으로 보존하며 현재 툴과 게임은 Profile 내부 항목을 사용한다.

프리뷰는 복제한 캐릭터·클립과 별도 PlayableGraph를 사용한다. 게임 동작 컴포넌트, 충돌 및 내장 AnimationEvent 실행을 비활성화하고 루트 위치·회전을 고정한다. 임의로 추가한 스크립트의 모든 `Awake` 부작용까지 격리하는 도구는 아니다.

공격 판정 키는 게임의 피해·충돌·투사체 생성에 연결하지 않는다. 기존 공격 완료 처리와 피해 확정 시점은 유지한다. 이번 변경의 컴파일·자동 테스트 결과는 관련 계획 문서의 캐릭터 키 목록 구현 기록에 남긴다. 이번 구조 변경 이후의 화면 조작 검증은 사용자가 수행한다.

컴파일 오류 0건, 애니메이션 데이터·재생기·툴 자동 테스트 254/254 성공, 독립 코드 리뷰 Pass를 확인했다. 전투 테스트는 1,056개 중 1,017 성공·기존 실패 39건 재현으로 기록하며 전체 전투 테스트 성공을 의미하지 않는다.
화면·시점 조작 변경 후 툴 자동 테스트는 117/117 성공했으며 Unity 컴파일 오류는 0건이다. 실제 화면 조작 검증은 수행하지 않았다.
