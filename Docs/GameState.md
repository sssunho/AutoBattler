# GameState와 하위 State 설계

- 기준일: 2026-11-07
- 범위: 현재 원정의 상태 소유권, 하위 State의 필드·타입, 노드별 후보·런 공통 소비, 단일 최종 목표와 최종 도전 전환, 장비·강화·상점 재고의 상태 경계
- 상태: 논의한 구조를 정리한 구현 전 설계 문서다. 코드 구현, Scene 배치, 저장 형식의 확정을 의미하지 않는다.
- 참조: [Plan.md](Plan.md), [EventSystem.md](EventSystem.md), [MercenarySystem.md](MercenarySystem.md), [BlessingSystem.md](BlessingSystem.md)

## 1. 문서 기준과 상태 구분

GameState는 현재 원정의 상태를 묶는 최상위 컨테이너다. MercenaryState는 보유 용병 전체의 상태를 종합적으로 보유하며, 각 용병의 상태는 MercenaryInstance로 구분한다. 이벤트 시스템을 포함한 관련 시스템은 이 상태를 참조하여 각자의 규칙을 처리한다.

| 구분 | 의미 |
| --- | --- |
| 확정 규칙 | 기존 상세 명세에서 확정된 게임 규칙과 이번 논의에서 합의한 컨테이너의 책임 구분 |
| 제안 | 규칙을 표현하기 위해 정리한 구체적인 C# 필드·타입·컬렉션과 구현 방식. 구현 완료나 기존 데이터 형식의 변경을 의미하지 않는다. |
| 미정 | 추가 게임 규칙이나 데이터 계약을 결정해야 하는 항목. 필드의 타입을 제안했다는 이유로 정책까지 확정하지 않는다. |

이벤트 발생·소비·종료 규칙은 EventSystem, 탐험의 큰 구조는 Plan, 용병의 원정 수명·HP 유지·공유 성장은 MercenarySystem, 축복의 획득·초기화 규칙은 BlessingSystem을 따른다. Plan이나 EventSystem에 과거 미정 항목이 남아 있더라도 용병 상세 문서에서 확정한 공유 성장과 용병 수명 규칙을 다시 미정으로 취급하지 않는다.

본문의 필드 표는 별도 표시가 없으면 **런타임 스키마 제안**이다. 필드의 의미에 포함된 게임 규칙과 실제 저장 타입의 확정 여부를 구분한다. 표의 이름은 논리적인 필드·조회 이름이며, 구현 시 비공개 필드는 프로젝트 규칙에 따라 `_` 접두사를 사용한다.

## 2. 책임과 수명

### 확정된 책임 구분

- MercenaryState는 보유 용병과 공유 성장 상태를 담당한다.
- 위치·이동 시간은 이동 시스템이 처리한다. 이벤트 Result는 위치나 원정 시간을 직접 변경하지 않는다.
- 이벤트 시스템은 현재 상태로 조건을 판정하고, 정상 완료한 결과와 런 공통 소비 상태를 반영한다.
- 축복 시스템은 관련 이벤트 결과 처리 후 현재 상태와 조건 사용 기록을 검사하고, 축복 획득·티어 상승·조건 사용 완료를 처리한다.
- 이벤트의 파티 성향 Trait와 용병 개인의 성장·전투 특성은 서로 다른 정보다.
- 용병 런타임 데이터는 한 원정 동안 유지하며 종료 후 필요한 기록을 남기고 폐기한다. 장착 장비와 공용 인벤토리의 장비도 원정 종료 시 초기화하며 다음 원정으로 이월하지 않는다. 축복 티어와 조건 사용 기록도 다음 원정에 초기화한다.
- 장비의 보관·장착·강화 상태와 상점의 남은 판매 재고는 원정 상태다. 거래·강화 처리가 이를 변경하며, 같은 원정의 재방문이나 최종 도전 진입을 초기화 계기로 사용하지 않는다.

### 구현 제안

- GameState와 주요 하위 State는 일반 C# `class`로 두고, GameState가 각 상태 객체를 소유한다.
- 같은 원정 값을 여러 시스템이 별도 사본으로 유지하지 않는다. 현재 이동 코드가 보유하는 위치·남은 시간을 연결할 때도 ExplorationState를 원본으로 사용하는 방향으로 소유권을 조정한다.
- State는 데이터를 보관하며, 이벤트 판정·이동·성장·축복 처리 코드는 각자의 규칙에 따라 이를 변경한다.
- 직업·스킬·특성·장비·이벤트·Goal의 공통 정의는 정적 데이터에서 조회한다. 현재 HP·성장 선택·개별 장비의 강화·재고·이벤트 소비 같은 원정 상태로 공통 정적 정의를 수정하지 않는다.
- 전투의 좌표·현재 타깃·행동 진행과 장비 효과의 전투 중 충전·발동 상태 등은 전투 시스템에서 관리한다. 원정 용병·장비 상태와 전투 시작 입력·종료 결과를 연결하는 구체 인터페이스는 별도 설계한다.
- 관련 상태 변경과 Unity 객체 반영은 메인 스레드에서 정해진 순서로 처리한다. 비동기 전투가 끝나기 전에 원정 데이터를 폐기하거나 다음 원정에 재사용하지 않는다.
- 원정 종료 후 연대기와 필요한 최종 상태를 값으로 복사하여 보존한다. 이 구조 자체가 세계의 지식·발견 기록까지 모두 초기화한다는 뜻은 아니다.

## 3. GameState

| 필드 | 타입 | 의미와 제약 |
| --- | --- | --- |
| MercenaryState | `MercenaryState` | 보유 용병과 공유 성장 상태 |
| Money | `int` | 파티 보유 골드. 0 이상 |
| Fame | `int` | 파티 명성. 0~10 |
| Reputation | `int` | 파티의 사회적 평판. -3~3 |
| Tags | `HashSet<string>` | 파티의 Fact·Knowledge·Trait 태그 |
| RunPhase | `RunPhase` | 현재 원정 단계 |
| RunResult | `RunResult?` | 종료 전에는 값이 없고, 종료 시 결과를 보유 |
| ExplorationState | `ExplorationState` | 위치·시간·방문 및 과거 유효 후보 이력 |
| EventState | `EventState` | 노드별 잠재 후보, 런 공통 미소비 상태, Arc·Goal 진행 |
| BlessingState | `BlessingState` | 신별 축복 티어와 조건 사용 기록 |
| Chronicle | `List<ChronicleEntry>` | 발생 순서대로 쌓이는 사건 기록 |

하위 State와 컬렉션은 생성된 상태를 유지하며, 비어 있는 컬렉션을 `null`로 표현하지 않는다. `?`는 값이 없을 수 있음을 뜻하며, 실제 nullable 참조 타입 표기와 설정은 구현 환경에 맞춘다.

위 표는 장비 보관·장착·강화와 상점 재고의 구체 필드까지 확정한 스키마가 아니다. 이 상태도 GameState가 묶는 원정 상태에서 관리해야 하지만, 하위 컨테이너 배치·ID·컬렉션·저장 형식은 7.5절의 요구사항을 기준으로 별도 설계한다.

Money·Fame·Reputation의 범위와 Tags의 의미는 EventSystem의 확정 규칙이다. Fame·Reputation은 효과 적용 후 범위로 제한하며, Money는 적용 후 음수가 될 수 없다. 값의 변경 계산이 정수 오버플로로 이 규칙을 우회하지 않도록 구현 단계에서 검증한다. 초기 Money·Fame·Reputation·Tags 값은 이 표만으로 새로 정하지 않는다.

Tags의 세 분류는 런타임에서 모두 boolean 보유 여부로 취급한다. 분류·설명은 정적 정의에서 조회하며, 용병 개인의 TraitIds와 합치지 않는다.

### 공통 enum

| 타입 제안 | 값 | 규칙의 상태 |
| --- | --- | --- |
| RunPhase | `Opening`, `Normal`, `FinalChallenge`, `Ended` | 일반 탐험·최종 도전·종료의 구분은 확정 방향. `FinalChallenge` 이름과 enum 추가는 구현 제안 |
| RunOutcome | `GoalSuccess`, `BattleDefeat` | 실제 길잡이 획득 성공과 기존 전투 패배. 시간 소진은 종료 결과로 사용하지 않음 |
| ArcStatus | `Pending`, `Active`, `Completed` | 상태와 의미는 EventSystem 확정 규칙 |
| EventBattleOutcome | `Victory`, `Defeat` | 연대기의 전투 결과를 표현하는 보조 타입 제안 |

단일 최종 목표는 왕의 길잡이를 획득할 장소다. 자유로운 탐험 중 제한 전에는 언제든 도전할 수 있으며, 시간이 소진되면 현재 방문의 결과를 마친 뒤 최종 도전으로 전환한다. `FinalChallenge`는 같은 원정 안의 진행 상태이므로 용병·성장·장비·상점 재고·축복·Tags를 초기화하지 않는다. 남은 시간 0을 이유로 최종 도전 중 다시 진입하거나 즉시 종료하지 않는다.

기존 `TimeExpired` 저장값·코드의 이행은 미정이다. 최종 도전의 강제 이동·목표 이벤트 발생 중 방식, 진입 문맥·복귀·기타 실패 처리는 별도 설계한다. 이 표로 새 enum·저장 스키마나 구체 UI를 확정하지 않는다.

## 4. 위치와 식별자

### LocationKey — 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| AreaId | `int` | Node가 속한 Area의 ID |
| NodeId | `int` | 해당 Node의 ID |

LocationKey는 `readonly struct`로 제안한다. 동등성 비교와 해시에는 AreaId와 NodeId를 모두 사용한다. 현재 위치, 잠재 후보, 방문 이력, 과거 유효 후보 이력과 연대기 위치에 같은 키를 사용한다. 원정을 시작할 때 실제 존재하는 시작 위치로 초기화한다.

Area는 Node의 소속 공간이며 Node 자체가 아니라는 점과 서로 다른 Node의 이력이 충돌하면 안 된다는 점은 확정 규칙이다. 위 복합 키와 `int` ID의 채택, 전역·Area 내부 ID 범위, 기존 Location ID와의 연결·마이그레이션은 제안·미정 사항이다. 현재 Locations CSV나 이벤트 JSON이 이미 이 구조를 지원한다고 해석하지 않는다.

### 그 밖의 식별자 — 제안

- Event ID, Arc ID, Arc Stage, Goal ID와 Tag ID는 기존 데이터 계약에 맞춰 `string`을 사용한다.
- 신·축복 조건·스킬·개인 특성·전문화·선택 보상 슬롯·보상 ID도 우선 `string`을 제안한다. 이들의 실제 정적 정의 스키마와 ID 계약은 별도 설계 대상이다.
- 문자열 ID를 키로 사용하는 Dictionary와 HashSet은 `StringComparer.Ordinal`을 사용한다. ID의 대소문자를 임의로 정규화하지 않는다.
- 기존 `MercenaryClass` enum은 직업 식별자로 사용한다. 현재 `AbilityType` enum을 향후 스킬·특성·전문화 ID 전체의 대체 타입으로 간주하지 않는다.

## 5. EventState

### 5.1. 확정 규칙

- 런 시작에 사용할 Arc와 일반 Standalone Event를 선정하여 런 공통 정규 이벤트 풀을 구성한다.
- 선정된 Arc의 모든 Introduction·Normal 이벤트와 선정된 일반 Standalone 이벤트를 포함한다.
- 장소 조건상 가능한 모든 Node에 동일한 Event ID를 잠재 후보로 연결한다.
- 초기 Tags·Fame·Reputation·Money·해결 이벤트 수·Arc 상태·Stage가 맞지 않아도 장소상 가능하면 포함한다. 아직 열리지 않은 Arc 후속 이벤트도 포함한다.
- Opening과 Goal은 정규 이벤트 풀과 노드별 정규 잠재 후보 목록에 포함하지 않는다.
- 잠재 후보의 장소별 연결은 해당 런에서 유지한다. 한 Node에 같은 Event ID를 중복 연결하지 않으며 이벤트 정의나 소비 상태를 노드마다 복제하지 않는다.
- 실제 진입 때 해당 Node의 잠재 후보만 검사한다. 상태 변화만으로 원격 Node의 목록을 교체하거나 현재 유효 후보를 미리 확정하지 않는다.
- 정상 완료한 정규 이벤트는 런 전체에서 소비되어 어느 Node에서도 다시 발생하지 않는다. 조건 불충족이나 미선택만으로 소비하지 않는다.
- `Completed` Arc의 남은 이벤트는 후보에서 제외한다. 정규 이벤트 고갈은 원정 종료 조건이 아니다.

### 5.2. 필드·타입 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| PotentialEventIdsByLocation | `Dictionary<LocationKey, string[]>` | 노드별로 사전 연결한 정규 이벤트 잠재 후보 ID |
| RemainingEventIds | `HashSet<string>` | 이번 런에 포함된 정규 이벤트 중 아직 소비하지 않은 ID |
| ArcStates | `Dictionary<string, ArcState>` | Arc ID별 현재 진행 상태 |
| FinalGoalId | `string` | 이번 모험의 단일 최종 목표. ID 참조·저장 방식은 제안 |
| RevealedGoalIds | `HashSet<string>` | 현행 계약의 공개 Goal 목록. 단일 최종 목표·일반 장소 정보 안내로 이행하는 방식은 별도 결정 |
| ResolvedEventCount | `int` | 정상적으로 결과 처리가 완료된 이벤트 수. 0 이상 |

PotentialEventIdsByLocation은 런 시작에 구성한 뒤 배열을 수정하지 않는 조회용 인덱스다. 이벤트 정의는 공통 정적 데이터에서 조회한다. 후보가 없는 Node는 사전 항목을 생략하고 조회 시 빈 목록으로 취급할 수 있다.

RemainingEventIds는 런 공통 소비 상태의 원본이다. 런 시작에 선정된 정규 이벤트 ID 전체로 초기화하고, 정상 완료한 이벤트 ID를 제거한다. 해당 ID를 참조하는 노드별 배열은 유지한다. 실제 진입 시 `RemainingEventIds.Contains(eventId)`를 먼저 확인하여 소비된 이벤트를 제외한다. 방문 때 RemainingEventIds 전체를 순회하여 장소를 찾지 않는다.

소비된 ID 집합과 미소비 ID 집합을 동시에 별도 수정하는 구조는 두지 않는다. 초기 선정 결과를 동일하게 사용해 RemainingEventIds와 노드별 잠재 후보 인덱스를 구성한다. Arc가 Completed가 되었다고 남은 이벤트를 정상 완료된 것으로 기록하지 않으며, 현재 Arc 조건으로 후보에서 제외한다.

현재 유효 후보와 이번 선택 대상은 진입 처리 중 계산하는 임시 작업 목록으로 둔다. GameState에 노드별 현재 유효 후보 캐시를 추가하지 않는다. 작업 메모리의 재사용과 실제 선택 알고리즘은 처리 코드 설계에서 정한다.

### 5.3. ArcState — 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| Stage | `string` | 해당 Arc가 정의한 현재 단계 ID |
| Status | `ArcStatus` | Pending·Active·Completed |

ArcState는 `readonly struct`로 두고 전이 시 새 값으로 교체하는 안을 제안한다. Stage는 Arc별 콘텐츠가 정의하므로 공통 enum으로 고정하지 않는다.

선정된 Arc는 Pending과 Catalog의 초기 Stage로 시작한다. Introduction의 정상 완료 가능한 모든 Result는 Arc를 Active 또는 Completed로 전환해야 한다. Completed는 유리하거나 불리한 결말을 모두 포함하며 다시 활성화하지 않는다. 원정 종료 시 Pending·Active 상태를 강제로 변경하지 않는다. 이 의미와 전이 제약은 확정 규칙이다.

### 5.4. 목표와 완료 수

- FinalGoalId는 길잡이 획득 목표 하나를 참조하는 제안이다. RevealedGoalIds는 현행 공개 정보 계약이며 복수 최종 목표를 허용한다는 뜻이 아니다. 중복 공개는 no-op이고 공개만으로 방문·획득·종료를 처리하거나 RunPhase를 바꾸지 않는다.
- 하나의 Node에는 Goal 하나만 연결한다. 최종 도전은 정규 후보 추첨·과거 후보 이력과 분리해 처리하며 같은 진입에서 정규 이벤트를 추가 실행하지 않는다. 배치와 Event 연결, 실제 획득 확인은 정적·런타임 계약에서 구체화한다.
- ResolvedEventCount는 정상 완료된 Opening·Goal도 포함한다. 전투 패배로 중단된 이벤트는 증가시키지 않는다. 따라서 정규 이벤트의 소비 개수로 대신 계산하지 않는다.

## 6. ExplorationState

### 6.1. 필드·타입 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| CurrentLocation | `LocationKey` | 현재 Area와 Node |
| RemainingExpeditionTime | `long` | 최종 도전 전 탐험·성장에 남은 준비 시간. 소진 자체는 종료가 아님 |
| VisitedLocations | `HashSet<LocationKey>` | 이번 원정에서 실제 진입한 Node |
| SeenEligibleEventIdsByLocation | `Dictionary<LocationKey, HashSet<string>>` | Node별 과거 탐험 기회에서 확인한 유효 후보 전체 |

남은 시간은 현재 이동 코드와 맞춰 `long`을 제안한다. 이 타입이 음수를 표현할 수 있다는 사실로 남은 시간보다 비싼 이동을 허용하거나, 차감 결과를 음수로 유지하거나 0으로 제한하는 정책까지 확정하지 않는다.

방문은 이벤트 발생 여부와 무관하게 실제 Node 진입으로 기록한다. 첫 방문 여부는 기록 추가 전 상태로 판단한다. UI를 열거나 닫는 것은 방문이 아니다. SeenEligibleEventIdsByLocation의 항목이 없는 경우 과거 유효 후보가 없는 것으로 취급하는 안을 제안한다.

### 6.2. 세 종류의 이벤트 정보

| 정보 | 소유자 | 의미 | 변경 계기 |
| --- | --- | --- | --- |
| PotentialEventIdsByLocation | EventState | 이번 런에 해당 장소에서 발생할 수 있는 정규 이벤트 참조 | 런 시작에 구성하고 유지 |
| RemainingEventIds | EventState | 런 공통으로 아직 소비하지 않은 정규 이벤트 | 정상 완료한 정규 이벤트 소비 |
| SeenEligibleEventIdsByLocation | ExplorationState | 해당 Node의 과거 탐험 기회에서 유효했던 이벤트 전체 | 실제 탐험 기회에서 기록 |

잠재 목록 작성과 원격 상태 변화는 방문이나 유효 후보 확인이 아니다. 런 시작에 잠재 목록을 과거 후보 이력으로 복사하지 않는다. 유효 후보 중 선택되지 않은 이벤트도 해당 Node의 과거 후보 이력에는 포함되지만 런 전체에서 소비되는 것은 아니다.

### 6.3. 정규 이벤트 진입 처리

다음 발생·선택 범위는 EventSystem의 확정 규칙이다.

1. 실제 진입한 Node의 기존 방문 여부를 확인하고 방문을 기록한다.
2. Opening 최초 진입과 최종 도전 진입은 각 특수 규칙으로 처리한다. 정규 후보·재방문 이력 때문에 최종 도전이 누락되지 않도록 한다.
3. 정규 판정에서는 해당 Node의 잠재 목록만 순회한다. 런 공통 미소비 상태와 현재 State·Tags·Arc 상태·Stage·선택지 및 전투 연결 조건을 검사한다.
4. 첫 방문은 현재 유효 후보 전체를 선택 대상으로 삼는다. 재방문은 그중 과거 후보 이력에 없는 새 유효 후보만 선택 대상으로 삼는다.
5. 선택 대상이 있으면 정규 이벤트 하나를 선택한다. 별도의 무이벤트 확률은 두지 않는다. 후보가 없으면 정상적인 무이벤트 방문이다.
6. 해당 탐험 기회에서 확인한 유효 후보 전체를 과거 후보 이력에 기록한다. 선택한 하나만 기록하지 않는다.
7. 선택한 이벤트의 Result가 정상 완료되면 런 공통으로 소비한다. 전투 패배 시 후속 효과를 적용하지 않고 원정을 종료한다.
8. Result로 같은 Node의 다른 조건이 열려도 그 진입에서 정규 이벤트를 이어 실행하지 않는다. 다음 실제 재진입에서 검사한다.

위 순서 중 **후보 이력의 정확한 기록 시점은 기존 명세의 미정 사항**이다. 이번 설계에서는 후보와 선택을 확정한 뒤 Result 적용 전에 그때의 유효 후보 전체를 기록하는 안을 제안한다. Result가 새로 연 후보를 소급하여 과거 후보로 기록하지 않는다. 실제 구현에서 재진입과 중복 처리를 막는 처리 경계는 함께 구체화해야 한다.

복수 유효 후보 중 하나를 고르는 구체적인 알고리즘·가중치·우선순위는 미정이다. 재방문의 선택 대상이 새 유효 후보라는 확정 규칙과 선택 알고리즘의 미정 상태를 구분한다.

### 6.4. 동작 예시

| Node | 런 시작에 연결한 잠재 후보 |
| --- | --- |
| A | E1, E2, E3 |
| B | E1, E2 |

A 첫 방문에서 E1·E2만 유효하고 E1을 정상 처리했다면 다음 상태가 된다.

- A의 과거 후보 이력에는 E1·E2가 모두 들어간다.
- RemainingEventIds에서는 E1만 제거한다.
- 두 Node의 잠재 후보 배열은 유지한다.
- A를 단순 재방문해도 E2는 새 후보가 아니다.
- B에서는 그곳의 조건과 과거 후보 이력에 따라 E2가 발생할 수 있다.
- 나중에 E3의 조건이 열려도 즉시 A의 이력을 바꾸지 않는다. A에 실제 재진입했을 때 새 후보로 판정한다.

### 6.5. Opening·Entrance·시간 — 확정 규칙

- 시작 Node의 최초 진입도 방문 기록에 남긴다. 그 방문에는 Opening만 발생하도록 콘텐츠를 구성하며 초기 정규 후보 이력은 비어 있다.
- 시작 Node의 잠재 목록에는 특별한 계기로 나중에 열릴 정규 이벤트가 들어갈 수 있다. 시작 Node의 정규 이벤트를 런타임에서 일괄 금지하지 않는다.
- Opening Result로 열린 후보도 실제 재진입 전에 과거 후보로 기록하지 않는다. Opening은 재방문으로 다시 실행하지 않는다.
- 최종 도전이 시작된 진입에는 정규 이벤트를 추가 추첨하지 않는다. 콘텐츠의 조건·선택지 완결성은 데이터 구성과 정적 검토로 보장하며 런타임에서 조건을 무시하지 않는다. 단순 정보 공개나 일반 장소 발견을 최종 도전·성공으로 처리하지 않는다.
- 목적지 Entrance는 입구 방문·이벤트 결과를 처리하고, 종료되지 않았으며 최종 도전 진행 중도 아니라면 비용 0으로 한 번 전환한 뒤 도착 Node의 방문·이벤트 결과를 처리한다. 도착지가 Entrance여도 자동으로 재전환하지 않는다.
- 도착지에서는 입구에서 변경된 State·Tags·Arc와 런 공통 소비 상태를 반영하여 자신의 잠재 목록을 검사한다. 입구와 도착지는 별도 Node이므로 각각 정규 이벤트가 최대 하나씩 발생할 수 있다.
- 경유 Entrance는 Area 전환만 생략한다. 방문과 이벤트 판정은 수행하며, 사건으로 잠시 멈춰도 원래 이동 목적지가 바뀌지 않는다.
- 어느 지점이든 길잡이 실제 획득 성공이나 전투 패배가 확정되면 남은 전환·이벤트를 중단한다. 도착·목격·전투 승리·Goal Result 정상 완료만으로 획득을 가정하지 않는다.
- Edge 이동으로 시간이 0 이하가 되어도 현재 도착 범위의 이벤트·전투·보상·결과를 모두 마친 뒤 시간 소진을 판정한다. 목적지 Entrance는 전환 1회와 도착지 처리까지 포함한다. 종료되지 않았고 일반 탐험 중이면 최종 도전으로 전환하며, 경유 Node라면 원래 목적지까지 남은 경로를 더 진행하지 않는다.
- 종료 확정 또는 최종 도전 전환 결정 뒤에는 weight 0인 Edge·추가 Entrance 이동으로 일반 탐험을 연장하지 않는다. 최종 도전 중 시간 소진을 반복 판정해 중복 전환하지 않는다.

목적지·경유 여부와 Entrance 전환 한 번의 진행 문맥은 이동 처리에서 유지해야 한다. 중간 저장 요구 없이 이를 모두 영속 GameState 필드로 추가하지 않으며, 구체 실행 문맥은 이동 처리 설계에서 정한다.

### 6.6. 최종 도전과 영구 발견의 경계

특별 장소 발견·영구 지도·발견 원정대 기록·영구 해금 개념은 유지한다. 방문·후보 이력과 이번 런의 신규 발견, 원정 간 영구 기록을 같은 컬렉션으로 합치지 않는다. 새 성공·실패 결과에서 신규 발견을 보존·무효화하는 기준과 확정 시점은 미정이며, 시간 소진 전환만으로 기록을 지우거나 확정하지 않는다. 기존의 특별 장소 발견 후 자발적 종료·흰밀물 종료 계약을 그대로 구현하지 않는다. 관련 상태 필드와 영구 저장 형식은 별도 설계한다.

## 7. MercenaryState와 MercenaryInstance

### 7.1. 확정 규칙

- 직업 템플릿을 공유하더라도 각 용병은 독립적인 인스턴스다.
- 레벨·경험치는 파티가 공유하고, 전문화·성장 보상 선택과 장착 장비는 용병별로 구분한다. 미장착 장비는 파티 공용 인벤토리에 보관한다.
- 프로토타입 시작 레벨은 1, 최대 레벨은 5다. 전투 승리마다 파티 경험치 1을 지급하며, 최대 레벨 미만에서 다음 레벨에 필요한 경험치는 현재 레벨 L이다.
- 전투 참가 여부나 전투 불능 여부로 개인 레벨·경험치 차이를 만들지 않는다.
- 현재 HP는 전투 사이에 유지하고 자동 완전 회복하지 않는다. HP 0인 용병도 파티에 남으며 회복 전까지 다음 전투에 참여하지 못한다.
- 용병과 공유 성장 데이터는 원정 수명이며 다음 원정에 동일 용병을 유지하지 않는다.

### 7.2. MercenaryState — 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| Mercenaries | `List<MercenaryInstance>` | 보유 용병 목록. 표시·편성 순서를 유지 |
| Level | `int` | 공유 레벨 |
| Experience | `int` | 공유 경험치 |
| NextInstanceId | `int` | 다음 용병에게 부여할 원정 내 ID |

NextInstanceId는 1부터 증가시키고 원정 중 재사용하지 않는 안이다. 용병이 빠진 뒤 ID가 중복되지 않도록 목록 개수로 ID를 생성하지 않는다. 저장·복원을 도입하면 다음 ID 값과 기존 ID의 일관성도 유지해야 한다.

Experience의 타입은 정수로 제안하지만, 시작 경험치·누적 경험치와 현재 레벨 진행도 중 어떤 값을 저장할지·레벨업 후 차감·초과 경험치·최대 레벨 이후 처리는 미정이다. 시작 경험치 0을 확정값으로 취급하지 않는다.

### 7.3. MercenaryInstance — 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| InstanceId | `int` | 원정 안에서 고유한 용병 ID |
| Name | `string` | 표시 이름 |
| Class | `MercenaryClass` | 기존 직업 enum |
| CurrentHP | `int` | 전투 사이에도 유지하는 현재 HP |
| SpecializationId | `string?` | 선택한 전문화. 미선택이면 값 없음 |
| SelectedRewardIds | `Dictionary<string, string>` | 선택 보상 슬롯 ID → 선택한 보상 ID |

선택 보상 슬롯은 선택 기회 하나를 식별한다. 같은 레벨에 여러 선택 기회가 있더라도 구분할 수 있도록 슬롯 ID를 키로 두는 안이다. 슬롯의 구체 ID와 보상 데이터 계약은 미정이다. 전문화 선택은 SpecializationId에만 기록하고 SelectedRewardIds에 중복 기록하지 않는 안을 제안한다.

신규 기본 직업 기사는 Lv2에서 기어스·대응 특성 쌍을 선택하고, 위반하면 대응 특성을 영구 몰수하되 기본 Lv1 능력을 유지한다. 선택한 쌍과 몰수 여부를 구분할 수 있어야 한다. 기존 Class enum·SpecializationId·보상 기록이 기사 계약을 이미 지원한다고 해석하지 않으며 구체 ID·필드·위반 판정 및 영구 몰수의 런 간 범위는 미정이다. 검소의 맹세의 장비 2개 이하, 퇴마의 맹세의 마법사와 팀 구성 금지는 장비·파티 구성과 연결되는 제약이며 검사 시점·거부 또는 위반 처리 방식은 별도 설계한다.

장비는 용병당 최대 3개이며 부위별 슬롯을 나누지 않는다. 같은 종류와 완전히 동일한 장비의 중복 장착을 허용한다. 실제 장비의 보관·장착 위치와 선택한 한 개의 강화 상태를 구분할 수 있어야 하며, 정의 ID가 같다는 이유로 서로 다른 보유 장비를 하나로 합치지 않는다. 구체 식별자·참조 타입·저장 구조는 7.5절의 후속 계약으로 두며 기존 EquippedItemIds를 확정 스키마로 간주하지 않는다.

### 7.4. 계산하여 조회하는 정보 — 제안

| 조회 정보 | 반환 타입 | 계산 근거 |
| --- | --- | --- |
| SkillIds | `IReadOnlyCollection<string>` | 직업·공유 레벨·전문화·선택 보상 |
| TraitIds | `IReadOnlyCollection<string>` | 직업·공유 레벨·전문화·선택 보상 |
| MaxHP | `int` | 직업 기본값과 현재 성장·장비·파티 효과 중 적용 대상 |

현재 확정된 성장 경로로 복원할 수 있는 정보는 원본 선택 기록에서 계산하여 조회하고, 별도의 수정 가능한 최종 목록을 중복 소유하지 않는 방향이다. 기사의 몰수된 대응 특성은 원래 선택 기록만으로 다시 부여하지 않도록 몰수 상태를 조회에 반영해야 한다. 반환 인터페이스는 조회 형태의 제안이며 캐시·재계산 시점이나 매 조회 시 새 컬렉션을 생성하는 구현을 의미하지 않는다.

이벤트나 개별 고유 특성 등 현재 경로 밖의 획득을 허용하면 해당 획득 사실을 별도로 저장해야 한다. 현재 이벤트 조건·Result가 이미 개별 용병의 스킬·특성·HP 변경을 지원한다고 해석하지 않는다.

최종 능력치의 계산 순서·중첩·반올림, 생성 시 현재 HP, 최대 HP 변경 시 현재 HP 조정, HP 0인 용병의 일반 회복 허용 여부와 전투 결과 반영 인터페이스는 미정이다. 재계산 자체로 자동 회복·소생하거나 일회성 지급을 재실행하지 않는다.

### 7.5. 장비·강화·상점 재고 — 확정 요구사항과 후속 데이터 계약

장비 효과와 콘텐츠의 원본은 [MercenarySystem.md](MercenarySystem.md), 전투 중 효과 판정은 [BattleSystem.md](BattleSystem.md)를 따른다. 일반 5종과 고정 강화형 5종은 확정 콘텐츠이며, 이 절에서 아이템 ID·필드나 전투 계산을 새로 정하지 않는다.

**확정 규칙**

- 용병당 부위 구분 없이 최대 3개를 장착하며 동일 장비 3개도 허용한다. 장비를 바꿔도 직업의 기본 공격 방식과 무기 표현은 유지한다.
- 전투 중에는 장비를 변경할 수 없다. 전투 밖에서는 장소 제한 없이 장착·해제·파티원 간 교환이 가능하다. 미장착 장비의 파티 공용 보관 수량은 제한하지 않는다.
- 장비의 효과와 수치는 고정이며 무작위 옵션·수치를 사용하지 않는다. 방향별 물리 피해 차단은 수호자 Lv2 패시브로 얻고 일반 방패의 물리방어 +1과 구분한다. 정면 50%·측면 10%·후면 0%는 테스트 기준이며 최종 밸런스 값은 아니다.
- 일반 장비 하나는 정해진 특수 장비 하나로 한 번만 강화한다. 기존 능력치를 삭제하거나 낮추지 않으며 정해진 특수효과를 추가한다. 능력치 증가 자체를 금지하는 규칙은 아니다. 강화 결과의 선택 분기·무작위 결과를 사용하지 않는다.
- 강화는 기본적으로 이벤트에서 제공하며 플레이어가 장착·보관 중인 강화 가능한 장비 한 개를 직접 선택한다. 같은 장비가 여럿이어도 선택한 한 개만 바뀐다. 특수 장비를 보상으로 직접 얻을 수도 있으며, 강화로 얻었는지와 관계없이 특수 장비는 추가 강화할 수 없다.
- 장비를 상점에서 골드로 구매하고 보유 장비를 판매해 골드를 얻을 수 있다. 상점 재고는 유한하며 구매 수량만큼 감소한다. 해당 원정 동안 보충하지 않고 재방문해도 복구하지 않는다. 판매품의 재고 편입 여부는 별도 결정한다.
- 장착·보관 장비 모두 원정 종료 시 초기화한다. 특수 장비도 중복 장착과 원정 수명 규칙을 따르며 다음 원정으로 이월하지 않는다.

**상태와 책임의 경계**

- 공통 정의는 장비 종류·고정 효과·일반형과 강화형의 대응을 설명하고, 런타임은 실제 보유한 각 장비와 현재 보관·장착 위치를 구분해야 한다. 한 개를 강화·이동·판매할 때 같은 정의를 쓰는 다른 장비까지 변경하지 않는다. 인벤토리와 용병 장착 목록에서 같은 실물을 중복 소유한 것으로 계산하지 않는다.
- 일반/특수 구분과 개체 상태로 1회 강화 제한을 판정할 수 있어야 한다. 별도의 강화 횟수 필드를 반드시 추가할지, 정의 교체·상태 변경 중 어떻게 표현할지와 개체 식별자의 형식은 아직 정하지 않는다.
- 상점의 초기 판매 설정과 현재 남은 재고는 구분한다. 시설 UI를 다시 열거나 노드에 재진입해도 구매 결과가 유지되어야 한다. 재고의 생성 시점·ID·필드·가격·되사기·판매품 처리와 시작 장비 구성은 미정이다.
- 자비의 1·2·3개별 처형 기준과 복수의 장비별 개별 반격은 해당 장비의 고유 중첩 규칙이다. 다른 효과의 합산·곱연산·확률·횟수·상한까지 확정된 것으로 취급하지 않는다.
- 촛농 갑옷은 전투 시작 시 피해 1회 방어가 충전되고, 발동으로 소모한 뒤 착용자의 자기 턴 5회 기준으로 재충전한다. 추가 자기 턴도 세지만 별도 추가 턴 기술을 도입하지 않는다. 충전·소모·턴 카운트는 전투 실행 상태이며, 중복 장착 시 소모·개별 재충전과 턴 시작/종료·발동한 현재 턴 포함 여부는 미정이다. 단순 장비 조회나 시설 재방문을 임의의 재충전 계기로 추가하지 않는다.
- 강화 대상 선택·대상 없음·취소·비용·미리보기, 이벤트 결과·완료 수·소비·기록과의 적용 순서는 후속 계약이다. 현행 Event JSON이나 AppliedEventEffects가 장비 지급·강화·선택 개체 기록을 이미 지원한다고 해석하지 않는다.
- 갑옷 등의 체력 효과와 장착·해제·교환·강화에 따른 현재 HP 조정은 미정이다. 장비 변경을 자동 회복·소생으로 처리하거나 장비 정의의 체력 수치를 임의로 다른 스탯에 대응시키지 않는다.

원정 종료 시 필요한 기록을 값으로 복사한 뒤 장착·보관 장비를 정리한다. 진행 중 전투가 참조하는 원정 데이터를 먼저 폐기하지 않는 2절의 수명 원칙을 유지한다. 상점 상태를 새 원정에서 구성하는 구체 시점과 초기 재고는 별도 설계하며, 이전 원정의 소진 재고를 다음 원정의 초기 설정으로 임의 확정하지 않는다.

### 7.6. 궁수의 특수화살 제작과 전투 효과 — 후속 데이터 계약

궁수 Lv1 패시브는 전투 종료 후 전투에서 사용할 특수화살 1개를 제작한다. 긴 기본 공격 사거리는 직업 수치·공격 특성이다. 제작을 일으키는 종료 결과, 제작 대상 궁수의 조건, 화살의 종류·효과·사용 방식·소비·보유 한도·중복·저장 및 수명은 미정이다. 특수화살을 기존 장착 장비나 무제한 공용 인벤토리에 자동 편입하지 않으며 장비의 원정 종료 초기화 규칙을 화살에 그대로 적용한다고 확정하지 않는다. 제작의 반복 방지와 전투 종료·보상·원정 종료 사이의 순서는 후속 설계한다.

정령궁수 Lv2의 정령 부여는 다음 기본 공격 1회에 추가 효과를 붙이는 능력이며 Lv1에서 만든 특수화살과 동일한 개체·보유량·소비 규칙으로 취급하지 않는다. 정령 부여 준비, Lv5의 물리 피해 1회 무효화 충전·자기 턴 3회 재충전, 사용 턴의 무속성 범위 사격은 전투 실행 상태와 불변 정의를 구분해 설계한다. Hex별 독립 지면·공기 슬롯과 반응 상태도 전투 환경의 책임이며, 현행 GameState나 이벤트 JSON이 이를 이미 저장·변경한다고 해석하지 않는다. 구체 필드·소유자·저장·종료 처리는 상세 전투 명세의 확정·미정 범위에 맞춰 정한다.

## 8. BlessingState

### 8.1. 확정 규칙

- 축복은 파티 전체의 원정 단위 상태이며 신별 티어를 독립적으로 보유한다.
- 최초 획득은 1티어이고 다음 티어가 존재하면 획득 한 번에 한 단계 상승한다.
- 이전 지속 효과는 유지하고 새 단계의 효과를 추가한다. 단계별 일회성 효과는 해당 단계 도달 때 한 번만 실행한다.
- 축복 획득 완료 조건은 원정 동안 사용 완료로 기록하며 재사용하지 않는다. 태그는 획득 대가로 제거하지 않는다.
- 조건 하나의 OR 대안들을 각각 별도 획득 기회로 세지 않는다.
- 다음 원정에는 티어·지속 효과 적용 상태·조건 사용 기록을 초기화한다. 조건 기록 초기화 자체는 축복 지급이 아니다.

### 8.2. 필드·타입 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| TiersByGodId | `Dictionary<string, int>` | 신 ID별 현재 축복 티어 |
| UsedConditionIds | `HashSet<string>` | 이번 원정에서 사용 완료한 축복 조건 ID |

TiersByGodId에 없는 신은 미보유, 있는 신의 값은 1 이상으로 표현한다. 별도 보유 축복 목록을 중복 저장하지 않는다. 최고 티어는 신별 정적 정의에서 조회하는 방향이다.

지속 효과 중 티어에서 재구성할 수 있는 부분은 계산하는 안을 제안한다. 구체 효과가 별도 실행 상태를 필요로 하는지는 효과 설계 후 판단하며, 이 두 필드만으로 모든 미래 효과를 표현한다고 확정하지 않는다. 조회나 재계산이 과거 일회성 효과를 다시 실행해서는 안 된다.

신·조건 ID와 조건 식의 실제 데이터 구조, 최고 티어·충돌·제거 정책, 비선택·거절·중단 조건의 사용 기록, 동시 발생 처리, 원정 종료와 축복 후처리의 순서는 미정이다.

## 9. RunResult

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| Outcome | `RunOutcome` | 확정된 종료 결과 |
| SucceededGoalId | `string?` | 성공한 Goal ID |

RunResult는 `readonly struct`로 제안하며 GameState는 `RunResult?`로 보유한다.

- 최종 도전 진행 중을 포함해 종료 전에는 RunResult가 없다. 실제 종료 결과 확정과 RunPhase의 Ended 전환을 함께 처리한다.
- GoalSuccess는 왕의 길잡이 실제 획득이 확인되고 결과 처리가 끝난 성공이며 SucceededGoalId가 반드시 있다. BattleDefeat이면 없다. 도전 진입·단순 도착·목격·전투 승리를 성공으로 대신하지 않는다.
- 현재 상태의 마지막 위치는 ExplorationState.CurrentLocation에서 조회한다. 종료 기록을 만들 때 값을 복사한다.
- RunPhase는 진행 단계, RunResult는 종료 사유다. 시간 소진과 RemainingEventIds 고갈로 종료 결과를 만들지 않는다. 시간 소진은 같은 원정의 최종 도전 진입 계기로 관리한다.

최종 도전의 진입 계기·실제 획득 확인·기타 실패 결과·복귀 문맥을 표현하는 필드와 기존 TimeExpired의 이행은 미정이다. 이미 확정된 성공·전투 패배는 시간 소진으로 덮어쓰지 않는다. nullable 값 타입과 성공 Goal ID의 저장 방식은 제안이다.

## 10. Chronicle과 기록 타입

### 10.1. 확정 규칙

- 실제 발생한 이벤트, 선택한 Choice ID와 적용된 결과를 순서대로 기록한다.
- Automatic 이벤트의 Choice ID는 `auto`다.
- 전투 패배 사실을 기록할 수 있지만 패배 때문에 적용되지 않은 후속 효과를 적용된 결과로 기록하지 않는다.
- 원정 종료 시 종료 결과, 성공한 Goal 또는 마지막 위치, Fame·Reputation, Arc 최종 상태와 주요 태그를 기록한다.
- 원정 종료 때문에 미완료 Arc 상태를 변경하지 않는다.

### 10.2. ChronicleEntry — 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| EventId | `string` | 발생한 이벤트 ID |
| ChoiceId | `string` | 선택한 선택지 ID 또는 auto |
| Location | `LocationKey` | 사건 발생 위치 |
| BattleOutcome | `EventBattleOutcome?` | 전투가 없으면 값 없음 |
| AppliedEffects | `AppliedEventEffects` | 실제로 적용한 이벤트 효과 기록 |

사건의 결과가 결정된 뒤 항목을 추가하고 추가 후 수정하지 않는 안이다. 진행 중 전투나 선택 UI 상태는 이 기록으로 표현하지 않는다.

### 10.3. AppliedEventEffects — 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| AddedTags | `string[]` | 실제 새로 추가된 태그 |
| RemovedTags | `string[]` | 실제 제거된 태그 |
| FameChange | `int` | 범위 제한 후 실제 명성 변화량 |
| ReputationChange | `int` | 범위 제한 후 실제 평판 변화량 |
| MoneyChange | `int` | 실제 골드 변화량 |
| RevealedGoalIds | `string[]` | 이번 결과로 새로 공개된 목표 |
| ArcChange | `ArcChangeRecord?` | 실제 적용된 Arc 전이. 없으면 값 없음 |

요청된 효과와 실제 변화량을 구분한다. Fame 9에서 +3 효과를 적용하여 10이 되면 기록할 변화량은 +1이다. 이미 있던 태그·공개 목표와 제거 대상이 없었던 태그를 새 변화로 기록하지 않는다. 전투 패배로 후속 효과를 적용하지 않았다면 배열은 비어 있고 변화량은 0이며 ArcChange는 없다.

### 10.4. ArcChangeRecord — 제안

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| ArcId | `string` | 변경된 Arc ID |
| Before | `ArcState` | 전이 전 상태의 값 |
| After | `ArcState` | 전이 후 상태의 값 |

연대기의 배열과 기록 객체는 현재 GameState의 가변 컬렉션을 공유하지 않고 값으로 복사한다. 종료 시 필요한 최종 값도 복사하여 원정 객체가 폐기된 뒤 기록이 바뀌지 않도록 한다.

이 기록 형식은 현재 명세의 사건 연대기를 위한 제안이다. 전투·시설·성장 등을 포함한 모든 상태 변화를 재생하여 GameState를 복원하는 이벤트 로그를 보장하지 않는다. 종료 요약의 실제 저장 형식과 콘텐츠 개정 이후 표시 방식도 별도 결정한다.

## 11. 초기화와 변경 흐름

### 런 시작 — 확정 규칙을 필드 제안에 대응

1. 유효한 시작 위치와 초기 원정 설정을 결정하고 하위 State·컬렉션을 생성한다.
2. 단일 최종 목표를 설정하고 정보를 안내한다. FinalGoalId와 현행 RevealedGoalIds의 연결은 제안·이행 계약에 맞춰 처리하며 여러 최종 목표를 추가하지 않는다.
3. 이번 런의 Arc·일반 Standalone Event와 Opening Event 하나를 선정한다.
4. 선정된 정규 이벤트 전체로 RemainingEventIds를 초기화한다.
5. 장소 조건으로 PotentialEventIdsByLocation을 구성한다. 초기 동적 조건으로 제외하지 않는다.
6. 선정된 Arc의 상태를 Pending과 초기 Stage로 설정하고 ResolvedEventCount를 0으로 설정한다.
7. 방문·과거 유효 후보 이력을 비우고 이번 원정의 용병·공유 성장·장비 보관·장착·축복 상태를 구성한다. 이전 원정의 장비를 이월하지 않는다. 시작 장비·상점 재고의 생성 시점과 초기값은 별도 계약을 따르며 미정 수치를 임의 확정하지 않는다.
8. RunPhase를 Opening, RunResult를 값 없음으로 설정한다.
9. 시작 Node의 방문을 기록하고 Opening을 처리한다. 최초 정규 후보 이력은 비워 두며 Opening 결과로 열린 후보도 미리 기록하지 않는다.

### 정규 이벤트 정상 완료

EventSystem의 순서에 따라 전투가 있으면 먼저 처리하고, 승리 또는 비전투 결과에서 Tags·Fame·Reputation·Money, Arc 전이, 목표 공개를 적용한다. ResolvedEventCount를 증가시키고 RemainingEventIds에서 해당 정규 이벤트 ID를 제거한 뒤 연대기를 기록한다. 위치별 잠재 배열은 유지한다.

전투 패배면 후속 효과를 적용하지 않고 BattleDefeat로 종료한다. 최종 콘텐츠에서 실제 길잡이 획득을 확인해 결과 처리를 마치면 GoalSuccess로 종료한다. 획득 확인의 구체 데이터 계약은 미정이다. Opening·최종 도전은 특수 규칙을 따르고, 아직 일반 탐험 중이면 Edge 도착 범위의 이벤트·전투·보상·결과를 모두 마친 뒤 시간을 검사한다. 소진 시 종료 결과 없이 같은 원정의 최종 도전으로 전환한다. 축복 후처리를 평가·지급하는 정확한 시점은 BlessingSystem의 미정 사항이다.

장비 강화 기회·특수 장비 보상은 확정된 요구사항이지만 위 현행 Result 순서에 바로 실행할 필드가 정의되어 있지는 않다. 개별 대상 선택과 장비 상태 변경, 이벤트의 정상 완료·소비·연대기 기록을 연결하는 계약은 EventSystem의 후속 명세에서 정한다. 장비 선택 UI를 열었다는 이유만으로 이벤트를 정상 완료하거나 장비를 지급·강화한 것으로 기록하지 않는다.

## 12. 남은 결정 사항과 구현 시 확인 항목

### 미정 사항

- LocationKey 채택과 Area·Node ID 체계, 기존 Locations·이벤트·Goal 참조의 연결 방식
- 후보 이력 갱신 시점 제안의 채택과 진입 처리의 중복 실행 방지 경계
- 복수 유효 후보의 선택 알고리즘과 콘텐츠 배치·우선순위
- 총 탐험 준비 시간, 남은 시간보다 비싼 이동의 허용·차감 정책, 이미 서 있는 Entrance 재선택·복귀 조작
- 단일 최종 목표 ID와 현행 Goal 공개 필드의 연결, 실제 길잡이 획득 확인과 성공 처리 계약
- 최종 도전의 강제 이동·목표 이벤트 발생 중 방식, 상태·중복 진입 방지·접근 UI·이동 비용·복귀·기타 실패 후 처리와 흰밀물의 연결
- 새 종료 결과에서 신규 발견의 영구 보존·무효화 기준과 확정 시점, TimeExpired 저장값·코드의 이행
- 용병 생성 시 HP, 경험치 표현·초기값·레벨업 후 처리, 중도 영입 보상과 성장 보상 적용 시점
- 스킬·특성·전문화·선택 보상 슬롯의 정적 스키마와 현재 성장 경로 밖의 획득 기록
- 장비 개체·보관·장착·강화와 상점 재고의 ID·필드·소유권·저장 구조. 부위 구분 없는 최대 3개 장착·중복 허용·공용 무제한 보관·원정 수명은 확정
- 장비의 일반 중첩 계산과 최종 능력치 계산·캐시·현재 HP 조정, 장비 효과의 전투 임시 상태와 입출력 계약
- 강화 대상 선택·대상 없음·취소·미리보기·비용 및 이벤트 결과 적용·완료·소비·기록 순서
- 시작 장비 구성, 상점별 초기 재고·생성 시점·가격·되사기·판매품 재고 편입 및 특수 장비 판매 여부
- 전투와 원정 상태 사이의 입력·결과 전달 및 결과 반영 순서
- 축복 ID·조건·효과의 구체 스키마와 동시 획득·거절·중단·종료 처리
- 원정 간 영구 기록과 저장·로드 형식, 중간 이동·이벤트·전투에서 저장할지 여부

### 구현 시 확인 항목

- 빈 잠재 목록·빈 유효 후보·빈 정규 풀을 정상적으로 처리하는가
- 노드별 잠재 목록에 중복 ID가 없고 실제 선정된 정규 이벤트만 연결되는가
- 초기 조건이 맞지 않는 Arc 후속 이벤트도 위치상 가능한 목록에 포함되는가
- 한 Node의 정상 완료가 같은 이벤트를 참조하는 다른 모든 Node에 반영되는가
- 미선택 후보는 그 Node의 과거 이력에만 남고 런 공통으로 소비되지 않는가
- 같은 진입의 Result가 새로 연 후보를 과거 이력에 미리 넣거나 즉시 실행하지 않는가
- Opening 최초 방문·최종 도전의 특수 처리와 Entrance 양쪽 방문의 순서가 유지되는가
- 마지막 방문의 이벤트·전투·보상·결과 뒤 최종 도전으로 전환하며 이미 확정된 성공·패배를 덮어쓰지 않는가
- 시간 소진만으로 RunResult를 만들거나 최종 도전 진입 시 같은 원정의 상태를 초기화하지 않는가
- 최종 도전 중 시간 소진 재판정·중복 진입·0비용 일반 탐험으로 진행 규칙을 우회하지 않는가
- 단순 도착·목격·전투 승리를 보물 획득 성공으로 잘못 기록하지 않는가
- 동일 장비 3개와 무제한 공용 보관을 표현하며 부위별 슬롯이나 종류 제한을 추가하지 않는가
- 장비 한 개의 장착·해제·교환·강화·판매가 같은 정의를 사용하는 다른 실물까지 변경하지 않는가
- 전투 중 장비 변경을 막고 전투 밖에서는 장소 제한을 추가하지 않는가
- 강화 가능한 실제 장비 하나만 바뀌고 특수 장비를 다시 강화하지 않는가
- 상점 재방문·시설 UI 재개방·최종 도전 진입으로 소진 재고나 장비가 초기화되지 않는가
- 자비·복수의 고유 중첩과 촛농 갑옷의 착용자 턴 기준을 지키며 미정인 충전 시점·중복 처리를 임의 확정하지 않는가
- 종료 기록에 필요한 값을 보존한 뒤 장착·보관 장비를 정리하고 다음 원정에 이월하지 않는가
- HP 0인 용병과 전장에서 제거된 참가자의 결과가 원정 데이터에서 누락되지 않는가
- 기록이 현재 상태의 가변 참조를 공유하지 않으며 범위 제한 후 실제 변화량을 보존하는가

본 문서는 문서 설계만 다룬다. 코드·테스트·Scene 구현 및 컴파일·빌드는 별도 요청 범위다.
