# 탐험·캐릭터·이벤트 통합 구현 계획

> 작성 기준: 2026-10-20  
> 문서 성격: **구현 로드맵 제안**. 기존 기획 문서의 미정 사항을 임의로 확정하지 않는다.  
> 개발 방향: **전투는 별도로 개발하고, 탐험·캐릭터·성장·이벤트를 먼저 플레이 가능한 형태로 완성한 뒤 연결한다.**

## 1. 목표

월드맵을 돌아다니며 모험가를 영입하고 성장시키고, 선택에 따라 다른 장소와 사건이 달라지는 탐험 RPG의 핵심 루프를 검증한다.

**첫 통합 플레이 목표**

`주점에서 파티 구성 → 월드맵 이동 → 이벤트 선택 → State 변경 → 다른 장소에서 변경된 세계 확인 → 모험가 성장 → 목표 장소 발견 또는 흰밀물 종료`

전투는 처음에는 **모의 승리/패배 결과**로 대체한다. 실제 턴제 전투는 마지막 단계에서 연결한다.

## 2. 반드시 유지할 기존 원칙

- **고정된 월드 그래프:** Location의 위치와 지리적 연결은 고정한다. 한 런에서 발생하는 사건과 플레이어가 아는 정보, 장소의 표현은 달라질 수 있다.
- **원정 시간:** 노드 간 이동에서만 소비한다. 이벤트·전투·대화·휴식·거래·성장 처리에는 별도 원정 시간을 소모하지 않는다.
- **원정 목표:** 먼 목표 Location 중 하나의 Goal Event를 성공적으로 처리하면 성공. 탐험 기간 소진과 전투 패배는 별도의 종료 사유다.
- **정적 이벤트:** 이벤트는 개발 중 JSON으로 제작한다. 런타임에 LLM을 사용하지 않는다.
- **State 기반 연결:** 이벤트는 다음 Event ID를 직접 가리키지 않고 `State / Tags / Arc Stage`에 따라 활성화된다.
- **첫 방문과 재방문:** 일반 Location 첫 방문에는 이벤트가 반드시 하나 발생한다. 재방문 시에는 `NewEntryEdge` 또는 `NewCondition` 등의 새로운 탐험 계기가 있을 때에만 새 정규 이벤트를 허용한다.
- **책임 분리:** 이벤트 생성기는 서사·조건·결과를 기술하고, Unity 런타임은 이동·시간·이벤트 선택·원정 종료를 관리한다.
- **전투 기준:** `Plan.md`의 오래된 오토배틀러 설명보다 최신 `BattleSystem.md`의 **헥스 기반 턴제 전투 구현/기획**을 우선 확인한다. 전투를 이 계획에서 다시 설계하지 않는다.

## 3. 첫 검증 콘텐츠 범위

- **Location:** 연결과 되돌아가기가 가능한 소규모 지역 8~12개(임시 범위).
- **Goal:** 서로 다른 방향에 있는 목표 장소 2개.
- **이벤트:** 첫 방문을 보장할 기본 사건과 State에 따라 열리는 조건부 사건 소수.
- **상태 변화 사례:** 한 장소의 선택이 다른 장소의 사건 및 지도 표시를 바꾸는 사례 최소 1개.
- **캐릭터:** 전사·도적·궁수 3직업을 우선 사용하고, 각 직업의 초기 2~3레벨 보상으로 검증한다. 이는 최종 직업 수나 레벨 상한이 아니다.
- **Arc:** 독립 이벤트 루프가 동작한 뒤 짧은 선택적 Arc 1개를 추가할 수 있다.
- **전투:** 임시 결과 반환으로 대체. 실제 전투 자산과 스킬 동작은 불필요.

예시: 상류 수문을 수리하면 `sluice_repaired` Fact가 남고, 하류 마을의 설명/아이콘과 이후 발생 가능한 이벤트가 달라진다. 이것은 **콘텐츠 예시**이지 확정 월드 설정이 아니다.

## 4. 구현 단계와 완료 기준

### M1. 월드맵·이동

**구현**
- 월드맵 일러스트 위에 Location 노드와 연결선 표시.
- `WorldGraph`에 Location ID, Edge, 이동 시간 데이터 관리.
- 클릭으로 이동, 연결 조건 검사, 경로 선택 및 역행.
- 현재 위치와 남은 원정 시간 표시; 이동 시에만 시간 차감.

**완료:** 플레이어가 갈림길에서 경로를 고르고, 같은 길을 되돌아오며, 이동 비용을 확인할 수 있다.

### M2. 캐릭터·파티 데이터

**구현**
- `CharacterDefinition`: 직업 및 기본 능력 등 정적 정의.
- `CharacterInstance`: 개별 모험가의 직업·레벨·습득 능력·장비 등 변화하는 정보.
- `PartyState`: 현재 동료 목록과 파티 편성 관리.
- 주점 영입 및 골드 지출, 캐릭터 상세 화면.
- 데이터의 생성·조회·변경 로직을 Unity View와 분리.

**완료:** 서로 다른 직업의 동료를 영입하고 개별 정보를 확인·관리할 수 있다. 전투 화면은 필요 없다.

### M3. 성장 시스템

**구현**
- 직업별 고정 레벨 보상 / 직업 내 선택 보상 / 공용 특성 데이터.
- 레벨업 시 해당 보상 부여 및 선택 결과 저장.
- 스킬·특성의 **보유 데이터**와 전투에서의 **실행 로직** 분리.
- 장비의 보유·장착 구조는 확장 가능하게 설계하되, 미정인 아이템 효과와 수치를 임의 확정하지 않는다.
- 실제 경험치 획득 조건이 정해지기 전에는 디버그 명령이나 시험용 보상으로 레벨업 테스트.

**완료:** 전투 없이도 레벨업·선택·습득 내역 및 캐릭터 정보 변화가 일관되게 유지된다.

### M4. 이벤트 런타임

**구현**
- 기존 `EventSystem.md`의 JSON·Catalog·참조 데이터 검증 및 로딩.
- `RunState`(Fame, Reputation, Money, Tags, ArcStates, RevealedGoalIds 등) 관리.
- `ExplorationRuntimeState`(방문 기록, 진입 경로, 후보 기록, 남은 시간) 별도 관리.
- Opening, Standalone, 선택지/결과 처리부터 시작해 Arc와 Goal 연동의 기반 마련.
- 첫 방문 보장, 새로운 진입 경로/조건으로 발생하는 재방문 이벤트, 반복 지급 방지.
- 전투 Result는 임시 승리·패배 반환으로 검증.

**완료:** 이벤트 선택에 따라 State가 변하고, 다음 방문의 이벤트 후보가 그 상태에 맞게 달라진다.

**주의:** 현재 Event Result는 경험치·영입·장비 지급을 직접 지원하지 않는다. 그런 기능을 사용할 때는 `EventSystem.md`의 Effect 계약을 **명시적으로 확장**한다. 임의 필드를 먼저 추가하지 않는다.

### M5. State에 반응하는 세계

**구현**
- State / Tags를 읽어 장소 설명, 상태 아이콘, 국소적인 월드맵 표시를 결정하는 표현 계층(예: `WorldPresentationResolver`).
- 동일한 장소라도 과거 선택에 따라 다른 표현을 제공.
- 변화된 조건으로 새 이벤트가 활성화된 경우, 기존 재방문 규칙에 따라 판정.
- 최초에는 맵 전체 교체, 대규모 지형 변형, 동적 Edge 생성은 구현하지 않는다.

**완료:** A 장소의 선택을 마친 뒤 B 장소로 이동해 사건과 시각적 표현의 차이를 실제로 확인할 수 있다.

### M6. 원정의 시작과 끝

**구현**
- Opening 후 초기 Goal 공개, 경로 중 새 Goal 공개.
- Goal Event 우선 처리와 `GoalSuccess`.
- 도착 이벤트를 모두 처리한 **뒤** 시간 소진을 확인하는 `TimeExpired`.
- 모의 전투 패배의 `BattleDefeat`.
- 연대기 및 기본 원정 결과 표시.

**완료:** 실제 전투 없이도 목표 발견 성공 / 흰밀물 종료 / 모의 전투 패배로 끝나는 전체 원정을 플레이할 수 있다.

### M7. 실제 전투 통합

**구현**
- 기존 규칙대로 `(Event ID, Choice ID)`에 제작한 전투 데이터 연결.
- 파티의 캐릭터 데이터를 전투 시작용 데이터로 변환하여 전달.
- 전투 시스템은 턴·AP·이동·공격·스킬 효과를 처리하고, 종료 결과를 반환.
- 승리 시 이벤트 Result Effect를 적용; 패배 시 후속 Effect 없이 원정 종료.
- 파티 체력·장비·성장 상태 등 전투 전후 무엇을 유지할지는 별도의 계약으로 정한다.

**완료:** 같은 이벤트 루프가 모의 전투 대신 실제 전투를 호출하고, 결과가 원정에 정상 반영된다.

## 5. 아키텍처 원칙

```text
정적 데이터
├─ WorldGraph / Locations
├─ Character & Class Definitions / Level Rewards
└─ Events / Arc Catalog / Goal Catalog

원정 로직 (순수 C# 우선)
├─ Exploration / Expedition Time
├─ RunState / ExplorationRuntimeState
├─ CharacterInstance / PartyState / Growth
├─ EventResolver / ResultApplier
└─ WorldPresentationResolver (표현에 필요한 상태 산출)

Unity View
├─ World Map / Location UI
├─ Event UI
└─ Party / Level-up UI

추후 연결
└─ Battle Adapter → 기존 턴제 Combat → Battle Outcome
```

- `CharacterDefinition`은 직업·성장 규칙을 담고, `CharacterInstance`는 개별 모험가의 변화하는 상태를 담는다.
- 모험가의 **공용 전투 특성**과 이벤트의 파티 서사 태그 `Trait`은 서로 다른 데이터다.
- 캐릭터·파티 데이터는 전투 시스템의 소유물이 아니다. 전투는 필요한 데이터를 전달받아 실행한다.
- 기존 `RunState`에 없는 파티·성장 필드를 무조건 섞지 않는다. 이벤트 조건이나 Result에서 필요해지는 시점에 시스템 간 참조 계약을 정한다.
- 구현은 순수 C# 상태 전이와 테스트를 우선하고, Unity View는 이를 표시한다.

## 6. 구현 전에 정해야 할 것과 미뤄도 되는 것

**각 기능에 착수할 때 정할 항목**
- M1: 첫 그래프 구성, 이동 비용과 잔여 시간 부족 시 이동 허용 정책(임시 밸런스와 최종 규칙 구별).
- M2: 캐릭터 ID·정의/인스턴스 경계, 파티 인원 관리 정책. 현재 전투 프로토타입의 인원 제한과 전체 기획의 상한 차이는 통합 전에 확인.
- M3: 레벨업 조건(경험치 사용 여부 포함), 레벨 보상 지급 시점, 장비 규칙의 첫 검증 범위.
- M4~M5: 캐릭터 성장/영입 보상을 Event Effect로 줄 필요가 있는지, 특정 직업이나 파티 구성을 이벤트 조건에서 참조할지.
- M6: 미공개 Goal의 선방문 처리 등 Goal의 남은 경계 조건.
- M7: 전투 시작·종료 데이터, 피해·사망과 원정 간 캐릭터 상태 유지 범위.

**최초 프로토타입에서 보류**
- 모든 직업의 전체 스킬·특성·장비 콘텐츠 완성 및 전투 밸런스.
- 월드 전체 규모의 반응형 변화와 동적 지리 구조.
- 반복 원정 사이 세계 기록/캐릭터 성장 유지 방식의 최종 확정.
- 축복 시스템의 실제 효과와 전투 적용. 축복의 별도 규칙은 `BlessingSystem.md`를 유지하며 이후 통합한다.
- 원정 성공 이후 자유 탐사 등 선택적 기능.

## 7. 가장 먼저 수행할 작업

1. **작은 테스트 지역의 월드 그래프**를 작성한다. Location 8~12개, Goal 2개, 분기·되돌아갈 길을 포함한다.
2. **한 장소에서의 선택이 다른 장소를 바꾸는 시나리오 하나**를 작성한다. 필요한 Fact와 기본/조건부 이벤트를 식별한다.
3. 그 시나리오를 목표로 M1부터 순서대로 구현한다. 완성형 콘텐츠 대신 최소 테스트 데이터로 검증한다.

**프로토타입 성공 기준:** 플레이어가 파티를 꾸리고 경로를 선택해 사건을 해결하며, 자신의 과거 선택이 다른 장소에 남아 있음을 확인하고, 성장과 목표 발견 또는 흰밀물 종료까지 경험한다. 이 전체 흐름은 실제 전투 구현 없이 먼저 작동해야 한다.

## 8. 새 세션에서의 작업 지침

- 먼저 `World_Premise.md`, `WorldLore.md`, `Plan.md`, `EventSystem.md`, `BattleSystem.md`, `BlessingSystem.md`를 확인하고, 이 계획과의 충돌·미정 사항을 구분한다.
- 각 단계에 착수할 때는 **구현 범위 → 필요한 데이터 계약 → 테스트 기준 → 구현 순서**를 먼저 정리한다.
- 기존 명세의 확정 규칙을 변경해야 한다면 해당 문서를 별도로 수정한다. 이 로드맵 자체를 확정된 시스템 명세로 간주하지 않는다.
- 매 단계의 구현과 검증을 끝낸 후 다음 단계로 진행한다. 전투 시스템 개발은 별도 흐름으로 병행할 수 있다.
