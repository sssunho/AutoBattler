# 탐험·캐릭터·이벤트 통합 구현 계획

> 작성 기준: 2026-11-07  
> 문서 성격: **구현 로드맵 제안**. 기존 기획 문서의 미정 사항을 임의로 확정하지 않는다.  
> 개발 방향: **전투는 별도로 개발하고, 탐험·캐릭터·성장·이벤트를 먼저 플레이 가능한 형태로 완성한 뒤 연결한다.**

## 1. 목표

Area 안의 노드를 자유롭게 탐색하고 Entrance로 다른 Area에 진입하며, 전투와 파티 성장으로 왕의 길잡이 획득을 준비하는 모험의 흐름을 검증한다. 최소 3개 스토리라인은 콘텐츠 목표이며 즉시 구현 범위가 아니다. 이야기를 별도의 일방통행 이동 루트로 고정하지 않는다.

**첫 통합 플레이 목표**

`주점에서 파티 구성 → 현재 Area 이동·Entrance 전환 → 사건과 전투 결과 처리 → State 변경과 파티 성장 → 자율 도전 또는 시간 소진 후 최종 도전 → 길잡이 획득 성공 또는 전투 패배`

전투는 처음에는 **모의 승리/패배 결과**로 대체한다. 실제 턴제 전투는 마지막 단계에서 연결한다. 이는 상태·진행 흐름의 통합 검증이며 전체 게임의 재미 검증과는 구분한다. 사건 길이·빈도 축소나 새 구현 일정은 이번 결정으로 확정하지 않는다.

## 2. 반드시 유지할 기존 원칙

- **공간과 이동:** Node는 공간 단위 Area에 소속되며 Area가 노드들을 소유한다. Area 자체는 Node가 아니고 World/Local 노드 구분은 사용하지 않는다. 같은 Area 안에서도 명시적인 Edge와 통행 조건을 따르며, 다른 Area의 노드는 일반 경로로 연결하지 않는다. 게임에는 현재 Area의 노드만 표시하고 목적지도 그 안에서 선택한다.
- **Entrance 전환:** 목적지 Entrance의 방문·이벤트 결과를 처리하고, 종료되지 않고 일반 탐험이 계속되면 비용 0으로 다른 Area의 지정 노드에 한 번 전환한 뒤 도착지를 처리한다. 최종 도전 진행 중에는 일반 Area 전환을 실행하지 않는다. 전환 도착으로 자동 재발동하지 않으며 경유 Entrance는 전환만 생략하고 방문·이벤트 판정을 유지한다.
- **원정 시간:** 이동한 Edge의 `weight`가 시간 비용이다. `weight = 0`인 연결도 허용하며 기존 내부 이동은 이 방식으로 표현한다. 같은 Area 안의 모든 Edge가 무료라는 뜻은 아니다. 이벤트·전투·대화·휴식·거래·성장 처리에는 별도 원정 시간을 소모하지 않는다.
- **원정 목표:** 최종 목표 장소는 하나다. 최종 난관을 넘어 왕의 길잡이를 획득하면 성공하며 도착·목격·전투 승리만으로 자동 성공시키지 않는다. 제한 전 언제든 자율적으로 도전할 수 있고 조기 도전의 별도 보상은 없다. 시간 소진은 해당 도착 범위의 이벤트·전투·보상·결과를 모두 처리한 뒤 최종 도전으로 전환하는 계기다. 이미 확정된 성공·전투 패배를 뒤집지 않으며 귀환·납품·즉위·통치의 후속 플레이는 추가하지 않는다.
- **정적 이벤트:** 이벤트는 개발 중 JSON으로 제작한다. 런타임에 LLM을 사용하지 않는다.
- **State 기반 연결:** 이벤트는 다음 Event ID를 직접 가리키지 않고 `State / Tags / Arc Stage`에 따라 활성화된다.
- **첫 방문과 재방문:** Node 첫 방문에 유효한 정규 후보가 없으면 이벤트 없이 정상 방문한다. 재방문은 과거 탐험 기회에서 후보가 아니었다가 조건에 따라 새로 유효해진 후보가 있을 때만 새 기회가 생긴다. 유효한 기회에 후보가 있으면 별도 무이벤트 확률 판정 없이 정규 이벤트 1개를 처리하며, 한 번의 진입에서 최대 1개만 실행한다.
- **책임 분리:** 이벤트 생성기는 일러스트·본문·선택지 또는 자동 결과·결과 문구·Effect로 표현하는 서사 사건의 조건과 결과를 기술하고, Unity 런타임은 이동·시간·이벤트 선택·원정 종료를 관리한다. 상점·영입 등 일반 시설 이용과 상호작용은 별도 시스템·UI가 담당한다.
- **전투 기준:** `BattleSystem.md`의 헥스 턴제 전투 구현·기획을 확인한다. 공통 은신·투명화와 도적 전문화의 문서 반영을 구현 완료로 해석하지 않으며 전투를 이 계획에서 다시 설계하지 않는다.
- **장비:** 용병당 최대 3개, 부위 슬롯 없음, 동일 종류·동일 장비 중복 허용과 직업 기본 공격·무기 표현 유지를 따른다. 전투 중 변경은 막고 전투 밖에서 장소 제한 없이 장착·해제·교환한다. 보관은 무제한 파티 공용이며 장착·보관 장비는 원정 종료 시 초기화한다.
- **거래·강화:** 골드로 장비 구매·판매를 지원하고 유한 재고는 구매량만큼 감소하며 원정 중 보충하지 않는다. 일반 장비는 선택한 한 개만 고정 특수 장비로 한 번 강화하고, 직접 보상으로 얻은 특수 장비도 재강화하지 않는다. 방향별 물리 피해 차단은 수호자 Lv2 패시브이며 일반 방패의 물리방어 +1과 구분한다.
- **기사와 기어스:** 신규 기본 직업 기사와 Lv2 기어스·대응 특성, 위반 시 대응 특성 영구 몰수 및 Lv1 능력 유지를 상세 명세에 따라 연결한다. 검소의 맹세는 장비 2개 이하를 요구한다. 구체 위반 판정·저장 구조·몰수의 런 간 범위는 미정이며 이 결정만으로 최초 검증 편성을 확대하지 않는다.

## 3. 첫 검증 콘텐츠 범위

- **Location:** 연결과 되돌아가기가 가능한 소규모 지역 8~12개(임시 범위).
- **Area 이동:** 현재 Area만 표시·이동 대상으로 삼는 규칙, Entrance의 목적지 도착과 경유 차이, 전환 재발동 방지 및 weight가 0인 내부 연결을 검증한다. 구체적인 Area 구성은 M1 착수 시 정한다.
- **Goal:** 최종 목표 장소 1개. 자율 도전과 시간 소진 후 도전 모두 같은 목표의 획득 결말로 연결한다. 강제 전환의 실제 방식은 착수 전에 정한다.
- **이벤트:** 이벤트가 있는 노드와 없는 노드, State에 따라 재방문 시 새 사건이 열리는 장소를 검증할 사건 소수.
- **상태 변화 사례:** 한 장소의 선택이 다른 장소의 사건 및 지도 표시를 바꾸는 사례 최소 1개.
- **캐릭터:** 전사·도적·궁수 3직업을 우선 사용하고, 각 직업의 초기 2~3레벨 보상으로 검증한다. 이는 최종 직업 수나 레벨 상한이 아니다.
- **Arc:** 독립 이벤트 루프가 동작한 뒤 짧은 선택적 Arc 1개를 추가할 수 있다.
- **전투:** 임시 결과 반환으로 대체. 실제 전투 자산과 스킬 동작은 불필요.

예시: 상류 수문을 수리하면 `sluice_repaired` Fact가 남고, 하류 마을의 설명/아이콘과 이후 발생 가능한 이벤트가 달라진다. 이것은 **콘텐츠 예시**이지 확정 월드 설정이 아니다.

## 4. 구현 단계와 완료 기준

### M1. Area 지도·이동

**구현**
- Area가 소유하는 Node와 Edge를 관리하고, 화면에는 현재 Area의 노드만 표시.
- 같은 Area의 명시적인 연결 관계와 통행 조건을 검사하여 경로 선택·이동·역행 처리. 다른 Area의 노드는 직접 목적지로 선택하지 않음.
- 이동한 각 Edge의 weight만큼 원정 시간을 차감. weight가 0인 내부 연결과 비용이 있는 연결을 모두 지원.
- Entrance를 지정 목적지로 선택해 도착하면 입구 처리를 마치고 일반 탐험이 계속될 때 비용 0으로 한 번 전환하여 표시 Area를 변경한 뒤 도착지 처리. 최종 도전 중에는 일반 전환하지 않으며 전환 도착지가 Entrance여도 자동 재발동하지 않음. 이벤트·종료 처리는 M4·M6과 연결.
- 경유 Entrance는 전환만 생략. 경유 노드의 이벤트로 잠시 멈춘 경우에도 그 노드를 선택 목적지로 바꾸지 않음.
- 현재 위치와 남은 원정 시간을 표시하고, 지도 UI를 열고 닫는 조작을 실제 진입으로 처리하지 않음.
- Area·Node·Edge·Entrance 목적지 데이터와 이미 서 있는 Entrance의 재선택·복귀 조작은 착수 전에 구체 계약을 정함.

**완료:** 현재 Area 밖의 노드를 표시하거나 직접 선택할 수 없고, Entrance를 지정 목적지로 삼았을 때만 Area가 전환된다. 같은 Entrance를 경유하면 전환 없이 이동하며, 전환 도착으로 자동 왕복하지 않는다. 시간 비용은 실제 이동한 Edge의 weight에 맞고 이벤트 없는 노드도 정상 방문한다.

### M2. 캐릭터·파티 데이터

**구현**
- 직업 및 기본 능력 등 정적 정의는 `MercenarySystem.md`를 따른다.
- 개별 용병의 HP·전문화·성장 선택·장비와 파티 공유 레벨·경험치를 분리한다.
- 상태 소유권과 `MercenaryState`·`MercenaryInstance` 필드 제안은 `GameState.md`를 따른다. 별도 상태 원본을 중복 추가하지 않는다.
- 주점 영입 및 골드 지출, 캐릭터 상세 화면.
- 용병별 최대 3개 장착과 파티 공용 보관, 동일 장비의 개체 구분, 상점 재고의 원정 수명을 반영하는 소유·참조 계약을 먼저 설계. 정의 ID만으로 여러 개체를 하나로 합치지 않음.
- 데이터의 생성·조회·변경 로직을 Unity View와 분리.

**완료:** 서로 다른 직업의 동료를 영입하고 개별 정보를 확인·관리할 수 있다. 전투 화면은 필요 없다.

### M3. 성장 시스템

**구현**
- 직업별 고정 레벨 보상 / 직업 내 선택 보상 / 공용 특성 데이터.
- 레벨업 시 해당 보상 부여 및 선택 결과 저장.
- 스킬·특성의 **보유 데이터**와 전투에서의 **실행 로직** 분리.
- 장비 3개 배분·중복·교체 제한·공용 보관, 유한 상점 재고와 구매·판매를 연결. 재방문 보충을 만들지 않으며 가격·되사기·판매품 재고 편입과 시작 장비는 별도 결정.
- 일반 5종과 고정 강화형은 `MercenarySystem.md`·`BattleSystem.md`를 따른다. 선택한 장비 한 개의 1회 강화와 특수 장비 직접 지급을 구분하고, 대상 없음·취소·결과 적용 순서·저장 계약을 먼저 정한다. 미정 수치 표기·중첩·발동 순서를 임의 확정하지 않는다.
- 전투 승리당 파티 경험치 1, 다음 레벨 필요 경험치가 현재 레벨인 규칙과 프로토타입 레벨 1~5를 검증. 전투 연결 전에는 모의 승리 입력을 사용하고 경험치 저장·초과 처리 등 미정 계약은 착수 전에 정한다.
- Lv3 공용 특성·Lv4 직업 스킬, 도적 전문화 Lv2·Lv5 보상과 도둑 Lv2의 명시된 선택 보상은 상세 문서를 따른다.

**완료:** 전투 없이도 레벨업·선택·습득 내역 및 캐릭터 정보 변화가 일관되게 유지된다.

### M4. 이벤트 런타임

**구현**
- `EventSystem.md`의 JSON·Catalog·참조 데이터 검증 및 로딩. 현행 데이터 형식과 Area·Entrance 구조에 필요한 미정 계약을 구분하고, 확정되지 않은 스키마를 임의로 추가하지 않음.
- `GameState.md`의 상태 소유권 제안에 따라 공통 수치·Tags와 EventState·ExplorationState를 연결. 단일 최종 목표의 식별·획득 확인 계약과 기존 Goal 필드의 이행은 별도 확정.
- 런 시작에 장소 조건으로 노드별 잠재 후보 참조를 구성하고 방문 때 그 노드 목록만 검사. 초기 조건이 맞지 않는 후속 사건도 포함하고 상태 변화만으로 원격 목록을 교체하지 않음. 런 공통 소비와 노드별 방문·과거 유효 후보 이력을 구분.
- Opening, Standalone, 선택지/결과 처리부터 시작해 Arc와 Goal 연동의 기반 마련.
- 목적지와 경유 노드의 실제 진입에 공통 이벤트 판정 적용. 경유 Entrance도 방문·이벤트 판정을 생략하지 않음. 첫 방문 후보 0개는 정상 무이벤트로 처리하고, 재방문은 새 조건으로 유효해진 후보가 있을 때만 기회 부여. 새 진입 경로 자체는 공통 발생 계기로 사용하지 않음.
- 한 기회에 유효했던 후보 전체를 기록하여 같은 상태에서 왕복으로 미선택 후보를 순차 소진하지 못하게 함. 정규 이벤트의 런당 1회 소비는 모든 노드가 공유하며 소비된 참조의 잠재 목록 내 물리 삭제는 필수가 아님.
- Result가 현재 노드의 다른 이벤트를 활성화해도 즉시 실행하지 않고 이후 실제 재진입에서 검사. 지도 UI 열기·닫기는 재진입이 아님. Entrance는 입구 처리 후 한 번 전환하고 최신 상태·런 공통 소비를 반영해 도착지 처리. 별도 두 노드에서 정규 이벤트가 각각 최대 1개 발생할 수 있음.
- 전투 Result는 임시 승리·패배 반환으로 검증.

**완료:** 첫 방문 후보 0개, 유효한 기회에서의 정규 이벤트 1개, 조건 변화에 따른 재방문, 여러 새 후보가 동시에 열린 뒤 왕복 소진 방지, Area별 노드 이력 분리와 경유 Entrance의 방문·이벤트 판정을 검증한다. 결과로 새 후보가 열려도 같은 진입에서 정규 이벤트가 연속 발생하지 않는다.

**주의:** 현재 Event Result는 경험치·영입·장비 지급·강화 대상 선택을 직접 지원하지 않는다. 이벤트 중심 강화와 특수 장비 보상 요구는 확정됐지만 실제 JSON·대상 선택·결과 적용 계약은 후속 설계다. 이를 구현할 때 `EventSystem.md`의 계약을 명시적으로 확장하고, 시설 거래와 이벤트 후보·소비 규칙을 혼용하지 않는다.

### M5. State에 반응하는 세계

**구현**
- State / Tags를 읽어 장소 설명, 상태 아이콘, 현재 Area 지도 표시를 결정하는 표현 계층(예: `WorldPresentationResolver`).
- 동일한 장소라도 과거 선택에 따라 다른 표현을 제공.
- 노드에서 변화된 조건으로 새 이벤트가 활성화된 경우, 실제 재진입 시 후보 이력과 함께 판정.
- 이벤트가 없는 노드의 장소 표현과 상점·영입 등 시설 UI를 서사 이벤트 UI와 구분. 구체 표시 방식과 불필요한 이동 클릭을 줄이는 방법은 별도 검토.
- 최초에는 맵 전체 교체, 대규모 지형 변형, 동적 Edge 생성은 구현하지 않는다.

**완료:** A 장소의 선택을 마친 뒤 B 장소로 이동해 사건과 시각적 표현의 차이를 실제로 확인할 수 있다. 이벤트가 없는 노드에서도 장소 표현과 가능한 시설 이용을 확인할 수 있다.

### M6. 원정의 시작과 끝

**구현**
- Opening에서 보물 탐색의 동기를 제공하고 단일 최종 목표의 정보를 안내. 다른 Area 목표 노드를 현재 지도에 표시하거나 직접 선택하지 않으며 제한 전 도전 접근·안내 방식은 별도 설계.
- 최종 도전 콘텐츠와 길잡이 획득 확인 후 `GoalSuccess`. 단순 도착·목격·전투 승리만으로 성공 처리하지 않음.
- Edge 도착 범위의 방문 이벤트·전투·보상·결과를 마친 뒤, 종료 결과가 없고 일반 탐험 중이면 시간 소진을 검사해 최종 도전으로 전환. 목적지 Entrance는 입구 처리·비용 0 전환 1회·도착지 처리까지 포함. 강제 이동과 목표 이벤트 발생 중 방식은 착수 전에 확정.
- 시간 소진을 `TimeExpired` 종료 결과로 만들지 않음. 전환 결정 뒤 일반 경로의 남은 이동이나 추가 0비용 이동으로 탐험을 연장하지 않으며 최종 도전 중복 진입과 시간 소진 재판정을 방지할 상태 경계를 구체화.
- 모의 전투 패배의 `BattleDefeat`.
- 연대기 및 기본 원정 결과 표시.

**완료:** 모의 전투로 자율 도전과 시간 소진 후 도전을 각각 진행하고 길잡이 획득 성공 또는 전투 패배로 끝나는 원정을 검증한다. 마지막 방문 결과가 최종 도전에 반영되며 시간 소진만으로 끝나지 않는다. 기타 실패·복귀 처리와 영구 기록 보존은 미정 계약을 먼저 정한다.

### M7. 실제 전투 통합

**구현**
- 기존 규칙대로 `(Event ID, Choice ID)`에 제작한 전투 데이터 연결.
- 파티의 캐릭터 데이터를 전투 시작용 데이터로 변환하여 전달.
- 전투 시스템은 턴·AP·이동·공격·스킬 효과를 처리하고, 종료 결과를 반환.
- 승리 시 이벤트 Result Effect를 적용; 패배 시 후속 Effect 없이 원정 종료.
- 원정 내 현재 HP 유지·자동 완전 회복 없음, HP 0 용병의 다음 전투 불참과 파티 공유 성장을 연결. 전투 참가 데이터·결과 반환·성장 보상과 이벤트 결과의 구체 처리 순서는 별도 계약으로 정한다.
- 장비 개체와 원정 소유 상태를 전투용 입력·임시 효과 상태에 연결. 복수의 장비별 반격과 촛농 갑옷의 착용자 자기 턴 기준 5턴 충전을 구분하며, 중복 소모·연쇄·정확한 시점은 미정 계약을 먼저 정한다. 전투 중 장비 변경은 허용하지 않는다.
- 궁수의 전투 종료 후 특수화살 1개 제작을 연결할 때 종료 결과별 발동·제작 대상·소비·보유·저장 계약과 보상·원정 종료 순서를 먼저 정한다. 정령궁수의 정령 부여·충전과 지면·공기 환경효과는 전투 명세를 따르며 기존 인벤토리·이벤트 Result가 이미 지원한다고 간주하지 않는다.

**완료:** 같은 이벤트 루프가 모의 전투 대신 실제 전투를 호출하고, 결과가 원정에 정상 반영된다.

## 5. 아키텍처 원칙

```text
정적 데이터
├─ Area / Node / Edge weight / Entrance 목적지 / Locations
├─ Mercenary / Class Definitions / Level Rewards
└─ Events / Arc Catalog / Goal Catalog

원정 로직 (순수 C# 우선)
├─ Exploration / Expedition Time
├─ GameState / EventState / ExplorationState
├─ MercenaryState / MercenaryInstance / Growth
├─ EventResolver / ResultApplier
└─ WorldPresentationResolver (표현에 필요한 상태 산출)

Unity View
├─ 현재 Area 지도 / 시설 UI
├─ Event UI
└─ Party / Level-up UI

추후 연결
└─ Battle Adapter → 기존 턴제 Combat → Battle Outcome
```

- 직업·성장 정적 정의와 원정 상태를 구분한다. 공유 레벨·경험치와 용병별 선택·HP 소유권은 `MercenarySystem.md`와 `GameState.md`를 따른다.
- 모험가의 **공용 전투 특성**과 이벤트의 파티 서사 태그 `Trait`은 서로 다른 데이터다.
- 캐릭터·파티 데이터는 전투 시스템의 소유물이 아니다. 전투는 필요한 데이터를 전달받아 실행한다.
- GameState의 하위 상태 소유권만으로 기존 이벤트 JSON이 용병·성장 필드를 지원한다고 간주하지 않는다. 이벤트 조건이나 Result에 필요할 때 참조 계약을 정한다.
- 구현은 순수 C# 상태 전이와 테스트를 우선하고, Unity View는 이를 표시한다.

## 6. 구현 전에 정해야 할 것과 미뤄도 되는 것

**각 기능에 착수할 때 정할 항목**
- M1: 첫 Area 구성, Area·Node·Edge·Entrance 목적지 ID·데이터 계약, 이미 서 있는 Entrance 재선택·복귀 조작, `Data/Locations.csv` 이행, Edge weight 단위·수치형·밸런스와 잔여 시간 부족 시 이동 정책. Entrance 전환 비용은 0이며 데이터 표현은 별도 결정.
- M2: 캐릭터 ID·정의/인스턴스 경계, 파티 인원 관리 정책. 현재 전투 프로토타입의 인원 제한과 전체 기획의 상한 차이는 통합 전에 확인.
- M3: 경험치 저장·초과 처리, 레벨 보상 지급 시점·선택 보상 데이터, 장비의 첫 검증 범위. 확정된 공유 성장·레벨·승리 경험치 규칙을 다시 미정으로 취급하지 않는다.
- M3~M4: 장비 개체·보관·장착·강화·재고의 저장 계약, 상점 가격·초기 수량·판매품 처리, 강화 대상 선택·취소·대상 없음·결과 적용 순서. 성검의 최종 물리공격력 보너스 +2와 방패파괴자의 공격당 최종 물리방어 파괴량 2는 확정했다. 나머지 미정 중첩·효과 계산은 상세 문서에서 확정한 뒤 데이터로 옮긴다.
- M4~M5: 캐릭터 성장/영입 보상을 Event Effect로 줄 필요가 있는지, 특정 직업이나 파티 구성을 이벤트 조건에서 참조할지.
- M4~M5: `locations`·잠재 후보·런 공통 소비·방문·후보 이력 스키마, 결과 전후 후보 이력 갱신 시점과 재진입 경계. 고정/랜덤 배치·선택·우선순위, 특정 진입 방향 조건도 후속 검토.
- M5: 이벤트 없는 노드의 콘텐츠 밀도와 표시, 시설 UI와 이벤트 UI의 구분 및 이동 클릭 수.
- M6: 단일 최종 목표 안내·접근 UI·선방문, GoalCatalog·획득 확인 계약, 강제 전환 방식·이동 비용·복귀·실패 처리, 흰밀물 로어 연결, 축복 후처리와 새 종료 구조의 영구 기록 보존.
- M7: 전투 시작·종료 데이터와 결과 적용 순서. 용병·공유 성장은 원정 수명이며 다음 원정에 동일 용병을 유지하지 않는다.

**최초 프로토타입에서 보류**
- 모든 직업의 전체 스킬·특성·장비 콘텐츠 완성 및 전투 밸런스.
- 월드 전체 규모의 반응형 변화와 동적 지리 구조.
- 특별 장소의 영구 기록·해금을 새 최종 도전과 종료 결과에 연결하는 세부 계약.
- 축복 시스템의 실제 효과와 전투 적용. 축복의 별도 규칙은 `BlessingSystem.md`를 유지하며 이후 통합한다.
- 길잡이 획득 이후 자유 탐사·귀환 납품·즉위·통치 플레이는 현재 범위에서 제외.

## 7. 가장 먼저 수행할 작업

1. **작은 테스트 지역의 Area와 노드 연결**을 작성한다. Location 8~12개, 최종 목표 1개, 분기·되돌아갈 길을 포함한다. 위치 수는 임시 제안이며 Area 구성은 별도로 정한다.
2. **한 장소에서의 선택이 다른 장소를 바꾸는 시나리오 하나**를 작성한다. 필요한 Fact와 조건부 이벤트, 이벤트가 있는 노드와 없는 노드를 식별한다.
3. 그 시나리오를 목표로 M1부터 순서대로 구현한다. 완성형 콘텐츠 대신 최소 테스트 데이터로 검증한다.

**통합 프로토타입 완료 기준:** 파티를 꾸리고 자유롭게 경로를 선택해 사건을 해결하며, 과거 선택이 다른 장소에 남아 있음을 확인하고 성장·최종 도전·길잡이 획득 결말까지 경험한다. 시간 소진도 마지막 방문 결과를 처리한 뒤 같은 도전으로 연결한다. 실제 전투 연결 전에는 흐름의 작동만 검증하고 재미 평가는 구분한다.

## 8. 새 세션에서의 작업 지침

- 먼저 `World_Premise.md`, `WorldLore.md`, `Plan.md`, `EventSystem.md`, `GameState.md`, `MercenarySystem.md`, `BattleSystem.md`, `BlessingSystem.md`를 확인하고 충돌·미정 사항을 구분한다.
- 각 단계에 착수할 때는 **구현 범위 → 필요한 데이터 계약 → 테스트 기준 → 구현 순서**를 먼저 정리한다.
- 기존 명세의 확정 규칙을 변경해야 한다면 해당 문서를 별도로 수정한다. 이 로드맵 자체를 확정된 시스템 명세로 간주하지 않는다.
- 매 단계의 구현과 검증을 끝낸 후 다음 단계로 진행한다. 전투 시스템 개발은 별도 흐름으로 병행할 수 있다.
