# 용병 데이터 시스템 설계

- 기준일: 2026-10-21
- 범위: 직업 기반 용병의 정적 데이터, 원정 런타임 데이터와 전투 데이터의 연결
- 상태: ClassDefinition·AbilitySettings·MercenaryDataList의 코드와 프로토타입 에셋, 데이터 검증을 구현했다. 직업 식별자는 MercenaryClass로 통일했다. 에셋의 전투 연결과 용병 런타임 데이터·계산 구조는 미구현이며 설계 중이다. 컴파일·빌드·Unity 테스트 실행 여부는 별도 검증 결과로 확인한다.

## 1. 목적과 문서 기준

용병의 데이터 역할, 소유권, 생명주기와 시스템 간 연결 규칙을 정한다. 미리 제작된 고유 캐릭터와 적·소환물을 포함하는 범용 캐릭터 시스템은 현재 범위에 포함하지 않는다.

관련 문서는 [Plan.md](Plan.md), [BattleSystem.md](BattleSystem.md), [EventSystem.md](EventSystem.md), [BlessingSystem.md](BlessingSystem.md)다. 용병의 원정 수명, HP 유지와 파티 공유 성장에 관해서는 이 문서의 확정사항을 우선한다.

| 상태 | 의미 |
| --- | --- |
| 확정 | 이번 용병 설계에서 합의한 규칙. 구현 완료를 의미하지 않는다. |
| 제안 | 검토할 설계 방향. 실제 스키마나 동작으로 확정하지 않는다. |
| 미정 | 이후 논의가 필요한 항목. 예시만으로 확정하지 않는다. |

Plan의 오토배틀·마나 관련 전투 본문은 개정 전 내용이다. 이번 설계는 현재 BattleSystem의 턴제·AP 규칙을 기준으로 한다. 기존 문서의 테스트값과 현재 구현값을 최종 밸런스로 취급하지 않는다.

## 2. 용병 생성과 생명주기 — 확정

- 용병은 직업 템플릿 기반으로 생성한다.
- 같은 직업의 용병은 기본 능력치와 성장 규칙을 공유한다.
- 각 용병은 독립적인 인스턴스로 존재한다. 레벨과 경험치는 파티가 공유하고, 전문화와 성장 보상의 선택 결과는 용병별로 가진다.
- 용병은 한 번의 원정에서만 유지한다.
- 원정이 끝나면 파티의 공유 레벨·경험치와 용병별 전문화·장비·성장 선택 기록 등 런타임 데이터를 폐기한다.
- 연대기나 통계에 기록을 남길 수는 있지만, 다음 원정에서 동일한 용병을 유지하지 않는다.

이 규칙은 기존 문서에서 미정으로 남아 있던 원정 간 성장 유지 문제를 용병 런타임 데이터의 범위에서 확정한다.

## 3. HP와 전투 불능

### 3.1. 확정 규칙

- 현재 HP는 전투 사이에도 유지한다. 전투가 끝나도 자동으로 완전 회복되지 않는다.
- HP가 0이면 전투 불능이며, 용병은 원정 파티에 그대로 남는다.
- HP가 0인 동안에는 다음 전투에 참여할 수 없다. HP가 회복되면 다시 참여할 수 있다.
- 전투 불능이 되어도 전문화·장비·성장 선택은 유지하며, 파티 공유 레벨을 적용받는다. 개인 레벨이나 경험치가 뒤처지는 구조는 두지 않는다.
- HP 0으로 인한 전투 불능은 영구적인 사망이 아니다.
- 전투 유닛 제거와 원정 용병 제거는 서로 다른 작업이다.

### 3.2. 제안과 미정 사항

별도의 전투 불능 상태를 저장하기보다 `CurrentHP == 0`으로 판정하는 구조를 우선 검토한다.

일반 회복으로 HP 0인 용병을 회복할 수 있는지, 별도의 소생 수단이 필요한지는 미정이다. 전투 중 전장에서 제거된 유닛의 복귀 규칙도 확정하지 않는다.

BattleSystem의 직업별 초기 테스트 표는 HP를 ‘전투 시작 시의 HP’로 설명한다. 이번 규칙에서는 최대 HP와 전투 시작 현재 HP를 구분한다. 프로토타입에서는 전사 10·도적 8·궁수 8을 직업 기본 최대 HP로 사용하기로 확정했다. 매 전투 현재 HP를 이 값으로 초기화하지 않으며, 생성 시 현재 HP 설정 규칙은 미정이다.

## 4. 기본 능력치와 적용 범위 — 확정

현재 설계의 기본 목록은 아래 10개 항목으로 한다. 최종 수치와 밸런스는 미정이다.

| 구분 | 항목 | 역할 |
| --- | --- | --- |
| 유닛 능력치 | 최대 HP | 현재 HP가 가질 수 있는 상한. 현재 HP 자체는 별도 런타임 상태다. |
| 유닛 능력치 | 이동력 | 자신의 턴에 사용할 이동량의 기준. 남은 이동력과 구분한다. |
| 유닛 능력치 | 치명타 확률 | 강제 치명타 조건이 없을 때 사용하는 일반 확률이다. |
| 유닛 능력치 | 물리 방어력 | 물리 피해를 줄이는 수치다. |
| 유닛 능력치 | 물 방어력 | 물 피해를 줄이는 수치다. |
| 유닛 능력치 | 불 방어력 | 불 피해를 줄이는 수치다. |
| 유닛 능력치 | 전기 방어력 | 전기 피해를 줄이는 수치다. |
| 유닛 능력치 | 독 방어력 | 독 피해를 줄이는 수치다. |
| 기본 공격 수치 | 기본 공격 피해 | 기본 공격의 치명타·방어력 적용 전 피해다. |
| 기본 공격 수치 | 기본 공격 사거리 | 기본 공격이 도달할 수 있는 최대 헥스 거리다. |

무속성 방어력은 존재하지 않는다. 속성별 방어력의 고정 수치 차감과 최소 피해 0 규칙은 BattleSystem을 따른다.

기본 공격 피해와 사거리는 기본 공격 전용 수치로 구분한다. 기본 공격 피해를 모든 스킬에 자동 적용하는 범용 공격력으로 취급하지 않는다. 스킬이 기본 공격 피해나 사거리를 참조할 필요가 있다면 해당 스킬의 규칙에서 관계를 명시한다. 스킬별 피해·사거리의 상세 구조는 미정이다.

이 구분은 적용 범위에 대한 합의이며, 데이터를 반드시 별도 객체나 파일로 나눈다는 뜻은 아니다.

## 5. 일반 능력치, 직업 능력과 공통 규칙 — 확정

### 5.1. 일반 능력치와 직업 능력

숫자를 포함하는지보다 무엇을 판단하거나 변경하는지에 따라 구분한다.

| 사례 | 분류 | 이유 |
| --- | --- | --- |
| 전사의 물리 방어력 1 | 일반 능력치 | 물리 피해 계산에 사용하는 수치다. |
| 전사의 방향별 물리 피해 무효화 | 직업 능력 | 공격 속성·방향·확률에 따른 별도 판정이다. |
| 도적의 높은 이동력 | 일반 능력치 | 이동량의 차이로 표현한다. |
| 도적의 후면 강제 치명타 | 직업 능력 | 상대와의 위치 관계에 따라 치명타 판정을 바꾼다. |
| 궁수의 기본 공격 사거리 3 | 기본 공격 수치 | 현재 정해진 차이는 사거리로 표현한다. |

위 수치와 직업 능력의 세부 동작은 BattleSystem의 초기 테스트 기획을 따른다. 최종 밸런스나 레벨별 획득 시점을 새로 확정하는 표는 아니다.

전사의 무효화 확률처럼 직업 능력 내부에 숫자가 있더라도 모두 공통 능력치로 만들지 않는다. 반대로 직업 능력이나 공용 특성이 일반 능력치를 증가시키는 효과를 제공할 수는 있다. 효과를 얻는 출처와 효과가 변경하는 대상을 구분한다.

능력치 계산은 사용할 수치를 산출하고, 공격 시 판정은 방향·속성·직업 능력 등을 확인하여 실제 피해를 결정한다. 조건부 판정까지 모두 하나의 최종 능력치 값으로 환산하지 않는다.

### 5.2. 공격 설정과 공통 전투 규칙

- 기본 공격 속성은 수치형 능력치가 아닌 공격 설정이다. 현재 전사·도적·궁수의 기본 공격 속성은 물리다.
- 치명타 추가 피해는 현재 공통 규칙인 +2를 따른다. 직업별 기본 능력치로 중복하지 않는다.
- AP 시작량, AP 상한, 턴당 AP 지급량과 기본 공격 비용은 직업별 차이를 도입하기 전까지 공통 BattleRules에 두고 직업 데이터에 중복하지 않는다.
- 무속성을 포함한 모든 속성의 공격에 치명타를 허용하는 기존 규칙을 유지한다.

Plan의 ‘치명적인 마법’ 등 공용 특성 예시는 확정 콘텐츠가 아니며, 기존 치명타 규칙을 변경하지 않는다.

## 6. 성장 규칙 — 확정

### 6.1. 파티 공유 레벨과 경험치

- 레벨과 경험치는 용병 개인이 아닌 원정 파티가 소유한다.
- 파티의 모든 용병은 같은 레벨을 적용받는다. 용병별 레벨·경험치 진행도는 두지 않는다.
- 프로토타입의 파티 시작 레벨은 1, 최대 레벨은 5다.
- 프로토타입에서는 전투 승리마다 파티 경험치를 고정 1 지급한다. 참가자 수나 생존자 수를 곱하거나, 개인별로 나누어 지급하지 않는다.
- 최대 레벨 미만에서 현재 파티 레벨이 L이면 다음 레벨까지 필요한 경험치는 `L`이다. 이는 현재 레벨에서 다음 레벨로 오르는 데 필요한 양이며, 원정 전체의 누적 경험치 기준값이 아니다. Lv5에서는 더 이상 레벨업하지 않는다.
- 파티 레벨이 오르면 각 용병은 자신의 직업별 레벨 보상표에 따라 성장한다. 선택 보상은 용병별로 선택하고 기록한다.
- 전투 참가 여부나 전투 불능 여부에 따른 개인 경험치 차이는 없다. 보상 선택·적용의 구체적인 시점은 별도로 정한다.

| 레벨업 | 필요한 파티 경험치 | 시작 경험치 0일 때 누적 승리 |
| --- | ---: | ---: |
| Lv1 → Lv2 | 1 | 1승 |
| Lv2 → Lv3 | 2 | 3승 |
| Lv3 → Lv4 | 3 | 6승 |
| Lv4 → Lv5 | 4 | 10승 |

시작 경험치를 0으로 가정하면 첫 전투 승리 직후 Lv2에 도달하며, 누적 10승에 최대 레벨인 Lv5에 도달한다. 한 원정에서 레벨업은 최대 네 번 경험한다. 위 예시의 시작 경험치 0은 아직 제안이며, 모든 원정에서 최대 레벨에 도달해야 한다는 조건은 아니다.

시작 경험치, 레벨업 후 경험치 기록 방식과 초과 경험치 처리, 최대 레벨 도달 후 경험치 처리는 미정이다. 중도 영입 시에도 파티 공유 레벨을 기준으로 하되, 이전 레벨의 보상을 지급하고 선택하는 절차는 별도로 정한다.

### 6.2. 용병별 성장 보상

직업별 레벨 보상표는 다음 세 가지 보상 방식을 사용한다.

1. 직업별 고정 보상
2. 직업 내 선택 보상
3. 직업 공통 특성 보상

모든 레벨에 동일한 보상을 지급하지 않는다. 프로토타입의 Lv2~Lv5 성장 흐름은 6.3절을 따른다. 직업·전문화별 실제 스킬과 특성의 목록, 수치 및 세부 보상 개수는 아직 정하지 않는다.

매 레벨 능력치를 일괄 상승시키는 자동 성장식을 전제하지 않는다. 레벨 성장에 의한 능력치 변화는 보상표에 명시된 보상으로 반영한다.

여기서 공용 특성은 용병 개인의 전투·성장 특성이다. EventSystem의 `Trait` 및 `Data/Traits.csv`가 표현하는 파티의 서사적 성향 태그와 다른 개념이다.

같은 직업의 용병도 전문화·선택 보상·장비를 달리할 수 있다. 파티가 레벨을 공유한다는 것은 성장 단계의 공유이며, 용병별 선택 결과나 최종 능력치까지 동일하다는 뜻은 아니다.

### 6.3. 레벨별 성장 흐름

| 도달 레벨 | 성장 보상 | 선택 방식 | 시작 경험치 0일 때 누적 승리 |
| --- | --- | --- | ---: |
| Lv2 | 전문화에 정해진 특성과 스킬 습득 | 용병별로 전문화 하나를 선택하고, 해당 보상을 받는다. | 1승 |
| Lv3 | 공용 특성 획득 | 용병별로 플레이어가 공용 특성 풀에서 직접 선택한다. | 3승 |
| Lv4 | 직업에 맞는 새로운 스킬 획득 | 직업에 따라 고정 지급하거나 후보 중 선택한다. 직업별 지급 방식은 미정이다. | 6승 |
| Lv5 | 전문화에 맞는 강력한 스킬과 특성 획득 | Lv2에서 선택한 전문화에 따른 보상을 받는다. | 10승 |

Lv1은 전문화 선택 전의 시작 단계다. 초기 보유 능력의 실제 레벨 보상표 연결은 별도로 정하며, 이 표가 기존 ClassDefinition의 초기 테스트 능력을 새로 배치하거나 변경하지는 않는다.

Lv2는 성장 방향을 선택하고, Lv3는 공용 특성으로 용병의 개성을 더하며, Lv4는 직업의 행동 선택지를 확장하고, Lv5는 전문화의 강점을 완성하는 단계로 구성한다. 레벨별 보상 종류와 선택 방식의 합의이며, 실제 콘텐츠·효과·밸런스가 확정되었다는 뜻은 아니다.

### 6.4. 전문화 선택과 유지

- 전문화는 직업 안에서 선택하는 성장 갈래다.
- Lv2에서 각 용병은 전문화 하나를 선택한다. 파티 전체가 하나의 전문화를 공유하지 않는다.
- 선택한 전문화는 해당 원정 동안 유지하며, 원정 중 다른 전문화로 변경하지 않는다.
- Lv2에서는 전문화 선택에 따라 정해진 특성과 스킬을 배운다. 해당 보상을 각각 다시 선택하는 방식은 아니다.
- Lv5에서는 선택한 전문화에 맞는 강력한 스킬과 특성을 배운다. 전문화를 다시 선택하는 단계는 아니다.
- 전문화는 용병별 성장 선택이며, 원정 종료 시 다른 용병 런타임 데이터와 함께 폐기한다.

공용 특성은 전문화 보상과 구분한다. Lv3에서는 공용 특성 풀에서 플레이어가 직접 선택하며, 구체적인 후보 제시 방식·선택 조건·효과는 이후 설계한다.

현재 기획 목표는 전사·도적·궁수·마법사 4직업과 직업당 3종, 총 12종의 전문화다. 전사의 전문화 이름·역할·로어는 6.6절을 따른다. 나머지 직업의 전문화 이름·테마와 모든 전문화의 실제 보상 스킬·특성은 미정이다. 이 목표는 현재 구현된 직업이나 정적 데이터의 범위를 변경하지 않는다. 중도 영입 용병의 전문화 및 이전 레벨 보상을 선택하는 절차도 별도로 정한다.

### 6.5. 보상 콘텐츠 설계 시 검토할 방향 — 제안

- Lv2 보상만으로 전문화의 핵심 플레이가 성립하고, Lv5는 이를 강하게 확장하는 방향을 검토한다.
- 전문화가 반드시 특정 공용 특성을 골라야 작동하도록 만들기보다, Lv3 특성이 강화·보완·변형을 제공하는 방향을 검토한다.
- Lv4 스킬을 고정 지급하는 직업은 모든 전문화에서 활용할 수 있는지 확인한다. 전문화에 따라 필요한 행동이 크게 다르면 선택 보상을 검토한다.
- 파티 전체가 동시에 성장하므로, 한 번의 레벨업에 필요한 선택량과 탐험 흐름의 중단 시간을 함께 살펴본다.

### 6.6. 전사의 공통 정체성과 전문화 — 기획 확정

이 절은 전사의 테마와 역할을 정의한다. 세부 스킬·특성, 전투 효과, 전문화별 수치와 장비 제한은 미정이며, 기존 초기 테스트 능력치나 직업 능력을 변경하지 않는다. 세계관의 기본 분위기는 [World_Premise.md](World_Premise.md)를 따른다.

#### 6.6.1. 전사의 공통 정체성

전사는 호위와 경비, 구조와 괴물 퇴치의 현장에서 무장 전투를 익혀, 일행이 위험에 맞설 수 있게 하는 사람들이다. 훈련과 실전 경험으로 다른 사람들이 맡은 일을 수행할 수 있도록 싸움을 담당한다. 무기 숙련은 이들의 전문 기술이며, 출신을 하나의 군대·학교·조직으로 한정하지 않는다.

상단 호위대, 성문 경비대, 변경 마을의 무장대나 선배 모험가에게 기술을 배운 사람 등 다양한 배경이 가능하다. 이는 배경의 예시이며 특정 조직의 존재나 소속을 필수 조건으로 확정하지 않는다.

전투에서는 적과 가까이 맞붙고, 위치와 방향을 이용해 전선을 만드는 근접 전투원의 정체성을 공유한다. 다가오는 공격 앞에서 자세를 유지하고 동료와 발을 맞추며 무기와 보호구를 실전에서 다루는 숙련을 갖춘다. 기존 방향별 물리 피해 무효화는 이러한 숙련과 연결하여 해석할 수 있다.

전문화는 이 공통 기반 위에서 싸우는 목적과 역할을 구분한다. 과거 경력이 전문화를 자동으로 결정하는 것은 아니며, Lv2의 선택은 이미 익힌 기술 중 이번 원정에서 집중할 역할을 정하는 것으로 해석한다.

#### 6.6.2. 세 전문화의 역할

| 전문화 | 역할 | 정체성과 동기 | 전투 방식 |
| --- | --- | --- | --- |
| 호위병 | 보호 | 사람들을 지켜온 전사. 맡은 일행의 무사 도착과 귀환을 우선한다. | 지킬 사람과 위험 사이에 서서, 일행이 안전하게 행동하거나 이동할 공간을 확보한다. |
| 개척자 | 돌파 | 위험한 길의 앞에 서온 전사. 자신과 동료들이 나아갈 길을 연다. | 막힌 접근로와 적의 배치를 살펴 진입할 지점을 고르고, 동료들이 따라 움직일 틈을 만든다. |
| 무사 | 제거 | 스스로 강해지기 위해 위험에 몸을 던지는 전사. 강적과 맞서 자신의 한계를 넘으려 한다. | 위협적인 상대에게 집중하고, 맞붙은 뒤 공격 기회를 놓치지 않으며 제압한다. |

#### 6.6.3. 호위병 — 맡은 사람을 도착시키는 전사

상단과 여행자, 탐험대를 보호해온 사람들이다. 이들에게 성공한 싸움은 맡은 일행이 무사히 길을 계속 갈 수 있게 된 싸움이다. 적을 쫓는 것보다 지킬 대상과 위치를 의식하며, 일행이 움직일 시간을 확보하고 필요하면 함께 물러난다.

누구를 보호하고 어디를 지킬 것인지가 역할의 중심이다. 혼자 오래 버티는 것뿐 아니라 동료의 안전에 기여하는 전문화로 설계한다. 구체적인 접근 차단·보호 수단은 이후 정한다.

#### 6.6.4. 개척자 — 동료가 나아갈 길을 여는 전사

탐험과 구조의 현장에서 위험한 길의 앞을 맡아온 사람들이다. 막힌 통로를 뚫고, 고립된 사람에게 접근하고, 동료가 들어오거나 빠져나갈 길을 확보하는 경험과 연결된다.

어디로 진입해야 전장의 배치가 달라지고 일행이 움직일 수 있는지를 판단한다. 홀로 깊이 들어가는 것 자체보다 돌파 이후 동료들이 활용할 수 있는 기회를 만드는 것이 중요하다. 진입과 진형 교란을 표현할 구체적인 전투 효과는 이후 정한다.

#### 6.6.5. 무사 — 위험 속에서 자신을 단련하는 전사

스스로 강해지기 위해 위험에 몸을 던지는 사람들이다. 강적과의 대결을 자신의 기량을 시험하고 부족함을 발견하는 기회로 받아들인다. 탐험 중 만나는 위험은 이들이 자신의 한계를 넘어설 수 있는 도전이 된다.

반드시 난폭하거나 죽음을 두려워하지 않는 인물일 필요는 없다. 두려움을 느끼면서도 성장을 위해 도전을 택할 수 있다. 무사의 중심 동기는 전문적인 토벌 업무가 아니라 자기 단련이다.

전투 역할은 위협적인 상대에게 집중하여 제거하는 것이다. 위험을 감수한다는 테마만으로 낮은 HP 유지·자해·분노 자원 등의 세부 규칙을 도입하지 않는다. 공격 기회를 붙잡고 상대를 압박하는 구체적인 방법은 이후 설계한다.

## 7. 데이터 책임과 정적 스키마

ClassDefinition은 7.4절의 프로토타입 스키마를 구현했다. 능력 종류의 보유 목록과 공통 기본 설정을 분리하며, AbilitySettings의 책임과 저장 구조는 7.5절을 따른다. 직업 식별자와 정적 데이터 목록은 7.6절을 따른다. 그 밖의 데이터 이름과 필드는 역할을 설명하는 제안이며 최종 스키마가 아니다.

### 7.1. 정적 데이터

| 데이터 | 책임 |
| --- | --- |
| ClassDefinition | 직업별 기본 능력치, 기본 공격 설정과 보유 능력 enum 목록 |
| AbilitySettings | 능력 종류별 공통 기본 설정을 하나의 ScriptableObject에서 관리 |
| MercenaryDataList | MercenaryClass 키와 ClassDefinition 참조의 대응 및 공통 AbilitySettings 참조 |
| ClassLevelTable | 직업별 레벨 보상표 |
| SkillDefinition | 스킬의 조건, 비용, 사거리와 효과 |
| TraitDefinition | 용병 개인 공용 특성의 조건과 효과 |
| ItemDefinition | 아이템의 장착 조건과 효과 |

같은 직업의 인스턴스는 읽기 전용 직업 정의를 공유하며, 개별 용병의 성장 결과로 직업 기본값 자체를 변경하지 않는다. 직업 능력의 초기 보유와 레벨 보상에 의한 획득을 어떻게 연결할지는 이후 구체화한다.

### 7.2. MercenaryInstance — 원정 수명·제안

MercenaryInstance는 아직 구현하지 않았다. 파티 공유 레벨·경험치는 원정 파티 데이터가 소유하며 MercenaryInstance에 중복 저장하지 않는다. 파티 데이터의 구체적인 타입과 필드명은 별도 설계한다.

| 데이터 후보 | 역할 |
| --- | --- |
| InstanceId | 용병 인스턴스의 고유 식별자 |
| Name | 용병 이름 |
| Class | MercenaryClass 타입의 직업 식별자. MercenaryDataList에서 직업 정적 데이터를 찾는 키 |
| CurrentHP | 전투 사이에도 유지하는 현재 HP |
| SelectedRewardIds | 파티 레벨업에 따라 용병별로 선택한 성장 보상 |
| EquippedItemIds | 장착 아이템 참조 |

전문화 선택은 용병별 원정 데이터에 기록해야 한다. 전문화 식별자를 별도로 둘지 기존 선택 보상 기록에 포함할지 등 실제 저장 구조는 미정이다.

직업별 고정 보상은 해당 용병의 직업과 파티 공유 레벨로, 전문화별 고정 보상은 선택한 전문화와 파티 공유 레벨로 계산하여 중복 저장을 피하는 방향을 검토한다. 선택 보상의 식별 방식과 선택 횟수·보상 위치를 표현하는 방법은 미정이다.

아이템 참조가 정적 정의와 개별 아이템 인스턴스 중 무엇을 가리키는지, 아이템 인스턴스를 별도로 소유하는 주체는 누구인지는 미정이다.

최대 HP 등 계산 가능한 최종 능력치는 별도의 영구 저장값보다 정적 데이터와 현재 성장 상태를 조합해 산출하는 방향을 검토한다. 캐시 여부와 재계산 시점은 확정하지 않는다.

### 7.3. BattleUnit — 전투 수명·제안

- 전투 유닛 ID와 원본 용병 참조
- 전투 시작 시 적용할 능력치
- 전투 중 HP
- AP와 남은 이동력
- Hex 좌표와 바라보는 방향
- 전투 중에만 유지되는 상태효과

전투 중 상태는 전투 시스템이 관리하고, 종료 후 필요한 결과만 원정 데이터에 반영하는 방향을 제안한다. AP·좌표·방향 등은 다음 전투로 그대로 넘기지 않는다. 현재 구현의 HexCharacter와 이 초안의 구체적인 대응 관계는 아직 정하지 않는다.

### 7.4. ClassDefinition — 프로토타입 코드·에셋 구현

같은 직업의 용병이 공유하는 기본 전투 설정을 정의한다. 적용 범위는 전사·도적·궁수를 생성하여 기본 전투를 진행하는 프로토타입이다. 파티의 현재 레벨·경험치와 개별 용병의 현재 HP·장비·성장 선택은 포함하지 않는다.

아래 필드를 ScriptableObject로 저장한다. BaseStats는 ClassBaseStats, BasicAttack은 BasicAttackDefinition 직렬화 struct다. 정수 수치는 int, 확률은 float로 저장하며, Abilities는 AbilityType 배열로 일반 직렬화한다. 외부에는 읽기 전용 프로퍼티와 능력 개수·인덱스 조회를 제공한다.

| 필드 | 형식 | 역할 |
| --- | --- | --- |
| DisplayName | 문자열 | UI에 표시할 직업 이름 |
| BaseStats | 능력치 묶음 | 성장·장비·축복 적용 전의 기본 유닛 능력치 |
| BasicAttack | 기본 공격 설정 | 기본 공격의 피해·사거리·속성 |
| Abilities | 능력 종류 enum 목록 | 프로토타입에서 해당 직업이 제공하는 능력 종류. 설정값은 포함하지 않는다. |

ClassDefinition에는 문자열 Id나 직업 enum 필드를 두지 않는다. 직업 식별자는 MercenaryDataList의 MercenaryClass 키 한 곳에서 관리한다. 에셋 이름이나 표시 이름을 바꿔도 해당 키와 에셋의 연결은 유지된다.

#### 7.4.1. BaseStats

| 필드 | 형식 | 단위·유효 범위 |
| --- | --- | --- |
| MaxHP | 정수 | 1 이상 |
| Movement | 정수 | 턴당 이동량, 0 이상 |
| CriticalChance | 실수 | 0~1. 0.05는 5% |
| PhysicalDefense | 정수 | 0 이상 |
| WaterDefense | 정수 | 0 이상 |
| FireDefense | 정수 | 0 이상 |
| LightningDefense | 정수 | 0 이상 |
| PoisonDefense | 정수 | 0 이상 |

프로토타입의 기본 방어력은 음수를 허용하지 않는다. 향후 취약성이나 방어력 감소를 도입할 때 최종 방어력의 음수 허용 여부를 별도로 정한다.

#### 7.4.2. BasicAttack

직업 정의 안에 포함하는 설정 묶음이다. 현재 범위에서는 별도의 BasicAttackId나 공유 공격 데이터를 두지 않는다.

| 필드 | 형식 | 단위·유효 범위 |
| --- | --- | --- |
| Damage | 정수 | 치명타·방어력 적용 전 피해, 1 이상 |
| Range | 정수 | 최대 헥스 거리, 1 이상 |
| DamageType | AttackAttribute | 물리·물·불·전기·독·무속성 중 하나. 전기는 Electricity 값에 대응한다. |

기본 공격 비용은 공통 전투 규칙을 사용한다. 스킬에 이 피해·사거리를 자동 적용하지 않는다.

#### 7.4.3. Abilities

각 항목은 능력 종류를 나타내는 AbilityType enum 값이다. 설정값이나 능력 에셋 참조는 목록에 저장하지 않는다. 같은 능력 종류는 직업에 관계없이 AbilitySettings의 공통 기본 설정을 사용한다. 향후 전투 연결에서는 직업 이름 대신 능력 종류에 따라 처리한다. 현재 전투의 직업별 능력 판정은 아직 에셋에 연결하지 않았다.

AbilityType은 Unity에 의존하지 않는 RaggedBanner.Mercenaries 어셈블리에 둔다. 능력 보유 여부는 전투뿐 아니라 이벤트에서도 검사할 수 있는 용병 데이터다. 전투 판정과 이벤트 조건의 실행은 각 시스템이 담당하며, 이벤트에서의 구체적인 사용 방식은 아직 정하지 않는다.

직업별 설정 덮어쓰기나 같은 능력 종류의 설정 변형을 선택하는 구조는 현재 범위에 두지 않는다. 임의의 조건·효과를 조립하는 범용 구조도 만들지 않는다.

| 능력 enum 항목 | AbilitySettings의 공통 설정 | 동작 |
| --- | --- | --- |
| DirectionalPhysicalNegation = 1 | 정면·측면·후면 무효화 확률 | 방향에 따라 물리 피해를 무효화한다. |
| RearGuaranteedCritical = 2 | 추가 설정 없음 | 후면에서 공격하면 강제 치명타가 발생한다. |

무효화 확률은 각각 0~1이며, 서로 다른 방향에 적용하므로 합계가 1일 필요는 없다. 측면은 BattleSystem의 ‘그 외 방향’에 해당한다. 방향 판정과 피해 처리 순서는 기존 공통 전투 규칙을 따른다.

후면 강제 치명타는 기본 공격 전용 설정에 넣지 않는다. 기존 규칙에 따라 적용 대상 공격의 사거리 안에서 후면 조건을 검사한다.

능력 목록은 비어 있을 수 있다. null 배열, 정의되지 않은 enum 값과 같은 능력 종류의 중복 등록을 거부한다. AbilityType은 Flags enum이 아니며 0은 정의하지 않는다.

Abilities는 프로토타입 초기 제공 능력을 뜻한다. 실제 게임의 1레벨 보상이나 영구 고정 능력으로 확정하지 않는다. 레벨 성장과 연결할 때 같은 능력을 중복 지급하지 않도록 획득 출처를 정한다.

#### 7.4.4. 프로토타입 직업 데이터

기존 테스트 수치를 사용하며, HP는 직업 기본 최대 HP로 해석한다. 최종 밸런스는 아니다.

| 항목 | 전사 | 도적 | 궁수 |
| --- | --- | --- | --- |
| MercenaryDataList의 키 | MercenaryClass.Warrior = 0 | MercenaryClass.Rogue = 1 | MercenaryClass.Archer = 2 |
| DisplayName | 전사 | 도적 | 궁수 |
| MaxHP | 10 | 8 | 8 |
| Movement | 2 | 4 | 2 |
| CriticalChance | 0.05 | 0.15 | 0.10 |
| PhysicalDefense | 1 | 0 | 0 |
| WaterDefense | 0 | 0 | 0 |
| FireDefense | 0 | 0 | 0 |
| LightningDefense | 0 | 0 | 0 |
| PoisonDefense | 0 | 0 | 0 |
| BasicAttack.Damage | 3 | 3 | 3 |
| BasicAttack.Range | 1 | 1 | 3 |
| BasicAttack.DamageType | 물리 | 물리 | 물리 |
| Abilities | DirectionalPhysicalNegation | RearGuaranteedCritical | 빈 목록 |

방향별 무효화 확률은 이 직업 표에 저장하지 않고 7.5절의 AbilitySettings에서 관리한다. 생성 시 현재 HP를 최대치로 채울지는 용병 생성 규칙에서 별도로 정한다.

#### 7.4.5. 사용 흐름과 검증

1. MercenaryDataList의 직업 키·정의 참조와 공통 AbilitySettings를 읽고 각각의 데이터 및 능력 설정 연결을 검증한다.
2. 향후 용병 인스턴스는 MercenaryClass 타입의 Class로 직업을 참조한다. MercenaryInstance 자체는 미구현이다.
3. 능력치 산출 과정이 직업 기본값을 읽고, 이후 파티 공유 레벨에 따른 직업 보상·용병별 성장 선택·장비 등의 효과를 반영한다. 구체적인 계산 구조는 8절의 설계 대상이다.
4. 연결부는 보유 능력 enum에 필요한 공통 설정을 확인하여 전투에 전달한다. 전투 시스템은 산출된 수치와 능력 종류·설정으로 판정을 수행한다.

직업 정의는 실행 중 공유하는 읽기 전용 원본으로 취급한다. 피해나 버프, 성장 때문에 원본을 변경하지 않는다.

ClassDefinition.Validate는 비어 있거나 공백뿐인 표시 이름, 기본 수치의 유효 범위, 공격 속성과 능력 enum의 유효성, 같은 능력 종류의 중복 여부를 검증한다. 확률은 NaN·무한대를 허용하지 않는다. 직업 키와 정의 참조의 검증은 7.6절의 목록 검증이 담당한다. 공통 능력 설정은 AbilitySettings.Validate에서 검증한다. 검증은 첫 오류에서 false와 원인 문자열을 반환하며 잘못된 값을 보정하거나 로그를 출력하지 않는다.

레벨 보상표, 외형·프리팹, 스킬 목록과 장비 슬롯은 이번 스키마에서 보류한다. 정적 데이터 코드·에셋과 검증은 구현했으며, 에셋 로더와 전투 연결은 미구현이다.

#### 7.4.6. 저장 형식 — ScriptableObject

- 직업당 ScriptableObject 에셋 하나를 두며, 전사·도적·궁수의 정의를 각각 작성한다.
- BaseStats와 BasicAttack은 해당 직업 에셋 내부에 포함한다.
- Abilities는 능력 enum 목록으로 직업 에셋 내부에 저장한다. SerializeReference와 능력별 ScriptableObject 에셋 참조를 사용하지 않는다.
- 능력의 설정값은 직업 에셋에 복사하지 않고 하나의 AbilitySettings ScriptableObject에서 관리한다.
- 직업 식별자는 MercenaryDataList의 MercenaryClass 키로만 관리하고 ClassDefinition 안에 중복 저장하지 않는다.
- 직업 정의의 원본은 ScriptableObject로 관리한다. 같은 데이터를 CSV에서도 수동 관리하는 이중 원본은 두지 않는다.

저장 형식과 전투 로직의 데이터 형식은 구분한다. 기존 전투 로직의 순수 C# 구조를 유지하도록 Unity 연결부에서 에셋을 검증하고 필요한 일반 C# 데이터로 전달하는 방향을 제안한다. 구체적인 변환 타입과 런타임 생성·참조 방식은 이후 설계한다.

ScriptableObject 자체가 불변성을 보장하지는 않는다. 공유 에셋은 읽기 전용 원본으로 취급하고, 현재 HP·버프·성장 결과는 런타임 데이터에서 관리한다. 직업 에셋은 Assets/GameData/Mercenaries의 Warrior.asset·Rogue.asset·Archer.asset이다.

### 7.5. AbilitySettings — 프로토타입 코드·에셋 구현

능력 종류별 공통 기본 설정을 하나의 ScriptableObject 에셋에 저장한다. ClassDefinition은 어떤 능력을 보유하는지만 선언하며, 같은 능력 종류는 모든 직업에서 같은 기본 설정을 사용한다.

현재는 능력별로 이름 붙은 설정 묶음을 일반 직렬화하여 에셋 내부에 포함한다. 능력별 독립 에셋, enum과 에셋을 연결하는 별도 등록 목록, 다형적 설정 목록은 두지 않는다. 능력 종류에 따른 명시적인 분기로 필요한 설정을 사용한다.

| 능력 종류 | 공통 설정 | 프로토타입 값 |
| --- | --- | --- |
| DirectionalPhysicalNegation | 정면·측면·후면 무효화 확률 | 정면 0.50·측면 0.10·후면 0 |
| RearGuaranteedCritical | 추가 설정 없음 | 설정 묶음이나 빈 에셋을 만들지 않는다. |

DirectionalPhysicalNegationSettings struct의 FrontChance·SideChance·RearChance를 float로 저장한다. 무효화 확률은 각각 유한한 0~1로 검증하며, 합계가 1일 필요는 없다. 모두 0이어도 유효하다. 설정이 없는 RearGuaranteedCritical을 누락된 설정으로 취급하지 않는다.

AbilitySettings는 읽기 전용 설정 데이터다. 발동 횟수·남은 시간·판정 결과 등 용병별 또는 전투별 런타임 상태를 보유하지 않으며, 능력 실행을 담당하는 전역 매니저로 사용하지 않는다. 전투에서 능력의 발동과 대상·방향 판정은 전투 로직의 책임이다.

공통 기본 설정을 변경하면 이후 해당 설정을 사용하는 모든 직업에 적용된다. 실행 중 에셋 변경의 즉시 반영은 이번 설계에 포함하지 않는다. 성장·장비·일시 효과에 의한 능력 보정이 필요할 경우 원본 설정 변경과 구분하여 별도로 설계한다.

공통 에셋은 Assets/GameData/Mercenaries/AbilitySettings.asset이며 MercenaryDataList가 참조한다. 목록 에셋을 로드하는 연결부와 전투에 전달할 일반 C# 데이터의 구체적인 구조는 미정이다. static 싱글턴이나 전역 접근 방식은 도입하지 않는다.

### 7.6. 직업 식별자와 MercenaryDataList — 코드·에셋 구현

MercenaryClass는 RaggedBanner.Mercenaries 어셈블리가 소유하는 순수 C# enum이다. Warrior = 0, Rogue = 1, Archer = 2로 정의하며, 기존 BattleUnitClass도 이 타입으로 통일한다. 직업 식별자가 필요한 전투·이벤트 등은 용병 도메인을 참조한다. Mercenaries는 전투나 Unity 에셋 계층을 참조하지 않는다.

ClassDefinition·AbilitySettings·MercenaryDataList와 에셋 검증은 RaggedBanner.MercenaryData 어셈블리에 둔다. MercenaryData는 Mercenaries의 직업·능력 enum과 Combat의 기존 AttackAttribute를 사용한다.

MercenaryDataList는 다음 참조를 보관하는 ScriptableObject다.

| 필드 | 형식 | 역할 |
| --- | --- | --- |
| _classes | SerializableDictionary<MercenaryClass, ClassDefinition> | 직업 식별자와 해당 직업 정의의 연결 |
| _abilitySettings | AbilitySettings 참조 | 모든 직업이 공유하는 능력 기본 설정 |

SerializableDictionary는 키와 값이 짝을 이루는 Entry 목록을 직렬화 원본으로 둔다. 조회용 Dictionary는 비직렬화 캐시이며 Entry 목록으로부터 만든다. 직렬화 원본과 캐시를 각각 수동 관리하지 않는다. 목록 검증은 원본 Entry를 확인하므로 중복 키나 잘못된 항목이 캐시 생성 과정에서 숨겨지지 않는다. 공유 원본의 실행 중 변경은 이번 범위에 포함하지 않는다.

MercenaryDataList.Validate(out error)가 성공한 이후에만 TryGetDefinition으로 직업 정의를 조회할 수 있다. 검증 전이나 검증 실패 후에는 조회에 실패한다. 목록의 OnEnable·OnValidate는 검증 상태와 조회 캐시를 무효화하고, SerializableDictionary의 OnAfterDeserialize는 조회 캐시를 무효화한다. 다시 사용하려면 명시적으로 검증한다. 검증과 캐시 무효화는 직렬화된 Entry 원본을 보정하거나 덮어쓰지 않는다.

SerializableDictionary와 MercenaryDataList의 검증은 다음을 확인한다.

- 직업 목록이나 원본 Entry 목록이 null이면 오류다.
- 모든 정의된 MercenaryClass가 정확히 한 번씩 등록되어야 한다. 빈 목록이나 직업 누락은 오류다.
- 정의되지 않은 enum 키, 중복 키, null인 ClassDefinition 참조는 오류다.
- 동일한 ClassDefinition 에셋을 여러 직업 키에 연결하면 오류다.
- 등록된 모든 ClassDefinition의 개별 데이터가 유효해야 한다.
- AbilitySettings가 연결되어 있으면 자체 데이터를 검증한다.
- DirectionalPhysicalNegation을 가진 직업이 하나라도 있으면 AbilitySettings 참조가 필수다. 설정 없이 사용하는 RearGuaranteedCritical이나 빈 능력 목록만으로는 공통 설정 참조를 요구하지 않는다.

MercenaryDataList.asset은 Warrior·Rogue·Archer 키에 각각의 직업 에셋을 연결하고 기존 AbilitySettings.asset을 참조한다. Assets/GameData/Mercenaries의 프로토타입 에셋은 직업 3개·공통 설정 1개·목록 1개로 총 5개다. 검증은 명시적으로 호출하며, 목록 에셋의 생성이 런타임 로드나 전투 초기화 연결까지 의미하지 않는다.

## 8. 최종 능력치 계산 구조 — 설계 예정

필요한 효과를 다음 출처에서 가져오는 방향을 검토한다.

- 직업 기본 능력치
- 파티 공유 레벨에 따른 직업 보상과 용병별 성장 선택
- 장비 효과
- 공용 특성과 직업 능력
- 파티 축복
- 전투 중 일시적 효과

이 목록은 합산 순서가 아니다. 각 출처의 모든 효과가 수치 보정인 것도 아니다. 구체적인 계산식, 합산 순서, 중첩·우선순위 규칙과 반올림·범위 제한은 미정이다.

축복은 파티가 보유하는 원정 단위 효과다. 각 MercenaryInstance에 복사하여 소유시키지 않고 계산에 필요한 파티 효과를 참조하는 방향을 제안한다. 구체적인 축복 효과가 미정이므로 축복만을 이유로 기본 능력치를 추가하거나 범용 효과 분류를 확정하지 않는다.

BlessingSystem에서 정한 지속 효과와 일회성 지급은 구분해야 한다. 능력치를 재계산하는 행위가 일회성 지급을 다시 실행해서는 안 된다. 회복이나 아이템 지급을 일회성 효과로 채택할 경우에도 같은 원칙을 적용하며, 이 예시 자체가 축복 콘텐츠를 확정하지는 않는다.

최대 HP 변경 시 현재 HP를 어떻게 조정할지는 별도 결정 사항이다. 능력치 재계산만으로 자동 회복이나 소생이 발생한다고 가정하지 않는다.

## 9. 전투 시스템과의 연결 — 제안

현재 전투의 직업 타입은 MercenaryClass로 통일했지만 BattleUnitStats.ForClass의 하드코딩된 테스트 수치와 기존 전투 동작은 유지한다. ClassDefinition·AbilitySettings·MercenaryDataList를 전투에서 읽어 적용하는 연결은 아직 구현하지 않았다.

1. 전투 시작 전 파티에서 HP가 1 이상인 용병을 참여 후보로 판정한다.
2. 실제 참가자의 능력치와 현재 HP를 바탕으로 BattleUnit을 생성한다.
3. 전투 중 HP·AP·남은 이동력 등의 변경은 전투 시스템이 관리한다.
4. HP가 0인 유닛은 기존 전투 규칙에 따라 전장에서 제거한다.
5. 승리 시 참가자의 최종 HP를 원정 용병 데이터에 반영한다.
6. 전투 불능 용병의 MercenaryInstance는 유지하며, 회복 전까지 이후 전투에서 제외한다.

전장에서 제거된 참가자도 결과 반영 대상에 포함되어야 한다. 남은 전장 유닛 목록만으로 결과를 구성하여 HP 0인 용병이 누락되지 않도록 설계해야 한다. 결과 기록의 소유자와 전달 인터페이스는 아직 정하지 않는다.

BattleSystem의 현재 `Waiting` 상태는 승리·패배 판정이 아니며, 전투 종료와 결과 전달 구현이 완료되었다고 가정하지 않는다.

승리가 확정되면 파티 경험치 1을 지급하는 성장 규칙을 적용한다. HP 결과 반영, 경험치 지급·레벨업, 성장 보상 선택과 이벤트 후속 결과의 구체적인 처리 순서는 미정이다.

EventSystem의 확정 규칙에 따라 전투 패배는 원정 종료로 연결한다. 일반적인 다음 전투 준비나 패배 이후 이벤트 후속 결과 적용으로 연결하지 않는다.

## 10. 이벤트 시스템과의 연결

현재 EventSystem의 조건과 결과는 개별 용병의 직업·스킬·HP 판정 및 HP 변경·영입을 지원하지 않는다. 현재 단계에서 개별 용병 ID에 의존하는 이벤트를 도입하지 않는다.

다음은 향후 검토 후보이며 확정 기능이 아니다.

- 특정 직업이나 능력·스킬 보유 여부에 따른 이벤트 선택지
- 이벤트 결과로 용병 HP 회복
- 이벤트를 통한 용병 영입

개별 용병의 HP를 변경하려면 기존 Result 및 Effect 구조의 확장이 필요하다. 마을 시설 등을 통한 회복은 이벤트 시스템과 별도로 구현할 수도 있다.

- 프로토타입 이후의 직업별 기본 수치와 최종 밸런스, 추가 능력치의 필요성

- ClassDefinition·AbilitySettings를 전투에 전달할 일반 C# 데이터 구조
- 생성 시 현재 HP 설정
- 파티의 시작 경험치
- 레벨업 후 경험치 기록 방식, 초과 경험치와 최대 레벨 도달 후 경험치 처리
- 성장 보상 선택·적용 시점과 승리 후 결과 처리 순서
- 중도 영입 시 이전 레벨 보상의 지급·선택 절차
- 도적·궁수·마법사의 각 3종 전문화 이름·역할·로어
- 전사 전문화를 포함한 모든 전문화의 Lv2·Lv5 실제 보상 스킬·특성, 전투 효과와 수치
- Lv3 공용 특성의 후보 제시 방식·선택 조건·효과
- 직업별 Lv4 스킬과 고정 지급·선택 여부
- 실제 보상의 수치·세부 개수와 전문화·선택 보상 기록 구조
- 스킬·특성·아이템의 상세 스키마와 아이템 인스턴스의 소유권
- 최종 능력치 계산식, 효과 중첩과 계산 순서, 재계산 시점
- 최대 HP 증감 시 현재 HP 처리
- 전투 중·전투 외 회복 및 HP 0인 용병에 대한 일반 회복 허용 여부
- 전투 가능한 용병이 한 명도 없을 때의 처리
- 전투 참가자 선정과 인원 제한
- 영입 후보 생성과 영입 이후 파티 편성
- 전투와 원정 사이의 결과 전달 인터페이스

기존 Plan의 최대 5인 파티와 현재 전투 구현의 인원 설정을 이 문서의 최종 정원으로 확정하지 않는다.

## 12. 다음 설계 순서

1. MercenaryDataList의 직업·능력 데이터 목록을 전제로 런타임 로드·참조 및 전투 데이터 전달 방식을 구체화한다.
2. 파티 공유 레벨·경험치와 MercenaryInstance의 개별 성장 선택을 구분하고, 생성 시 현재 HP 등 초기화 규칙을 정한다.
3. 원정 중 변경값과 전투 임시값, 전투 연결 시 전달할 데이터의 경계를 구체화한다.
4. 성장·장비 등의 기능을 연결할 때 필요한 능력치 계산·중첩 규칙과 HP 상태값 처리 방식을 결정한다.

기본 능력치 10개와 역할 구분, ClassDefinition의 ScriptableObject 저장 및 능력 enum 목록, 하나의 AbilitySettings를 통한 능력별 공통 기본 설정 관리는 합의했다. 해당 정적 데이터와 검증, MercenaryClass를 키로 사용하는 MercenaryDataList 및 프로토타입 에셋 5개를 구현했다. 성장 규칙은 파티 공유 레벨·경험치와 용병별 보상 선택, 프로토타입 시작 Lv1·최대 Lv5, 승리당 파티 경험치 1 및 다음 레벨 필요 경험치 `현재 레벨`로 확정했다. 용병 인스턴스·전투 연결과 나머지 스키마·계산 규칙은 필요한 범위부터 설계하며, 구현은 별도 요청 후 진행한다.
