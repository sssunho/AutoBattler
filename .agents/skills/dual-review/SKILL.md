# Dual Review

두 리뷰어가 같은 대상을 독립적으로 조사하게 하고, 메인 에이전트가 근거를 확인하여 최종 판정을 내린다. 리뷰 요청 자체는 수정 권한이 아니다. 재미 검증은 사용자가 담당하며, 리뷰어에게 재미 평가나 플레이 실험 설계를 요청하지 않는다.

## 적용 시점

- 명시적인 리뷰 요청 외에도 프로젝트 AGENTS.md에 따라 메인이 새 설계안 또는 실질적으로 변경된 설계안을 사용자에게 제시하기 전에 적용한다. 사용자에게 제시할 설계 초안을 두 리뷰어에게 전달한다.
- 이미 검토한 동일 설계의 재설명이나 승인 후 구현 때문에 같은 설계 리뷰를 반복하지 않는다. 리뷰어의 검토·대안 보고에는 이 호출 규칙을 재귀 적용하지 않으며, 사용자의 명시적인 리뷰 생략·단일 리뷰어 지시를 우선한다.

## 검토 대상 준비

- 대화에서 설계 리뷰인지 코드 리뷰인지 확인한다. 설계는 대화의 최신 합의, 메인이 준비한 초안 또는 지정 문서를 사용할 수 있으며 리뷰를 위해 파일을 만들 필요는 없다. 승인 전 초안은 기존 승인 사항과 구분한다.
- 최신 요구사항과 결정, 승인 범위, 관련 기획·로드맵, 구현 경로, 수행한 검증과 미실행 검증, 실행 권한을 간결한 공통 자료로 정리한다. 구현자의 기대 판정이나 다른 리뷰어의 결론은 초기 자료에 넣지 않는다.
- 현재 개발 단계, 이번에 구현·확인할 기능과 플레이 흐름, 명시적으로 보류한 범위를 공통 자료에 포함한다. 관련된 확정 규칙·검증용 수치·미정 사항을 구분하고, 후속 단계의 기능을 현재 단계의 완료 조건으로 취급하지 않는다.
- 코드 리뷰는 대상 변경과 기준점을 특정하고 관련 호출부까지 포함한다. 작업 트리에 여러 작업이 섞여 있으면 전체 diff를 이번 작업으로 취급하지 않는다. 확인 가능한 문맥으로 범위를 좁히고, 결과를 바꿀 필수 정보가 없을 때만 질문한다.
- 이 저장소는 대부분의 파일이 git에 추적되지 않으므로 git diff를 코드 리뷰의 기준점으로 쓰지 않는다. 코드 리뷰를 받을 승인된 구현 작업에서는 파일을 처음 수정하기 전에 대상 파일을 scratchpad의 `review/<작업명>/baseline/`에 프로젝트 상대 경로를 유지해 복사한다. 작업 중 새로 수정하게 된 파일은 수정 직전에 사본을 추가한다. 작업마다 새 디렉터리를 쓰고, 수정 후 재리뷰에서도 처음 만든 사본을 기준점으로 유지한다.
- 리뷰 직전 `review/<작업명>/pack/`을 만들고 경로를 공통 자료에 포함한다.
  - `files.md`: 수정·신규·삭제 파일 목록(Unity 도구로 저장된 에셋 포함), 사본을 만들지 못한 수정 파일 표시, 사용자 요청 범위(로그·주석·Scene 변경 요청 여부 포함).
  - `changes.diff`: 파일별 `git diff --no-index --ignore-cr-at-eol <사본> <현재>` 결과. 신규 파일은 빈 파일과 비교하고, 삭제 파일은 사본만으로 만든다.
  - `bytes.md`: 파일별 기준·현재의 CR 개수, 줄 수, 첫 3바이트.
- 검토 대상이 의존하는 데이터·에셋·직렬화 연결도 범위에 포함한다. Scene·Prefab·ScriptableObject·콘텐츠 데이터는 변경과 관련된 부분만 읽기 전용으로 확인하며 전체 에셋 감사로 확대하지 않는다.
- 프로젝트 AGENTS.md의 제한을 전달한다. 명시적으로 허용되지 않은 컴파일·빌드·컴파일을 유발하는 테스트, Scene 변경, Unity 실행 상태 변경을 수행하지 않는다.

## 두 리뷰어 호출

프로젝트 루트 기준 역할 파일:

- `.codex/agents/independent_reviewer.toml`: 요구사항 충족과 기존 기획·구현의 일관성.
- `.codex/agents/critical_reviewer.toml`: 구체적인 실패 시나리오와 경계조건·자원 수명.

1. 두 역할 파일을 읽고 호출 도구의 사용 가능한 역할을 확인한다. Codex에서는 `independent_reviewer`와 `critical_reviewer`, Claude에서는 `.claude/agents/`에 등록된 `independent-reviewer`와 `critical-reviewer`가 노출되어 있으면 각각 해당 역할로 서브에이전트를 호출한다. Claude 등록 역할은 `Read`·`Grep`·`Glob`만 가지므로 리뷰에 필요한 diff·측정값·git 기록은 검토 자료로 제공하며, worktree 격리 없이 호출한다.
2. 등록 역할이 현재 세션에 노출되지 않으면 역할 파일의 `developer_instructions` 전체와 공통 자료를 각각 별도의 일반 서브에이전트에 전달한다. 이 경우 등록 역할 대신 지침을 전달하여 실행했으며 도구 제한이 적용되지 않았음을 보고한다. 파일이 없거나 읽을 수 없으면 임의로 역할 내용을 복원하지 말고 누락을 알린다.
3. 초기 리뷰는 구현에 참여하지 않은 별도 에이전트 두 명으로 수행한다. 지원하면 `fork_turns="none"`으로 생성하고 준비한 자료를 명시적으로 전달하여 서로의 초기 결론이 섞이지 않게 한다. 모델은 사용자가 지정하지 않았다면 별도로 고정하지 않는다.
4. 각각 읽기 전용, 추가 서브에이전트 호출 금지, 실제 자료 및 호출부 확인, 대안 탐색, 위험 등급과 개별 판정 보고를 요청한다. 병렬 호출이 가능하면 병렬로 진행하고 두 결과를 모두 기다린다.
5. 두 명을 실행할 수 없으면 완료한 검토와 누락을 보고한다. 메인 에이전트의 자체 검토를 두 독립 리뷰로 대체했다고 표현하거나 최종 Pass를 내리지 않는다.

## 대안 탐색

- 두 리뷰어 모두 같은 요구사항과 제약을 만족하는 더 나은 대안이 있는지 탐색한다. 설계 리뷰에서는 접근 방식과 책임 분담을, 코드 리뷰에서는 실제 구현과 연결 구조를 비교한다. 현재 개발 단계와 검토 범위에서 실익이 있는 대안을 다룬다.
- 독립 리뷰어는 더 단순한 구조, 기존 구현의 재사용, 중복 상태·불필요한 의존성 감소를 중심으로 본다. 비판적 리뷰어는 실패 경로, 취소·재진입 처리와 자원 수명 위험을 줄이는 대안을 중심으로 본다.
- 유의미한 대안은 현재 방식 대비 이점·단점·적용 조건·변경 비용과 근거를 제시한다. 성능 이점은 확인한 비용이나 측정 근거와 추정을 구분한다. 뚜렷한 이점이 없으면 대안을 억지로 만들지 않고 더 나은 대안을 확인하지 못했다고 보고한다.

## 종합과 판정

- 각 지적의 위치, 발생 조건, 영향과 근거 및 범위를 메인 에이전트가 확인한다. 같은 원인의 중복 지적은 합친다. 의견 차이는 다수결로 결정하지 않고 관련 코드나 요구사항을 확인하며 필요한 경우 해당 리뷰어에게 좁은 후속 질문을 한다.
- 확인된 결함, 개선 대안, 미확정 설계 결정, 범위 밖 제안과 검증 한계를 구분한다. 대안이 있다는 사실만으로 현재 방식을 결함이나 Fail로 판정하지 않는다. 중요 지적을 기각하거나 위험 등급을 바꿀 때는 근거를 남긴다.
- 대안의 채택 여부는 메인이 근거, 변경 위험과 승인 범위를 확인하여 판단한다. 대안 제안 자체는 수정 권한이 아니며, 승인된 요구사항·외부 동작·책임 경계·변경 범위를 실질적으로 바꾸는 적용은 변경 설계를 제시하고 사용자 승인을 기다린다.
- **Fail:** 범위 내 확인된 높음 또는 중간 문제가 남아 있다.
- **Pass:** 두 리뷰가 완료되었고 필수 검토 근거가 확보되었으며 범위 내 높음·중간 문제가 없다. 낮음 문제와 실행 검증 한계는 별도 기재한다.
- **판정 보류:** 검토 대상이나 핵심 근거 부족 또는 리뷰어 미실행으로 위 판정을 책임 있게 내릴 수 없다. 단순히 실행 검증을 하지 않았다는 이유만으로 정적 리뷰를 보류하지 않는다.
- 최종 보고에는 검토 범위, 두 리뷰어의 개별 판정, 통합 지적(등급·위치·조건·영향·최소 수정안), 유의미한 대안과 채택·보류·기각 근거, 최종 판정과 근거, 실제 수행한 검증 및 한계를 포함한다. 지적이나 유의미한 대안이 없다면 명시하고 불필요한 표는 만들지 않는다.
- 설계 제시 전 리뷰에서는 확인한 지적과 대안을 검토하여 초안을 보완하고 설계와 리뷰 결과를 함께 제시한다. 보완한 부분과 영향받는 경로만 필요한 재검토를 수행한다. 남은 문제와 판단 한계를 공개하며, Fail·판정 보류·리뷰 미실행도 그 사실을 밝힌 설계 제시를 막지는 않는다. 리뷰 결과는 사용자 승인을 대신하지 않는다.
- 파일 수정이 별도로 승인되지 않았다면 파일을 변경하지 않고 검토 결과를 보고한다. 승인된 구현 작업에 포함된 리뷰라면 확인된 범위 내 결함을 수정하고, 바뀐 부분과 영향받는 경로만 재검토한다. 새 근거 없이 전체 리뷰를 반복하거나 Pass가 나올 때까지 결론을 유도하지 않는다.
